Status

Execution-ready planning state

The repo already has active and archived plan behavior, source sync, comments, queue delivery, CLI commands, and an index/review shell. This plan locks a small lifecycle extension: add a reversible deferred state for plans that should leave the active queue without becoming archive/history, and add first-class notes that stay with the plan and are readable by agents through CLI and API surfaces.

Goal

Let operators defer a plan with a reason/status note, find deferred plans later, resume them back into the active workflow, and attach persistent plan-scoped notes that agents can read before acting on the plan.

Why this plan exists

Archive currently hides plans as historical/quiet items. It is not the right product concept for “pause this because I need to pick it up later.” A deferred plan needs to be out of the active index, visible in a follow-up inbox, and carry durable context such as why it was paused, current state, or the next agent action.

Authority and inputs

  • User request: add a deferred state to plans for later pickup, and add notes that stay with a plan and are agent accessible.
  • Repo reality: README.md, src/schemas.ts, src/storage/database.ts, src/server/app.ts, src/cli.ts, src/server/sourceSync.ts, src/__tests__/contracts.test.ts.
  • Planning doctrine: the correct recovery/pickup path should be obvious; routine resume context should be embedded in the normal plan surfaces, not hidden in conversation memory.

Product intent alignment

Golden path

An operator can pause with one action: plan-review defer <planId> --note "why and next step" or the browser “Defer” action. The plan disappears from the active index, appears in a deferred inbox with the note and timestamp, stops source-sync work while paused, and can be resumed with one action. Agents can inspect plan-review notes list <planId> --json or GET /api/plans/:planId and receive the same durable context.

Locked lifecycle model

Use a single lifecycle source of truth with states active, deferred, and archived. Keep existing archived_at for compatibility and add deferred metadata rather than treating notes as state. Archive remains long-term/historical; deferred means paused-but-expected-to-resume.

Locked notes model

Plan notes are append-only records tied to plan_id, independent of plan versions and reviewer comments. They are not queue events requiring agent ack. Defer may create a note atomically, and regular notes may be added while active, deferred, or archived.

Source sync behavior

Deferred filesystem plans should unregister watchers and skip queued/in-flight source sync the same way archived plans do. Resuming a deferred plan should register the watcher and run a manual sync so the browser opens with current source content or a truthful sync warning.

Fail-closed boundaries

Do not auto-resume on source changes, comment activity, or reregistration. Reregistration may refresh metadata and latest content but must preserve the deferred state until the user or agent explicitly resumes it. Ambiguous slug errors should keep the existing “use plan ID” guidance.

Locked decisions

  1. Deferred is first-class lifecycle, not archive: active index excludes deferred and archived plans; /deferred lists deferred plans; /archive remains archive-only. The HTML planner must add navigation buttons between Active, Deferred, and Archived views in the same style as the current archive navigation, and plan/review pages must expose explicit Defer and Resume controls for moving plans in and out of deferred status.
  2. Notes are append-only: no edit/delete is required for this scope. A future task can add note editing if needed.
  3. Defer requires human/agent-readable context: browser and CLI defer flows require a non-empty note/reason. Direct API should validate this too.
  4. Resume preserves notes: resuming clears deferred state but leaves every note attached to the plan.
  5. Agent access is API/CLI first: agents should not need browser scraping to read notes or deferred reasons.

Acceptance criteria

  1. A registered active plan can be deferred with a required note/reason through API, CLI, and browser UI, including a visible browser Defer control on active plan pages.
  2. Deferred plans are hidden from the active index, shown in a deferred inbox, excluded from the archive page, and included by API only when requested or addressed directly. Active, deferred, and archived HTML pages include clear navigation buttons to the other lifecycle views.
  3. A deferred plan can be resumed through API, CLI, and browser UI, including a visible browser Resume control on deferred plan pages; it returns to active index visibility and source sync resumes safely.
  4. Plan notes can be added and listed for active, deferred, and archived plans through API and CLI; plan detail payloads include recent notes and latest-note summary.
  5. Defer creates or records the defer reason as plan-scoped note data so agents can understand why work paused and what to do next.
  6. Reregistering, filesystem sync, service restart rehydration, and source changes preserve deferred state until explicit resume.
  7. Errors are actionable: missing note, ambiguous plan identifier, not found plan, and invalid lifecycle transition explain the exact next action.

BDD scenarios

BDD-1: Defer an active plan

Given a filesystem-backed active plan is registered, when the operator defers it with “Blocked on PM review; next agent should revisit AC-3”, then the plan has lifecycle deferred, the note is stored with the plan, source watching stops, the active index omits it, and the deferred inbox displays the reason.

BDD-2: Resume a deferred plan

Given a deferred filesystem-backed plan with notes, when the operator resumes it, then lifecycle becomes active, notes remain visible, the plan reappears on the active index, the watcher is registered, and manual source sync is attempted once.

BDD-3: Agent reads durable plan context

Given a plan has multiple notes and a deferred reason, when an agent calls GET /api/plans/:planId or plan-review notes list :planId --json, then the response includes note IDs, bodies, authors, timestamps, and the latest note summary without requiring browser access.

BDD-4: Reregister preserves deferred state

Given a plan is deferred, when the source file is edited or plan-review register runs again for the same plan, then the plan remains deferred and quiet until explicit resume.

BDD-5: Missing defer reason fails clearly

Given an operator tries to defer without a note, when the API or CLI validates the request, then it rejects the transition and says to retry with --note "why paused and next step".

BDD-6: Notes stay with archived plans

Given a plan has notes, when it is archived and later restored or inspected, then those notes remain attached and visible through detail API and CLI note list.

Non-goals

  • No note editing/deletion, rich text, tagging, or attachments.
  • No changes to browser reviewer comments, queue claiming, ack/resolve semantics, or agent-next behavior.
  • No auth/permissions model for notes beyond the existing unauthenticated MVP boundary.
  • No automatic defer/resume rules based on comments, source file changes, or elapsed time.
  • No migration of existing reviewer comments into notes.
