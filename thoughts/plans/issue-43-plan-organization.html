Progress

Goal

Users should be able to organize a growing pile of planning documents as a kanban board grouped by project, configurable column status, lifecycle, and pin state, while keeping collaboration documents available through a separate Collab docs selector/view instead of mixing them into the plan board. The default plan-board columns are Backlog, Ready to Pull, In Progress, and Done; humans can move plan cards between columns by drag and drop, and agents can assign columns through CLI/API without editing source plan files.

Important boundary: execution readiness remains an independent agent-provided readiness signal, not the board column itself. A plan can be in Ready to Pull because a human moved it there, while the execution-ready signal still tells whether the reviewed plan gate has passed.
Important boundary: ⌘O must continue to cut across categories and document kinds. Selecting Kanban, All documents, Collab docs, lifecycle deep links such as Deferred/Archived, or any future board-status view must not constrain quick-open search; it should search all registered documents unless the user explicitly filters inside the palette later.

Solution narrative

Introduce a persisted organization model on top of the existing document records: use existing reviewMode to separate planning documents from collaboration documents; keep lifecycle state as active, deferred, or archived; add configurable kanban column definitions for planning documents; store each plan's current boardColumnKey; keep execution readiness as separate publication/readiness metadata; add derived/stored project identity; and add pinnedAt. Archive/defer remain lifecycle operations, while kanban columns represent human/agent-assigned workflow status for plans only.

The index becomes a document-kind-aware organizer with one consistent selector: Kanban | All documents | Collab docs. Kanban opens the board-first planning organizer with configurable columns, detailed cards, and no extra Kanban filter or pin controls in this slice; All documents shows mixed planning and collaboration discovery; Collab docs opens an independent collaboration-document list with kind/status/source/comment cues but no execution-ready/build/board-column controls. The review shell left navigator uses the same selector and preserves current-document visibility even when the active filter would otherwise hide it. The quick-open endpoint/search payload expands from active-only navigation to an all-documents search source so ⌘O can find active, deferred, archived, backlog, ready-to-pull, in-progress, done, execution-ready, pinned, and collaboration documents regardless of the currently selected category.

Product intent alignment

This plan advances the product intent by making board column, lifecycle, repository/project metadata, and execution-readiness easier to see and manipulate as the plan set grows.

  • Golden path decision: the default user flow is decided: users open the index, use the Kanban selector for the planning board, switch to All documents for mixed discovery or Collab docs for collaboration documents, read detailed planning cards, drag planning cards across kanban columns, open card details when more context is needed, and use ⌘O to jump anywhere. Pinning remains available outside Kanban cards.
  • Truthful state decision: the UI must show each state signal for what it actually means. reviewMode decides whether a document is a planning document or collaboration document; lifecycleState decides whether it is active, deferred, or archived; boardColumnKey is only a human/agent workflow column for planning documents; executionReady only comes from the reviewed-plan readiness gate; progress comes from checked phases; and pinnedAt only affects ordering. These signals must not be inferred from each other: moving a card to Ready to Pull does not make it execution-ready, archiving a completed plan does not erase its Done column, and collaboration documents must not show plan-only board, Build Plan, or execution-ready controls.
  • Safe defaults decision: migration must preserve what users already see today before adding new organization fields. Existing archived_at and deferred_at records become the explicit archived or deferred lifecycle state; ordinary active records stay active. On first run, the service creates the default plan-board columns Backlog, Ready to Pull, In Progress, and Done in a stable order, assigns existing planning documents to a deterministic valid column, and leaves collaboration documents outside the board. Existing Archive, Defer, and Resume commands keep changing only lifecycle state; they must not silently change a plan's board column, execution-readiness flag, project override, pin, comments, source-sync state, or notes.
  • Actionable recovery: invalid lifecycle/column transitions, failed drag/drop saves, and failed toggles return clear UI/CLI errors without losing plan reviewability.
  • Cross-surface consistency: API, CLI, index board, collaboration view, review shell navigator, quick-open, README, and tests describe the same document-kind, lifecycle, board-column, and execution-readiness semantics.

Locked decisions

  1. Use reviewMode as the document-kind source of truth. Planning documents are eligible for the Kanban board and plan execution controls. Collaboration documents are shown through All documents/Collab docs discovery views and must not be assigned board columns or execution-ready/build controls.
  2. Separate lifecycle, board column, and execution readiness. Lifecycle remains active, deferred, or archived. Board column is configurable workflow status for planning documents, defaulting to backlog, ready_to_pull, in_progress, and done. Execution readiness remains independent agent-provided metadata from the reviewed-plan gate.
  3. Board column is explicit organization metadata. Registration does not silently set board column from --execution-ready; humans and agents must set boardColumnKey explicitly through drag/drop or the column API/CLI when workflow status changes. Migration may backfill sensible initial values for existing rows only. Completeness remains a progress ratio for display and a migration defaulting signal, not the lifecycle state or execution-readiness signal.
  4. Preserve existing archive/defer behavior. Existing /archive, /deferred, CLI archive/defer/resume commands, and archive/defer buttons update lifecycle state during this slice without overwriting board column or execution readiness.
  5. Project is inferred, stored, and available as a grouping selector. Default project comes from repo/worktree metadata in this order: parent worktree/repo root basename when recognizable, then repoName. Humans and agents can explicitly override the stored projectKey/projectName through API/CLI when inference is wrong for monorepos, renamed worktrees, or repos that contain multiple product areas. The review-shell Project top-bar control is not an inline editor; it is a selector that jumps to the selected project's plans.
  6. Pinned plans are not a Kanban card control. Pins remain available in the review shell, API, CLI, and list/navigation surfaces, but the Kanban board is organized by workflow columns and ordinary card ordering. Kanban cards must not show pin buttons, pinned badges, or pinned-first ordering.
  7. ⌘O searches all registered documents. It must include every document kind plus every lifecycle, board-column, and execution-readiness combination, including active, deferred, archived, backlog, ready-to-pull, in-progress, done, execution-ready, pinned plans, and collaboration documents across projects. It may visually show kind/lifecycle/column/readiness/project badges, but it must not inherit the current organizer facet.
  8. The left navigator is always present in the review shell. Any directly opened document, including archived, deferred, done-column, backlog, or collaboration documents, must render with the left navigator. The navigator can prioritize nearby/active work and respect the Kanban | All documents | Collab docs selector, but it must include or highlight the current document and show truthful kind/lifecycle/column/readiness/project labels.
  9. Kanban columns are configurable, hideable, and persisted for plans. The service creates default columns Backlog, Ready to Pull, In Progress, and Done on first run, stores column order/labels/visibility in the local database, preserves configuration across service restarts, and applies those columns only to planning documents. Empty columns can be hidden from the Kanban board; occupied columns must be emptied before hiding so plans do not silently disappear.
  10. Toggling column/project/pin does not edit source HTML plans. Organization state lives in the plan-reviewer store so humans and agents can update it without changing reviewed plan content or source sync hashes.
  11. No authentication or sharing expansion. This is local organizer state for the existing trusted-network MVP, not a multi-user permission system.

Lifecycle, board column, and readiness defaulting rules

  1. If archived_at is present or lifecycle_state = 'archived', keep lifecycleState = 'archived'.
  2. Else if lifecycle_state = 'deferred', keep lifecycleState = 'deferred' and preserve existing deferred note behavior.
  3. Else keep lifecycleState = 'active'.
  4. On first run, create default board columns in this order: backlog (“Backlog”), ready_to_pull (“Ready to Pull”), in_progress (“In Progress”), and done (“Done”).
  5. For existing rows only, if progress has phases and all phases are complete, backfill boardColumnKey = 'done'.
  6. For existing rows only, if progress shows any started/incomplete implementation work, backfill boardColumnKey = 'in_progress'.
  7. Else set boardColumnKey = 'backlog'. Do not auto-move a plan to ready_to_pull from --execution-ready.
  8. New registrations and re-registrations default to backlog only when no stored boardColumnKey exists and no explicit column argument/API call is provided. --execution-ready remains publication/readiness metadata and must not change board column by itself; agents must call the column API/CLI explicitly when they want ready_to_pull, in_progress, or done.

Kanban column configuration persistence

Column configuration is repo-local service state for planning documents, not source-plan content. It must survive process restarts, service upgrades, and plan re-registration without changing HTML plan files or collaboration documents.

  • Storage: add a local board_columns table keyed by stable column keys with label, position, done/default markers, and optional hidden timestamp.
  • Validation: a plan move must target an existing non-hidden column and a reviewMode: planning document. Failed validation returns an actionable UI/API/CLI error and leaves the card in its previous column; collaboration docs reject board-column moves as not applicable.
  • Ordering: column position controls board layout; card ordering inside a column is pinned first, then selected sort such as activity or completion.
  • Configuration changes: renaming a column changes labels only; hiding/removing a column requires either an empty column or a replacement target so plans are never orphaned.
  • Restart recovery: startup creates missing default columns idempotently, reads persisted custom columns before rendering the index, and never overwrites custom labels/order during registration.
  • Events: column configuration changes and card moves should emit the same durable event shape used by other organization updates so browser views can refresh consistently.

Acceptance criteria

  1. Project organization: each plan exposes projectKey and projectName derived from worktree/root/repo metadata by default, supports explicit project overrides through API/CLI when inference is wrong, displays project identity on board cards and detail/list surfaces, and uses the review-shell Filter: Project control to narrow the left navigator/list rather than navigate away or edit the current plan.
  2. Document-kind separation and shared top bar: every appropriate index, list, configuration, and review-shell surface uses the shared top bar contract and screen matrix: one consistent Kanban, All documents, and Collab docs selector at the top, backed by existing reviewMode; Kanban shows the planning board, All documents shows mixed discovery, Collab docs shows collaboration documents independently, screen-specific controls appear in addition to the shared selector, and the current document remains visible in the review shell even when out of filter.
  3. Configurable board columns: the service creates default columns backlog, ready_to_pull, in_progress, and done for planning documents, lets users configure column labels/order/visibility, hides empty columns from the Kanban board when requested, prevents hiding occupied columns without moving plans first, and persists configuration across restarts.
  4. Card movement: humans can move planning-document cards between columns by drag and drop from the board; agents can change boardColumnKey through CLI/API with clear success/error output; collaboration documents reject board-column moves as not applicable.
  5. Independent readiness: existing --execution-ready / publication readiness remains an independent agent-provided signal and never silently changes boardColumnKey.
  6. Archive/defer compatibility: existing archive, unarchive, defer, and resume controls still work and update lifecycle state without overwriting board column or execution readiness.
  7. Pinning: plans can be pinned/unpinned from the review shell and CLI/API, and list/navigation surfaces may use pin state for priority ordering; Kanban cards do not expose pin controls, pinned badges, pinned styling, or pinned-first ordering.
  8. Sorting: Kanban columns use deterministic ordering by activity/title tie-breakers without pin priority; this slice does not add user-facing Kanban filter, sort, or pin controls.
  9. Scoped discovery controls: document-view selection separates Kanban, All documents, and Collab docs, but the Kanban board itself does not include project/lifecycle/readiness filter controls in this slice; those states appear as card metadata and in details instead.
  10. Global quick open: ⌘O fuzzy search includes all registered documents across projects, document kinds, lifecycle states, columns, and readiness states, including archived done plans, deferred backlog plans, execution-ready plans, in-progress plans, pinned plans, and collaboration documents.
  11. Truthful badges and controls: board cards, collab cards, list cards, review shell header/navigator, quick-open results, and archived/deferred deep links show the same kind/project/lifecycle/column/readiness/pin labels where applicable. Dense shell action buttons can be icon-only only when their full action text is preserved in aria-label and tooltip text.
  12. Informative board cards: each kanban card shows enough detail to identify the work without opening it: title, short executive summary, project, Linear/issue link state where issue IDs render as links, lifecycle, board column, execution-readiness state, phase progress, pending-comment count, source-attention state when present, and a Details/Open affordance for full metadata.
  13. All-documents index cards: the All documents view is not a Kanban board. It uses compact index/list cards that retain the current plan index metadata: title, summary, kind, project/repo/path, Linear issue link state, lifecycle, board column for plans, execution readiness for plans, progress, pending/resolved comment counts, source health, PR state, latest note when present, updated time, and archive/defer affordances where applicable. A Needs attention badge is reserved for source-sync or source-recovery conditions requiring operator action: missing source path, stale cached copy, failed source write, unresolved source conflict, or equivalent non-comment recovery state.
  14. Data preservation: existing local databases migrate without losing archived/deferred timestamps, notes, progress, source sync state, comments, registration metadata, board column assignments, or column configuration.
  15. Regression coverage: contract and e2e tests cover the shared top bar matrix across shown and unshown appropriate screens, document-kind filtering, current-document safety, migration, column config persistence, drag/drop card moves, column/pin APIs, index board rendering, collab docs view rendering, sort order, review shell controls, quick-open all-document search, and old archive/defer paths.

BDD scenarios

Project metadata is visible on cards

Given registered plans from plan-reviewer, doct, and heddle, when the user opens the Plans Kanban board, then each card shows its project identity so the user can understand where the work belongs without using a project filter.

Plans and Collab docs are separate views

Given the service has active planning and collaboration documents, when the reviewer selects Kanban, then planning documents appear on the board; when they select All documents, then planning and collaboration documents appear in mixed discovery; when they select Collab docs, then collaboration documents appear in an independent list without board-column, execution-ready, or Build Plan controls.

Current document remains visible outside selected kind

Given the reviewer is viewing a plan, when they select Collab docs in the review shell, then the current plan stays visible as the active navigator item, the rendered plan remains commentable, and only discovery lists are filtered.

Dragging a card persists its column

Given a plan has lifecycleState: "active" and boardColumnKey: "backlog", when a human drags it to Ready to Pull, then the card moves columns, the review shell badge updates after reload, the API returns boardColumnKey: "ready_to_pull", and the source HTML file is not modified.

Agent can set a board column explicitly

Given an agent has completed execution-ready review for a plan and re-registered it with --execution-ready true, when it separately runs the column update CLI/API to set ready_to_pull, then the plan appears in Ready to Pull, keeps its current lifecycle state, shows execution-ready as an independent badge, and no source HTML file is modified.

Kanban cards stay workflow-focused

Given a plan has been pinned elsewhere, when the user views the Kanban board, then the card does not show a pin button, pinned badge, pinned styling, or pin-priority sort; the board remains focused on workflow column status.

Cmd-O ignores category scope

Given the user is viewing the Plans Kanban board, when they press ⌘O and type a matching archived doct plan title, then the archived doct plan appears in results with project/lifecycle/column/readiness badges and can be opened.

Existing defer flow preserves board column

Given a plan is in board column in_progress, when the user clicks Defer plan and adds a note, then lifecycleState becomes deferred, boardColumnKey remains in_progress, the note is saved, and the existing Deferred page/deep link still shows it.

Collab docs cannot be moved to board columns

Given a document has reviewMode: "collaboration", when a client or CLI tries to set boardColumnKey, then the service rejects the move with a clear not-applicable error and leaves the collaboration document reviewable in the Collab docs view.

Existing database migrates safely

Given a database with active, deferred, archived, execution-ready, in-progress, and complete plans plus collaboration documents but no board columns, when the service starts after migration, then default board columns are created, every planning document receives deterministic lifecycle/column/project values, collaboration documents keep reviewMode: "collaboration" without board assignment, no comments are lost, and old archive/defer routes still work.

Column configuration survives restart

Given the user reorders the default columns Backlog, Ready to Pull, In Progress, and Done, when the service restarts and the index is reopened, then the configured order is still present and every plan remains in one of the actual default columns.
