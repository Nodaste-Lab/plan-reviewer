Issue 33: Filesystem Live-Link Stale Sync Plan

Status: validation-complete; implementation reviews and regression gates passed

Source issue: GitHub issue #33. No Linear issue exists for this GitHub-only intake.

Goal

Make filesystem live-link sync trustworthy: whenever a sync reports synced, advances lastSyncAt, or exposes a latest version, the stored source metadata and rendered HTML must match the current on-disk source file that triggered the sync.

Solution narrative

Fix the bug by making source sync commit from a verified fresh source snapshot, not merely from a watcher event. The sync path should read the source and stat information together, reject or retry unstable snapshots, render only those verified bytes, commit version metadata from the same snapshot, then verify the stored latest version still matches that snapshot before reporting success. The existing last-good-render safety behavior remains: if the source is missing, incomplete, unsafe, or mutating under the service, keep serving the previous good render and surface actionable sync metadata instead of claiming success.

Why this plan exists

Issue #33 reports silent staleness: after editing a registered live-linked HTML file, GET /api/plans showed lastSyncStatus: synced, a fresh lastSyncAt, and a new version signal, while latestVersion.sourceSize stayed at the old byte count and GET /render/<planId> continued serving previous content. A manual plan-review register ingested the edit, proving the source file was valid and the automatic ingestion path was the problem.

Current implementation reality

Source sync flow

SourceSyncService.register() watches the source file and discovered local assets with chokidar. Change events debounce for 500ms and call syncNow(planId, 'filesystem_watch').

Commit path

performSync() stats and reads plan.sourcePath, computes a hash, renders the payload, and calls store.registerPlan(..., 'filesystem_watch') when the hash or rendered output differs from the latest stored version.

Success metadata path

When the read hash and rendered output match the current latest version, performSync() calls markPlanSyncSucceeded(), which advances sync metadata and emits plan.version.synced without re-validating source size or render content against disk.

Storage contract

registerPlan() stores source_mtime_ms, source_size, raw HTML blob, rendered blob, and sync_origin on plan_versions. /render/:planId serves the stored rendered blob for the latest version.

Existing coverage

Contract tests cover missing sources, partial/incomplete writes, startup rehydration, image-asset watches, and ordinary source changes. They do not yet assert the invariant from issue #33: every successful automatic sync must make latestVersion.sourceSize equal the current on-disk byte count and render the latest sentinel.

Product intent alignment

  • Desired outcome advanced: plan authors can trust live-linked HTML plans to stay synchronized with source files while preserving review context and safe rendered output.
  • Truthful status: synced must mean the service ingested and serves the latest safe source snapshot; it cannot mean “a watcher event fired.”
  • Safe default: if the service cannot prove the source snapshot is fresh and stable, keep serving the last good render and report a retryable sync state.
  • Self-healing: routine race or partial-write conditions should automatically retry on the next stable change; manual re-registration remains an escape hatch, not the normal recovery path.
  • Actionable errors: failure metadata should say whether the source was missing, incomplete, unsafe, or changed during sync, what the service already did, and that the last good render is still being served.

Locked decisions

  1. The filesystem source remains authoritative. The service cache/history is derived state for live-linked plans.
  2. Successful sync requires a post-commit invariant. After automatic sync, latest stored sourceSize and rendered output must correspond to the source snapshot that was read from disk.
  3. Last good render remains the fail-safe. Do not overwrite a good rendered plan with stale, incomplete, or unverified bytes.
  4. Manual re-register is not the fix path. The automatic watcher path must self-heal normal edits without asking users or agents to rerun plan-review register.
  5. Asset-only changes remain supported. Verifying HTML source freshness must not break existing relative-image watch behavior.
  6. Do not trust cached version metadata as proof of disk freshness. The success branch must compare against a fresh source snapshot and current stored version metadata before claiming synced.

Acceptance criteria

  • AC1: After any successful filesystem-watch sync, GET /api/plans/:planId reports latestVersion.sourceSize equal to fs.statSync(sourcePath).size for the synced source snapshot.
  • AC2: After editing the source file to include a unique sentinel, GET /render/:planId for the latest version contains that sentinel before sync status is reported as successful for the edit.
  • AC3: If the source changes while a sync is reading or committing, the service does not emit a misleading success for the old bytes; it either retries or records a retryable failure while keeping the last good render.
  • AC4: The unchanged-content success path may advance lastSyncAt only when the latest stored sourceMtimeMs and sourceSize both match the current disk snapshot; if either field changed since the stored version, treat the read as potentially stale and do not call markPlanSyncSucceeded().
  • AC5: Missing, incomplete, parse-invalid, and unsafe source states continue to keep the last good render with actionable failure metadata.
  • AC6: Complete smaller rewrites and asset-only changes still sync automatically and refresh already-open review pages.
  • AC7: Startup rehydration uses the same fresh-snapshot invariant as watcher sync and cannot mark stale cached content as newly synced.
  • AC8: Manual plan-review register remains compatible and continues to update the same plan thread with correct source metadata.

BDD scenarios

BDD1: larger edit becomes rendered latest content

Given a live-linked filesystem plan is registered, when its source file is edited to a larger complete HTML document containing a unique sentinel, then the latest plan metadata reports the new byte size and /render/<planId> contains the sentinel.

BDD2: stale success is blocked

Given a sync observes or attempts to commit bytes that no longer match the current source file, when the sync completes, then it does not report synced for that stale snapshot and does not expose a latest version whose sourceSize differs from disk.

BDD3: stable source recovers automatically

Given a sync was rejected because the source changed during ingestion, when the file is stable on the next watcher cycle, then source sync ingests it, clears the warning, and serves the new render without manual registration.

BDD4: no-op sync is truthful

Given a live-linked source file has not changed since the latest stored version, when a watcher event fires anyway, then the service may update lastSyncAt only after confirming the stored metadata still equals the fresh disk snapshot.

BDD5: incomplete source remains last-good

Given a source file is missing terminal HTML structure or cannot be rendered safely, when source sync runs, then the service keeps the last good render and reports actionable failed sync metadata.

BDD6: asset-only sync still works

Given HTML source is unchanged and a watched relative image changes, when source sync runs, then the rendered asset hash changes and the sync status remains truthful.

BDD7: startup does not bless stale cache

Given a filesystem plan exists in the database and the source file changed while the service was down, when startup rehydrates source sync, then the service reads the current file and either serves that current content or reports a truthful failure; it does not mark the old cached render as newly synced.

P2: commit from verified source snapshots

End State

performSync() reads, renders, stores, and reports success from a single verified source snapshot. It does not mark stale cached content as synced.

Tests first

Run P1 tests and confirm the stale-success cases fail before implementation.

Expected files

  • src/storage/database.ts only if a narrow store helper is needed to compare latest version metadata without widening public API

Work

  • Introduce a small source snapshot helper that performs stat → readFile → stat, computes fileHash, and rejects/retries if size or mtime changes across the read.
  • Keep the existing complete-HTML guard from issue #10 in the same path, so incomplete writes and startup rehydration remain fail-safe.
  • Build the RegisterPlanInput only from the verified snapshot: html, fileHash, sourceMtimeMs, sourceSize, and discovered assets must describe the same bytes.
  • For the “unchanged content/render” branch, confirm the latest stored source metadata still matches the fresh snapshot before calling markPlanSyncSucceeded(). If metadata differs, re-register/update the version metadata or fail and schedule retry; do not silently claim synced.
  • After store.registerPlan(), re-read the stored latest version and assert its sourceSize and rendered blob correspond to the snapshot before emitting the success event. Do not call this.bus.emitEvent(result.event) until that post-commit check confirms the stored version matches the snapshot.
  • If the source changed during sync, record a retryable failure such as stale_source_snapshot with next-action text that says the last good render is still served and source sync will retry on the next stable change.
