Add Build Plan Button

Execution-ready plan for adding a top-nav plan action and improving progress visibility while plans are being executed.

Status: execution-readyScope: plan action + progress monitoringRisk: medium-low

Progress

Goal

Add a Build Plan button to the top of every plan review page and make active execution progress easier to monitor from both the HTML plan and the plan index. The button should work like the existing Request execution-ready review button: clicking it creates one pending, agent-visible comment in the plan queue. The comment body must be:

/skill:scoped-plan-run thoughts/plans/<plan filename>

Once execution starts, reviewers should be able to see plan progress immediately: the plan document should keep Progress at the top, and the active index should prioritize plans with started progress, sorted from most complete to least complete.

Why this plan exists

The plan-review UI already supports queuing agent work through the execution-ready review button. This feature adds the adjacent golden path for the operator: once a plan is ready, they can request implementation directly from the review page without copying a command out of band. Reviewer feedback also clarified that the reviewer should remain useful after execution starts, so progress needs to be prominent in the plan document and active execution should rise to the top of the index.

Authority and inputs

  • User request: add a button labeled Build Plan that executes /skill:scoped-plan-run thoughts/plans/<plan filename>.
  • Existing implementation: src/server/app.ts renders the review shell, client JS, and plan action endpoints.
  • Existing test precedent: src/__tests__/contracts.test.ts has coverage for the execution-ready review button and queue event.
  • Registered plan metadata source: PlanReviewStore.getPlan() exposes plan.planPath.
  • Reviewer comment on this plan: move plan progress to the top of the document and sort actively executing plans first in the index, from most complete to least complete.

Product intent alignment

The obvious operator action should be available in the normal review page. The service should not launch a local process directly from browser state; it should preserve the established safe queue contract by creating an agent-visible comment that an authenticated agent harness claims and executes. Once that work starts, the normal monitoring surfaces should highlight progress without requiring the operator to hunt through a long plan or manually filter the index.

Locked decisions

  • Queue, not direct shell execution: the button creates a pending comment, matching the execution-ready review button and avoiding browser-triggered process execution.
  • Command body: the exact body format is /skill:scoped-plan-run thoughts/plans/<plan filename>.
  • Filename source: derive <plan filename> from path.basename(plan.planPath), then prefix thoughts/plans/. This matches the user-specified command shape even if the registered path includes repo-relative directories.
  • Anchor: use a body-level DOM anchor with textPreview: "Plan build request", paralleling the review request endpoint.
  • Progress placement: keep Progress directly after the plan header in this plan artifact so execution status is visible without scrolling.
  • Index active-progress sort: treat a plan as actively executing when progress.totalPhases > 0 and progress.completedPhases > 0. Sort those plans before not-started plans by completion ratio descending, with existing activity/name ordering as the tie-breaker.

Acceptance criteria

  1. Every plan review page at /p/:planId includes a visible Build Plan button with id="build-plan".
  2. Clicking the button posts to a build-request endpoint and creates one pending comment.
  3. The created comment body exactly equals /skill:scoped-plan-run thoughts/plans/<plan filename>.
  4. The created comment has conversationPayload.type === "browser.comment.v1" and is visible to the queue-backed agent flow.
  5. The queue poll emits a comment.created event for the build request.
  6. Existing execution-ready review, archive, restore, comments, and mobile nav behavior remain intact.
  7. This plan document has Progress immediately after the header so execution state is visible at the top of the reviewer page.
  8. The active index lists plans with started progress before not-started plans and sorts started plans from most complete to least complete.

BDD scenarios

BDD-1 - Build request happy path

Given a registered plan whose path is thoughts/plans/sample-plan.html, When the user clicks Build Plan, Then the service creates a pending comment with body /skill:scoped-plan-run thoughts/plans/sample-plan.html.

BDD-2 - Agent queue visibility

Given the build request comment is created, When the agent queue is polled from sequence zero, Then a comment.created event is returned and the comment payload is a browser.comment.v1 payload.

BDD-3 - Request failure

Given the endpoint returns a non-OK response, When the user clicks Build Plan, Then the client re-enables the button and shows an actionable failure alert without changing page state.

BDD-4 - Existing action parity

Given the Build Plan button is present, When the existing execution-ready review and archive/restore actions are used, Then their previous endpoints, IDs, and behavior still work.

BDD-5 - Active progress index priority

Given the active index contains one not-started plan, one 25% complete plan, and one 75% complete plan, When the index renders, Then the 75% plan appears first, the 25% plan appears second, and the not-started plan appears after started plans.

BDD-6 - Complete plan ordering

Given a complete plan has all phases checked, When the active index renders alongside partially complete plans, Then the complete plan appears above partially complete started plans because it is the most complete active plan.
