Plan Reviewer Modes: Planning and Agent Collaboration

Plan for evolving plan-reviewer from a plan-specific reviewer into a multi-mode HTML review surface. Planning mode preserves the reviewed-plan workflow; collaboration mode lets a human converse with an agent through anchored document comments and document updates.

Status

execution-ready. Browser feedback has been processed, first-round blocker findings were integrated, and both Codex and Claude Code R2 reviews agreed the plan is ready for implementation.

Goal

Reframe plan-reviewer around explicit review modes rather than one plan-specific product. The shared platform should host HTML documents, capture anchored comments, maintain threaded conversations, publish comment events through a queue, and let agents update documents. Planning becomes one supported mode; agent collaboration becomes another.

Solution narrative

Keep plan-reviewer as the proven local review substrate, but introduce a mode layer that controls document constraints, top-bar actions, routing, and agent behavior. Planning mode enforces reviewed-plan structure, keeps planning-specific buttons and readiness metadata, and treats each comment as plan-iteration feedback. Collaboration mode removes planning-specific chrome and format enforcement, treats each comment as a document-scoped conversation with an agent, and lets the agent update the document as the conversation progresses.

Smallest complete slice

Two explicit modes share the same render/comment/thread/queue infrastructure: existing planning mode remains compatible, and a new collaboration mode can host one Hermes-published HTML document, accept one anchored comment, deliver it to Hermes, show the agent reply inline, and sync a source update back into the open review page.

Review modes

Planning mode

  • Each comment iterates on the plan artifact.
  • Threaded conversations are supported for clarification and follow-up.
  • Planning-specific buttons remain at the top of the screen, including readiness/review actions.
  • Plan-specific document format is enforced for reviewed HTML plans.
  • Execution-readiness metadata and plan index semantics remain intact.

Collaboration mode

  • Each comment is a conversation with an agent about the selected document context.
  • Agent responses are visible inline as thread replies.
  • The agent can update the document in response to the conversation.
  • No planning-specific buttons appear at the top of the screen.
  • No planning-specific document format is enforced.
  • Future collaboration-specific buttons may be added after the basic conversation/update loop works.

Mode selection policy

Mode should be selected automatically when a document is published. The publishing agent is responsible for choosing the appropriate interaction mode from the document type and intent: reviewed implementation plans default to planning mode; general documents, drafts, mockups, briefs, or other agent-collaboration artifacts default to collaboration mode. Operators and agents can change a document's mode after publication when the inferred mode is wrong or the workflow changes.

Shared infrastructure

Both modes must share DOM/text/image selection, comment markers, threaded conversations, durable storage, pub/sub comment queue, source sync, safe rendering, and agent delivery infrastructure. Mode-specific behavior should be configuration and policy on top of that substrate, not duplicate implementations.

Execution contracts

These contracts remove implementation-time invention from the first slice. The user-facing term is “document,” but the first implementation keeps the existing plan storage and routes unless a listed phase explicitly changes them.

Mode model

Add reviewModeSchema = z.enum(['planning', 'collaboration']) and persist it as plans.review_mode TEXT NOT NULL DEFAULT 'planning'. API records expose reviewMode. Existing rows, URLs, blobs, comments, and index records backfill to planning during migration without changing IDs.

Mode inference is server-side only when the caller omits reviewMode: payloads with publicationMetadata.executionReadyBasis default to planning; general HTML documents without planning metadata default to collaboration; the thoughts/plans/ path is a secondary compatibility signal for legacy plan publication. Explicit --review-mode / API reviewMode overrides inference, and PATCH /api/plans/:planId with a { reviewMode } body updates only mode policy, not the source file.

Registration contract

Planning mode continues to require publicationMetadata.executionReady and executionReadyBasis: 'agent-review-results'. Collaboration mode reuses the register endpoint but may omit publicationMetadata; the API/UI must not synthesize execution-ready state for collaboration records and must hide readiness chrome. The CLI keeps current register ... --execution-ready behavior for planning mode and adds --review-mode collaboration for non-plan documents.

Thread entry model

Add comment_thread_entries with id, plan_id, comment_id, sequence, role (human, agent, system), body, created_by_json, optional claim_id, optional delivery_adapter, optional action_json, and timestamps. sequence is a monotonic integer starting at 1 and incremented per comment thread. The original browser comment creates the first human entry. Agent replies append entries; ack/resolve remain lifecycle state and never substitute for a visible reply. Existing agent_response_json/action.responseSummary is read only as legacy display/backfill input.

Hermes delivery contract

Extend delivery adapters from codex to codex | hermes. Hermes supports fake for fixtures and webhook for the first real transport. The delivered payload includes planId, commentId, claimId, reviewMode, sourcePath, anchor/context, screenshot metadata, and thread history. A successful Hermes result may include replyBody and changed-file metadata; the worker appends the reply entry, then acks with the active claim. Ambiguous session/document routing fails closed and leaves the claim retryable.

Multi-document queue contract

P5 adds an atomic cross-document claim path for Hermes: POST /api/agent/queue/claim and plan-review agent next --all --adapter hermes --json. It selects one pending comment across active, non-archived records matching mode/adapter filters, returns the same agent next claim shape plus reviewMode, planPath, and source metadata, and never pre-claims comments for an unavailable adapter.

Product intent alignment

This plan advances the existing product intent by generalizing the same durable browser-comment workflow without weakening its trust bar.

  • Extends “agents publish reviewable HTML artifacts with stable URLs” beyond implementation plans through explicit modes.
  • Preserves durable, deduplicated, queue-visible, recoverable comment delivery as shared infrastructure across all modes.
  • Keeps the simplest reviewer workflow: open URL, select content, submit comment.
  • Extends the simplest agent workflow: drain/watch, claim, converse/update, ack, repeat.
  • Respects current non-goals by keeping planning format enforcement in planning mode only; collaboration mode supports document conversation and updates without becoming a full collaborative editor in the first slice.

Acceptance criteria

  1. Mode registration: Records expose reviewMode: planning | collaboration, the server infers the mode when omitted, and existing records migrate to planning mode without URL/comment/index regression.
  2. Mode changes: Operators and agents can change a document's mode after publication through CLI/API, and the UI/status reflects the new mode truthfully without editing the source HTML.
  3. Planning mode: Existing reviewed-plan behavior remains intact: planning buttons, execution-readiness metadata, and format enforcement.
  4. Collaboration mode: Hermes can publish/register a non-plan HTML document with --review-mode collaboration and no execution-readiness metadata, without planning-specific top-bar buttons or plan format enforcement.
  5. Annotate: A reviewer can select DOM/text/image content in either mode and submit a comment with preserved anchor context.
  6. Deliver: Hermes can subscribe to collaboration comments through the hermes delivery adapter or cross-document agent next --all queue path and receive enough context to respond or fail closed.
  7. Thread: Hermes replies are persisted as ordered comment_thread_entries and visible inline inside the same browser conversation thread as the human's original comment and follow-up replies, not as separate Hermes-initiated comments or hidden ack metadata.
  8. Update: Hermes can update the source-backed HTML document and the browser view refreshes without losing comments.
  9. Fan-out: A single Hermes watcher can safely monitor multiple active documents through an atomic cross-document claim API and route comments by mode/session/document context.
  10. Safety: General document hosting remains local/trusted-network by default with no script execution in documents unless explicitly designed later.
  11. Conflict alert correctness: The comments drawer shows the background-update/conflict alert only when there is an actual active comment conflict or stale edit state, not as default drawer chrome.
  12. Docs/tests: CLI/API/UI docs and contract/e2e/fixture tests describe the same mode lifecycle.

BDD scenarios

Scenario: automatic mode selection

Given an agent publishes a reviewed implementation plan under thoughts/plans/ or with execution-readiness metadata, when the document is registered without reviewMode, then the server stores reviewMode: planning. Given the agent publishes a general HTML collaboration document without planning metadata, then the server stores reviewMode: collaboration. Given an explicit CLI/API mode override, then the explicit value wins and either the operator or agent can later change it through the mode-change API.

Scenario: planning mode keeps plan behavior

Given an existing reviewed HTML plan, when it is opened in planning mode, then plan-specific buttons, execution-readiness metadata, required format checks, and current browser-comment workflow remain available.

Scenario: collaboration mode comment and reply

Given Hermes publishes a file-backed HTML document in collaboration mode, when Aaron comments on a DOM element in the browser, then the original comment creates a human thread entry, Hermes receives one claimed comment payload with thread history, Hermes replies by appending an agent thread entry, the worker acks the claim, and the thread shows both turns without planning-specific chrome.

Scenario: update source and sync

Given a source-backed collaboration document with comments, when Hermes edits the source HTML in response to a comment, then the rendered document syncs safely, the open review page refreshes, and existing comment history remains attached or truthfully marked stale.

Scenario: multiple documents and modes

Given watched planning and collaboration documents with separate Hermes contexts, when comments arrive across all documents, then agent next --all --adapter hermes atomically claims one processable comment at a time, includes mode/document/session metadata, and routes it to the correct session without cross-talk or starving older pending comments.

Scenario: ambiguous or unsafe routing

Given a comment cannot be mapped to a known Hermes session, document, or mode policy, when delivery is attempted, then the system fails closed with an agent-legible error and leaves the comment pending/retryable rather than silently dropping or misrouting it.

Verification strategy

Use the existing repo bar and expand it where collaboration mode differs from planning mode.

  • Contract tests for mode schema, CLI/API lifecycle parity, and legacy planning compatibility.
  • Playwright e2e for mode-specific chrome plus shared browser comment/thread/update UX.
  • Fixture smoke tests for queue and Hermes delivery semantics across multiple documents.
  • Sanitizer and host-boundary tests for safe default document rendering.
  • README/CLI examples validated directly or by fixture harnesses.

Delivery order

  1. Preserve existing planning-mode behavior with contract tests before adding collaboration mode behavior.
  2. Land explicit mode registration, automatic mode inference, mode-change commands, and mode policy behind non-disruptive compatibility defaults.
  3. Add shared thread infrastructure before mode-specific collaboration delivery.
  4. Add collaboration-mode Hermes delivery with a fake adapter first, then real Hermes integration and source updates.
  5. Add multi-document watch after single-document collaboration routing is proven.

Non-goals

  • Do not build a full Google Docs/Figma-style collaborative editor in the first slice.
  • Do not turn the unauthenticated local MVP into public multi-tenant hosting without a separate security plan.
  • Do not support arbitrary document-authored JavaScript by default.
  • Do not regress existing planning-mode reviewed-plan workflows, plan metadata, or execution-readiness gating.
  • Do not design a complete set of collaboration-specific buttons before validating comment-thread conversation and source updates.
  • Do not solve every Hermes platform delivery surface before validating local/browser/Hermes loop.
