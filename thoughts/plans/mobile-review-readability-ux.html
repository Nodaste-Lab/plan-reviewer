Mobile Review Readability and UX

Make plan reviews readable and commentable on phones without weakening the existing desktop review shell, queue-backed comment lifecycle, or source-linked plan artifact model.

Goal

Reviewers on a phone should be able to open a plan review URL, read the plan without pinch-zooming or horizontal panning for normal prose, understand comment status, open comments as an intentional tray, and leave a precise comment on text, DOM blocks, images, or diagrams with native-feeling touch behavior.

Decision Attention / Low-confidence Areas

No product decision required. Browser feedback requested the execution-ready review for this plan. The defaults are locked for this implementation slice: reading-first mobile shell, bottom comments tray, bottom-sheet composer, and contained overflow for genuinely wide content.

  • Mobile navigation default locked: hide the desktop plan navigator on phones and rely on index/quick-open/comment controls for this slice. A dedicated mobile navigator drawer is a future follow-up, not required to make reviews readable.
  • Wide content policy locked: normal prose/tables/code/images should fit the viewport; genuinely wide diagrams and tables get an obvious horizontal scroll affordance rather than being scaled to illegibility.
  • Composer flow locked: keep the current mobile bottom-sheet composer position and add selection/quote context, keyboard-safe controls, and stronger dismissal protection.

Solution narrative

Implement a mobile reviewer mode that treats the plan as a readable document first, then layers review actions around it. The parent shell keeps the current native scroll and transparent touch overlay, but the rendered iframe receives a mobile readability stylesheet after plan content loads. The shell chrome collapses into compact controls, comments become a bottom tray, and the composer becomes a keyboard-safe bottom sheet with selection context.

The implementation should not edit plan source files or require authors to manually make every historical plan responsive. The viewer owns the mobile adaptation while the plan HTML remains the authoritative source.

Authority and inputs

  • User request: “our plan viewer is not responsive to viewing on mobile… make reviews on mobile readable and improve ux.”
  • Repo guidance: AGENTS.md requires reviewed HTML plans, product-intent alignment, e2e gates for UI/comment-shell work, and no product code edits during planning.
  • Product intent: thoughts/specs/product_intent.md says the simplest reviewer workflow must work without extra setup, browser comments must be durable, and browser interactions/rendered markers need e2e coverage when changed.
  • Observed source: src/server/app.ts review shell markup/CSS/JS; src/render/render.ts sanitized iframe render; src/test-fixtures/e2e-run.ts existing mobile/touch e2e coverage.

Current implementation reality

Review shell already has a mobile mode

clientCss in src/server/app.ts activates at @media(max-width:760px),(pointer:coarse). It hides the plan navigator, makes #review the native scroll container, uses #plan-touch-layer as the tap surface, and turns comments into a bottom sheet.

Rendered plan content is not normalized for mobile readability

The iframe loads arbitrary sanitized plan HTML from /render/:planId. Plan-authored CSS remains active, and the viewer does not currently inject a general mobile reader stylesheet for prose, tables, code blocks, figures, mermaid output, or historical plan layouts.

Mobile tests protect touch mechanics, not reading quality

src/test-fixtures/e2e-run.ts already asserts native mobile scrolling, tap-layer behavior, link handling, text/image annotation, mobile comments toggle, and tablet/coarse-pointer behavior. It does not assert that typical plan content is readable without horizontal overflow or pinch zoom.

Risk is CSS collision and marker drift

Any viewer-injected mobile stylesheet must be scoped to mobile/coarse-pointer mode, appended after plan CSS, and re-run after live source-sync iframe refreshes so comment anchors, selection boxes, mermaid rendering, images, and text wrapping stay aligned.

Target mobile mocks

These full-width mocks define the intended product shape, not final pixel-perfect styling. They prioritize annotation detail in the browser reviewer over compact gallery layout.

Product intent alignment

  • Reviewer job-to-be-done: advances “open a local plan, select the exact section/image/text, leave a comment” by making that flow usable on phones.
  • Golden path: opening a review URL on mobile should work without extra setup, desktop mode, pinch zoom, or chat-side screenshots.
  • Browser shell owns interactivity: the viewer adapts the sanitized render and shell controls; plan-authored scripts/forms remain unsupported.
  • Quality bar: browser comment interactions and rendered markers remain covered by e2e tests; no queue or source-sync semantics change.
  • Safe failure: if a plan contains genuinely wide content, the viewer contains it with a visible local scroll affordance instead of clipping or globally forcing tiny text.

Locked decisions

  1. Viewer owns mobile adaptation. Do not require authors to rewrite every plan; inject/readjust in the review shell/rendered iframe for mobile and coarse-pointer contexts.
  2. Preserve native scroll. Keep #review as the native mobile scroll container and keep #plan-touch-layer as the tap surface; do not reintroduce JS scroll emulation.
  3. Desktop stays stable. Existing desktop navigator/comments/sidebar behavior should not materially change except for shared bug fixes and reduced-motion/accessibility improvements.
  4. Comments are a tray on phones. The mobile comments panel should behave like an activity tray with filters/counts and jump-to-anchor behavior, not a permanent sidebar.
  5. Composer remains a bottom sheet. Keep the current mobile bottom-sheet position and add keyboard-safe controls plus selection/quote context.
  6. No lifecycle/API expansion. Comment queue, ack/resolve/release semantics, registration, and source-sync metadata remain unchanged.

Acceptance criteria

  1. At phone viewport widths, normal plan prose, headings, lists, figures, and mocks are readable without pinch-zooming and without page-level horizontal scroll.
  2. Tables, pre/code blocks, mermaid diagrams, and intentionally wide figures are contained in local horizontal scroll regions with an obvious visual affordance.
  3. The review shell chrome leaves most of the viewport for reading; desktop-only navigator controls are hidden or accessible through compact mobile controls.
  4. The comments tray opens and closes with a 44px minimum touch target, shows comment count/status context, and does not permanently obscure the selected plan content.
  5. A reviewer can tap a DOM/text/image/diagram target on mobile, see the selected region, open a bottom-sheet composer with selection context, type with the on-screen keyboard, submit, and see the new comment in the tray.
  6. Existing desktop review behavior, source-sync refresh behavior, marker rendering, lightbox, and queue-backed comments remain intact.
  7. Coarse-pointer tablets activate the mobile touch/overlay behavior even when their width exceeds the phone breakpoint.
  8. Automated e2e covers representative mobile readability cases and touch review flows, including rotation/resizing and a source-sync iframe refresh after mobile styles are applied.

BDD scenarios

BDD-1: Open and read on phone

Given a registered plan with prose, a table, a code block, an image, and a mermaid diagram, when a reviewer opens the review URL on a 390px-wide phone viewport, then the shell has no page-level horizontal overflow, normal prose is legible, and wide blocks are scrollable inside their own regions.

BDD-2: Comments tray supports triage

Given a plan has pending, claimed, acknowledged, and resolved comments, when the reviewer opens the mobile comments control, then the bottom tray shows counts/status filters and each row can jump to its anchored plan target without losing native scroll.

BDD-3: Mobile composer preserves context

Given a reviewer taps a text or DOM target, when the composer opens, then the selected region remains highlighted, the composer shows section/quote context, the text area is keyboard-safe, and submit creates exactly one comment.

BDD-4: Wide content is recoverable, not hidden

Given a table row or code line cannot wrap without destroying meaning, when it renders on mobile, then the content remains available through local horizontal scroll and a visible affordance indicates it can be swiped.

BDD-5: Source sync keeps mobile styles and anchors

Given the plan source refreshes while a phone reviewer is reading, when the iframe content is replaced safely, then the mobile readability stylesheet is re-applied and markers/selection boxes reflow to the new content height.

BDD-6: Desktop parity is preserved

Given a desktop reviewer opens the same plan, when they use the navigator, sidebar, comments, image lightbox, and action buttons, then those behaviors match the current desktop flow except for intentional shared accessibility improvements.

Verification strategy

  • Regression evidence: bun run test keeps CLI/API/render contracts stable.
  • Manual visual gate: open this plan and one historically dense plan on a phone-sized viewport and confirm mocks/prose/tables/comments/composer match the target shape.
  • Review gate: run scoped implementation review before final handoff because this touches browser shell layout, iframe styling, and comment creation UX.

Delivery order

P1 defines failing evidence. P2 fixes core readability. P3 makes mobile comments usable. P4 tightens annotation creation and marker stability. P5 documents behavior and runs final gates. Do not merge shell/chrome polish before the reader layer because readable content is the primary user outcome.

Non-goals

  • No rewrite of the plan authoring contract or requirement that plan authors use a new CSS framework.
  • No queue, ack, release, resolve, source-sync, or registration semantics changes.
  • No public authentication/security changes for the unauthenticated local MVP.
  • No replacement of iframe rendering with a full document editor.
  • No desktop redesign beyond preserving parity and avoiding shared regressions.
  • No plan-authored JavaScript, active embeds, or form interactivity support.
