Plan State Visual Regression Prevention

Investigate the missing plan-state pulldown and confusing archive icon, then harden the product against this class of visual and interaction regression.

Goal

Restore a clear, usable state-management experience for plan detail pages and add automated UI regression gates so future toolbar/status changes cannot silently remove key affordances or make a non-clickable status look like a broken button.

Decision Attention / Low-confidence Areas

  • Locked product decision: archived and deferred plans keep the existing Restore/Resume-first contract before board-column/status changes. The implementation must not auto-restore a plan merely because a reviewer attempts to change its board status.
  • Required recovery UX: inactive pages must make the path forward obvious: archived pages show a labelled Archived state, a primary Restore action, and helper copy saying status changes are available after restore; deferred pages do the same with Resume.
  • Regression source is high-confidence: commit 8cee24a intentionally hides #current-plan-status-control for non-active plans, and the screenshot plan plan_5hvCL70FK6wq is currently archived.

Why this plan exists

The current UI presents contradictory cues: the left navigator can show an archived current plan while its filter says Active, the top toolbar shows a round archive-looking glyph that is not clickable, and the board-column pulldown disappears without explaining why. That makes a correct internal lifecycle state feel like a broken visual regression.

Current Implementation Reality

  • The product has two state concepts: lifecycle (active, deferred, archived) and board status/column (backlog, in_progress, etc.).
  • Active planning documents can change board status from the top detail toolbar using #current-plan-status-control.
  • Deferred plans can be resumed or archived from the detail toolbar, but their board status selector is hidden.
  • Archived plans can be restored from the detail toolbar, but the archive-state indicator looks like an inactive archive button.
  • Current e2e coverage exercises many interactions, but it does not lock the visible toolbar contract as a user-facing state matrix.

Product Intent Alignment

This plan advances thoughts/specs/product_intent.md by making the plan index/detail state truthful and by ensuring browser UI, API, and tests describe the same lifecycle semantics. It follows the experience principles that routine workflows should not depend on tribal knowledge and every user-visible failure or unavailable action should explain the next safe action.

Locked Decisions

  • Keep the server-side invariant that only active planning documents can move board columns; inactive plans must use Restore/Resume before board-status changes.
  • Do not make non-clickable spans look like icon buttons. Status indicators must be visually and semantically distinct from actions.
  • Automated tests must cover the shipped browser surface, not just returned HTML strings.
  • Visual regression gates should target stable toolbar/navigation regions and pair screenshots with semantic clickability assertions to avoid flaky full-page snapshots.

Acceptance Criteria

  1. Active planning detail pages visibly expose a board-status selector and an archive action, both keyboard reachable and clickable, and they do not show or hit-test the restore action.
  2. Archived planning detail pages do not show a round/button-like archive icon; they show an unmistakable archive status pill, a restore action, and next-step guidance for changing status.
  3. Deferred planning detail pages show a deferred label, resume/archive actions, and next-step guidance for changing status after resume.
  4. When the current detail page is archived or deferred, navigator lifecycle filters default to that current plan lifecycle instead of showing the page under an unqualified Active filter.
  5. E2E tests cover the active/deferred/archived toolbar matrix with semantic assertions for roles, labels, clickability, pointer cursor, disabled state, and expected absence/presence of controls.
  6. The e2e fixture enforces a deterministic toolbar regression gate for active/deferred/archived states using DOM, computed-style, hit-target, and geometry assertions; clipped toolbar screenshots are captured only as debug artifacts on failure, not compared with image-diff baselines.
  7. Future UI-impacting plans in this repo must include current/target UI evidence and a shipped-surface browser verification step by adding explicit guidance to thoughts/plans/AGENTS.md.
  8. Regression coverage must prove both initial render and lifecycle transitions: active → deferred, deferred → active, active → archived, and archived → active restore, with toolbar and navigator assertions after each transition.

BDD Scenarios

Active plan can change board status

Given an active planning document with Kanban enabled, when the reviewer opens its detail page, then the toolbar exposes #current-plan-status-control, changing it persists through PUT /api/plans/:id/column, #restore-plan is not visible or hit-testable, and the navigator refreshes without losing the current page.

Archived plan is explanatory, not button-looking

Given an archived planning document, when the reviewer opens its detail page, then the toolbar shows an archive status pill and Restore action, no round/button-like archive icon, no standalone archive glyph, and guidance saying Restore is required before status changes.

Deferred plan guides recovery

Given a deferred planning document, when the reviewer opens its detail page, then the toolbar shows Deferred, Resume, and Archive controls, and status-change guidance points to Resume first.

Navigator state label stays truthful

Given the current page is archived or deferred and the request does not explicitly choose another lifecycle filter, when the detail page renders, then the left navigator selects that current page lifecycle filter so the plan is not presented as part of Active Plans.

Visual regression gate catches lost affordances

Given the e2e fixture creates one active, one deferred, and one archived planning document, when the toolbar semantic/geometry/clickability matrix runs, then removing the active status selector or making archived status look like an icon button fails before merge, with clipped toolbar screenshots available as failure artifacts for diagnosis.

Lifecycle transitions preserve the toolbar contract

Given an active plan detail page, when the fixture defers, resumes, archives, and restores plans through the real browser controls, then each resulting page state matches the toolbar matrix, the board-status selector appears only after active restore/resume, and the navigator lifecycle filter follows the current inactive lifecycle before returning to Active.
