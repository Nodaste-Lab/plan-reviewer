Implementation plan

Provide watcher instructions when agents register plans

Make the plan-reviewer registration response itself teach agents to start comment monitoring, with a known-good reference implementation in the API and CLI output instead of relying on a skill file being loaded.

Repo: plan-reviewerSurface: /api/plans/registerCLI: plan-review registerRisk: low-medium contract expansion

Product intent

Desired outcome

After any agent registers an HTML plan, the service response should make the next operational step unavoidable: start a monitor for browser comments immediately, using an included reference command that is known to work with the existing queue/watch contract.

Current gap

Registration already returns watchCommand, and external harness skills may document watcher patterns, but agents can miss or ignore those out-of-repo aids. The instruction is not a first-class response contract, and the CLI's success output presents the watch command as informational rather than a required follow-up.

Scope boundary

This plan does not make the server spawn a watcher process on the agent's machine. The server cannot safely control arbitrary agent harnesses. This plan's shipped user-visible outcome is that registration returns actionable instructions plus copy-paste/reference watcher commands. Reliable automatic monitoring is completed when harness adapters consume agentInstructions and auto-start the watcher; that adapter auto-start work is a named follow-up outside this server/CLI contract change.

URL and JSON behavior decisions

Decision: API commands are portable service-local templates, not fully resolved copy-paste commands. API consumers already know the registration service URL they called and should render watcher commands with --url <registration service URL> before execution so adapters monitor the same service that accepted registration. For flat commands, --url is appended to the watcher command. For durable tmux commands, --url must be inserted inside the quoted inner watcher command, not after the tmux wrapper. agentInstructions.reviewUrl remains the existing relative review path; the builder must not absolutize it because the service may not know its externally reachable URL. The CLI human output is the copy-paste surface and must render the resolved --url using resolveServiceUrl(). CLI --json must print the exact unwrapped registration data payload returned by requestJson(), not the HTTP { ok, data } envelope and not CLI-enriched commands; enriched JSON adapter shapes are deferred.

Decision: preferredCommand, durableCommand, and referenceImplementations are emitted from one helper/builder. The builder constructs commands from planId plus the canonical watcher flag set (--mode queue --format browser-comment --json) and does not parse or string-extend the legacy watchCommand; watchCommand is passed through unchanged for compatibility. The same module exposes a rendering helper that accepts an optional serviceUrl and places --url correctly in both flat and tmux-wrapped command forms, so the CLI formats human output without regenerating agentInstructions or mutating JSON output. Tests should validate the generated object and rendered commands so command examples cannot drift from the canonical watch flags.

Known-good watcher reference implementation

The commands in this section show rendered forms after CLI or adapter URL placement. The API/builder templates omit --url; rendered human output and adapters add it according to serviceUrlInstruction.

Pi background process pattern

When the registering agent has a background process tool, start the watcher as a managed long-running process and react to browser.comment.v1 lines. The pi harness label in referenceImplementations means the Pi harness background-process pattern; the list is extensible, and tests should assert required entries by tool/command semantics rather than treating the two sample entries as a closed enum.

plan-review watch <planId> \
  --mode queue \
  --format browser-comment \
  --json \
  --url <serviceUrl>

Durable shell pattern

When monitoring must survive the current agent turn, write browser-comment payloads to NDJSON from a detached tmux watcher.

mkdir -p ~/.plan-reviewer/watchers
tmux new-session -d -s plan-review-<planId> \
  'plan-review watch <planId> --mode queue --format browser-comment \
   --conversation-out ~/.plan-reviewer/watchers/<planId>.ndjson --json \
   --url <serviceUrl>'

Comment processing loop

The builder's agentInstructions.processingLoop array is authoritative. This prose is documentation-only and may summarize the same steps, but tests should assert the builder output rather than treating this HTML copy as a second contract.

  1. Receive a browser.comment.v1 payload from the watcher.
  2. Run plan-review queue claim <planId> --ids <commentId> --json for that event and read <claimId> from claimed[0].claim.id in CLI JSON, or data.claimed[0].claim.id in raw API JSON; use --one only as a fallback if a future event shape does not expose a comment ID.
  3. Read the plan and selected context, then make the smallest appropriate plan change.
  4. Run plan-review ack <commentId> --claim <claimId> --summary "..." --changed-files thoughts/plans/... --json.
  5. Run plan-review resolve <commentId> --note "Done" --json only after the reviewer-visible issue is complete.

BDD scenarios

Agent registers via CLI

Given an agent runs plan-review register, when registration succeeds, then stdout includes the plan URL, source sync state, and a required watcher command with --format browser-comment.

Agent registers via API

Given a harness adapter calls /api/plans/register, when it parses the JSON response, then it can read agentInstructions.preferredCommand, render it with --url using the registration service URL it already called, and start monitoring without consulting a skill file.

Reviewer comments after registration

Given the registering agent started the provided watcher, when a browser reviewer submits a comment, then the watcher emits a browser.comment.v1 payload and the agent can claim, process, acknowledge, and resolve through existing commands.

Adversarial: agent ignores human prose

Given an agent only consumes machine-readable registration output, when it registers a plan with --json, then the required watcher instruction is still present in agentInstructions with a stable type, required: true, service URL guidance, and a preferred command template.

Adversarial: registration fails

Given registration fails because the input is invalid or the service returns an error, when the API or CLI surfaces that failure, then it follows the existing error path and must not emit agentInstructions or a REQUIRED NEXT ACTION: watcher block.

Adversarial: copied command lacks service URL

Given the service is not running on the CLI default URL, when the CLI prints registration instructions, then every human copy-paste watcher command includes the resolved --url value so the monitor connects to the same service that accepted registration.

Adversarial: API adapter preserves registration service URL

Given a harness adapter registers through any service URL, when it starts agentInstructions.preferredCommand or renders a durable tmux watcher, then it places --url <registration service URL> according to agentInstructions.serviceUrlInstruction—appended for flat commands and inside the quoted inner watcher for tmux—so the watcher connects to the service that returned the plan ID.

Adversarial: watcher startup fails

Regression guard: this relies on existing watch fallback coverage in bun run test, not new fallback behavior in this plan. Given the agent starts the provided watcher but SSE or the network fails, when the command runs, then the existing plan-review watch polling fallback and saved watch state keep the watcher usable without losing already-seen sequence position.

Adversarial: duplicate registration or watcher

Regression guard: this relies on existing queue claim lifecycle coverage in bun run test, not new duplicate-watcher logic in this plan. Given an agent re-registers the same plan or starts the watcher more than once, when comments arrive, then the queue claim lifecycle remains the source of truth and only a holder of an active claim can acknowledge feedback.

Decisions and follow-up

Decision: CLI JSON is exact unwrapped registration payload

For this phase, plan-review register --json prints the exact unwrapped registration data payload returned by requestJson(), not the HTTP { ok, data } envelope. CLI-only --url enrichment belongs only in human stdout. If a future adapter needs enriched JSON, add a separate adapter-specific field in a follow-up plan.

Out-of-scope follow-up: register-time process lifecycle

A later phase may consider plan-review register --watch or --auto-watch, but this plan deliberately avoids changing process lifecycle semantics. The current plan only returns instructions and reference implementations.
