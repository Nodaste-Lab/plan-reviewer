Goal

Let operators and agents know when the installed plan-reviewer is behind the version that Homebrew can actually install, and show the exact safe command to update. The notification must distinguish normal stable installs, Homebrew --HEAD installs, development checkouts, and ambiguous builds.

Decision Attention / Low-confidence Areas

Core decision accepted: normal Homebrew users should be notified from stable formula availability, not arbitrary commits on main. Keep the release path as lightweight as possible while staying compatible with brew update: bump the package version, create and push a version tag, update Formula/plan-reviewer.rb to that tag tarball with the matching checksum, and push the formula change. A separate rich GitHub Release and packaged binary assets are optional follow-ups, not required for this slice. HEAD commit detection remains an advanced channel for users who explicitly installed with brew install --HEAD, and its update command must use brew upgrade --fetch-HEAD.

D1 — Release channel policy (resolved)

Decision: stable formula releases are the canonical update signal. Commit-based detection is a secondary HEAD-channel signal only.

Release process requirement: document the essential Homebrew-compatible release procedure in repo-visible docs such as README.md or a checked-in release note, then create or update a project-specific, user-local skill at ~/.agents/skills/plan-reviewer-release/SKILL.md that mirrors that repo-visible procedure for agents. The skill is intentionally not checked into this repository, but it is a convenience wrapper rather than the sole source of truth. Both docs and skill must cover preflight, version bump, version tag, formula URL/checksum update, push order, and install/upgrade smoke verification. They should treat rich GitHub Release creation as optional unless we later decide we need release notes or binary artifacts.

D2 — Outbound network checks (resolved)

Decision: enable a throttled automatic check against GitHub/Homebrew metadata by default, with a service-level opt-out visible in the browser configuration screen and backed by the user config file. Send no plan data; cache status; never block service startup if the check fails.

Config requirement: add an Update checks section to the browser configuration/settings screen linked from the existing top-bar gear. It must show the current automatic-check setting, last-check status/cache timestamp when available, a checkbox or toggle to disable automatic checks, and the manual plan-review update check command. Saving persists to ~/.config/plan-reviewer/config.json (for example updateChecks.enabled: false) without sending plan data upstream. Env/CLI overrides may exist for tests and ad hoc runs, but the visible config screen is the normal operator control.

D3 — Notification surfaces (resolved)

Decision: implement both a CLI command and a very unobtrusive browser indicator. The CLI gives agents copy-paste JSON and shell output; the browser gives human operators passive visibility.

Browser indicator requirement: when an update is available, show a small fixed-position green up-arrow control that does not participate in page layout and therefore does not move existing buttons, cards, columns, comments, or plan content. On the desktop review shell, the preferred spot is the lower-right viewport corner inside the currently sparse collapsed comments rail; if the comments sidebar is open or the mobile comments control would collide, keep the same fixed/no-layout-shift behavior and move to the nearest unobstructed corner. The icon must have accessible text/tooltip such as “plan-reviewer update available” and open a compact detail/popover with the exact update command. Ambiguous, unsupported, dev, or check_failed states must not use the green up-arrow because that icon means an upgrade is actually available; those states remain visible through CLI/API/config status details only.

D4 — Apply updates automatically? (resolved)

Decision: no auto-update and no update/apply flow in this slice. Detection is instruction-only: show the exact Homebrew command for the detected install channel, explain whether a service restart is needed, and leave execution to the operator.

Instruction requirement: CLI output, JSON nextAction, API status, and the browser up-arrow detail must provide copy-paste instructions. Stable installs should show brew update && brew upgrade Nodaste-Lab/plan-reviewer/plan-reviewer; HEAD installs should show brew update && brew upgrade --fetch-HEAD Nodaste-Lab/plan-reviewer/plan-reviewer. When the service appears Homebrew-managed, include a follow-up restart/verify step such as brew services restart plan-reviewer and a version or health check, but never run those commands automatically.

Solution narrative

Add one canonical update-status module that classifies the current install from local executable/package shape, fetches the latest installable target for that proven channel, compares current versus latest, and returns an actionable status object. Stable update checks use the Homebrew formula stable version as the installable source of truth; tags or GitHub releases that the formula does not point to must not trigger stable update notices. HEAD update checks use upstream branch metadata only for installs whose local Homebrew shape proves they are HEAD installs. Surface the same status object through:

  • plan-review update check [--json] for local CLI diagnostics.
  • GET /api/runtime/update for the running service and browser shell.
  • A browser configuration/settings screen control that lets operators disable or re-enable automatic checks while keeping manual CLI checks available.
  • A non-blocking fixed green up-arrow browser indicator on the index and review pages only when an update is available.

Add companion release-process deliverables: repo-visible release/update documentation that operators and maintainers can inspect, plus a project-specific user-local skill that is not committed to this repo and guides agents through the same minimum stable Homebrew-installable release path. The path should rely on GitHub's tag archive plus a formula update so brew update sees the new version through the tap.

Why this plan exists

The installed service is long-lived and currently gives no signal that a newer build exists. That creates hidden drift: agents may follow current docs while the daemon/CLI serving plans is older, lacks newer commands, or has stale queue/source-sync behavior. A truthful update notice reduces support burden and keeps operator-facing behavior aligned with the repository.

Product intent alignment

This plan cites and advances thoughts/specs/product_intent.md:

  • Operators need installable CLI/service behavior with actionable diagnostics: update status returns the exact safe Homebrew command and explains unsupported/ambiguous installs.
  • Repo maintainers need source-linked plans, stable metadata, and aligned tests: repo-visible release documentation is the source of truth for bumping versions, tagging source, updating the Homebrew formula, and verifying brew update/brew upgrade compatibility; the user-local release skill mirrors that path for agents without becoming hidden tribal knowledge.
  • HTTP API, CLI, browser UI, README guidance, and tests should describe the same lifecycle semantics: one update-status object drives every surface.
  • Routine recoverable failures should self-heal or retry inside the normal flow: network failures are cached as non-blocking check_failed status with next action; stale checks refresh on demand.
  • Every failure should explain the next safe action: ambiguous channel, dev checkout, missing GitHub metadata, and outdated install all produce agent-legible next actions.

Locked decisions

  • Do not overload /health. Health remains a liveness probe; update status belongs in a runtime/status endpoint and CLI command.
  • No automatic upgrade in this slice. Detection shows copy-paste instructions only; it does not stop services, run Homebrew, restart daemons, or mutate user data.
  • Automatic checks require visible opt-out. If the service/browser performs automatic metadata checks, the browser configuration/settings screen must expose an Update checks toggle backed by persisted user config. Manual plan-review update check remains available even when automatic checks are disabled.
  • Browser update notice must not move existing UI. The browser surface is a fixed green up-arrow indicator in a sparse corner, not an inline banner, navbar button, card, or grid item.
  • Do not claim stable updates from arbitrary commits, tags, or releases. A commit on main is an installable update only for the HEAD channel, and a stable tag/release is installable for normal users only after Formula/plan-reviewer.rb points to it.
  • Install channel must come from local install shape. Production code must not infer stable, head, or dev from package version, latest formula metadata, GitHub tags/releases, or env/test overrides. Resolve the running CLI/service executable and package root; classify Homebrew stable only for realistic Cellar/opt stable shapes such as .../Cellar/plan-reviewer/0.1.0/..., classify HEAD only for realistic Homebrew HEAD shapes such as .../Cellar/plan-reviewer/HEAD-.../..., and return unknown or unsupported_channel when the shape is absent, conflicting, or unparseable.
  • Essential release procedure is repo-visible. README or checked-in docs must document the minimal Homebrew release path; hidden user-local skills can mirror but not replace it.
  • Release automation skill stays user-local. The project-specific release skill belongs at ~/.agents/skills/plan-reviewer-release/SKILL.md or the user-approved global skill location, not in this repository.
  • No real network in tests. Tests use fake endpoints and deterministic metadata fixtures.

Acceptance criteria

  1. Current build is identifiable from local evidence: the CLI/service can report package version, build commit when available, formula name when installed through Homebrew, canonical executable/package path evidence, metadata source, and a clear dev/stable/head/unknown classification. Stable and HEAD channel classification must be derived from realistic Homebrew install shapes, not from package version, latest metadata, tags/releases, or production env overrides.
  2. Stable update truthfulness: stable installs compare against the latest stable version exposed by Formula/plan-reviewer.rb. If a newer tag or GitHub release exists but the formula still points at the installed version, the status does not say ordinary brew upgrade will install it.
  3. HEAD update truthfulness: HEAD installs compare against the configured upstream branch and return update-available only when the upstream branch is ahead of the installed commit; the next action includes brew upgrade --fetch-HEAD.
  4. Ambiguous builds and failed checks fail closed: dev checkouts, local commits not present on the tracked branch, and missing build metadata return unknown or unsupported_channel; unreachable metadata endpoints return retryable check_failed. All include specific next actions rather than false update claims, and none render the green update-available arrow.
  5. CLI/API/UI parity: plan-review update check --json, GET /api/runtime/update, and the browser indicator/config details use the same status vocabulary, next-action wording, and update instructions when an update is actually available.
  6. Non-blocking behavior: update checks are throttled/cached and never block service startup, plan registration, comment queue delivery, or source sync.
  7. No-layout-shift browser indicator: update-available browser UI is a fixed green up-arrow in a sparse corner, preferably the desktop review shell's lower-right collapsed-comments rail, with accessible text and a compact command detail; rendering it does not change navbar, board, review-shell, iframe, navigator, or comments layout measurements.
  8. Instruction-only upgrade guidance: update-available statuses include copy-paste Homebrew upgrade, optional service restart, and verification instructions, but no CLI, API, browser, or service path runs upgrade/restart commands automatically.
  9. Visible automatic-check opt-out: the browser configuration/settings screen can disable and re-enable automatic update checks, persists the setting to the shared user config path, and the service/browser respects the disabled state without removing manual plan-review update check.
  10. Docs match the chosen channel: README or checked-in docs explain stable formula releases as the normal channel, HEAD as an explicit advanced channel, local install-shape detection, the matching update commands for both, how to restart/verify after upgrading, how to disable automatic checks, and the minimal maintainer release procedure, including formula license alignment when the stable tarball license changes.
  11. Release skill exists outside the repo and mirrors docs: a project-specific user-local skill mirrors the repo-visible minimal Homebrew-compatible release process: preflight, version bump, tag creation, formula URL/checksum update, push, brew update, and Homebrew install/upgrade smoke test.

BDD scenarios

Stable install, no newer release

Given the installed build is stable 0.1.0 and the latest stable formula version is also 0.1.0, when the operator runs plan-review update check --json, then the status is up_to_date and no browser update indicator is shown.

Homebrew stable install shape proves stable channel

Given the running command is invoked through a Homebrew stable path such as .../opt/plan-reviewer/bin/plan-review that resolves to .../Cellar/plan-reviewer/0.1.0/bin/plan-review and the package root is under the matching libexec, when build identity is read, then the channel is stable, formula name is plan-reviewer, current version is 0.1.0, the path evidence is included in JSON diagnostics, and no network metadata is needed to prove the channel.

Homebrew HEAD install shape proves HEAD channel

Given the running command resolves to a Homebrew HEAD Cellar path such as .../Cellar/plan-reviewer/HEAD-abcdef0/bin/plan-review and the build commit is available, when build identity is read, then the channel is head, the commit is reported, and later update instructions use brew upgrade --fetch-HEAD. If the HEAD-shaped install lacks a usable commit, the checker returns unknown or unsupported_channel rather than comparing raw version strings.

Untrusted metadata cannot prove install channel

Given a local checkout, npm global install, or fixture supplies a package version, generated metadata, or latest formula response that says stable or head, but the canonical executable/package path does not match a supported Homebrew install shape, when update status is checked in production mode, then the status is unknown or unsupported_channel, no green update arrow appears, and env/test overrides are accepted only by explicit test seams.

Stable install, newer release available

Given the installed build is stable 0.1.0 and Formula/plan-reviewer.rb exposes stable version 0.1.1, when the checker runs, then it returns update_available, identifies 0.1.1, renders brew update && brew upgrade Nodaste-Lab/plan-reviewer/plan-reviewer, and provides service restart/verify instructions without running them.

Release docs and skill publish a stable Homebrew update

Given a maintainer follows the repo-visible release docs or invokes the user-local plan-reviewer release skill mirror for version 0.1.1, when the minimal procedure completes, then package.json is bumped, a v0.1.1 git tag exists on the remote, Formula/plan-reviewer.rb points at the tag tarball with the matching checksum, the formula change is pushed to the tap, and brew update && brew upgrade Nodaste-Lab/plan-reviewer/plan-reviewer can install the release.

Stable tag exists but formula is not bumped

Given a v0.1.1 tag or GitHub release exists but Formula/plan-reviewer.rb still exposes stable version 0.1.0, when a stable install checks for updates, then the status remains up_to_date for the stable channel or reports a non-upgradeable informational note, and it must not show the green update arrow or tell the operator that ordinary brew upgrade will install 0.1.1.

Stable install, newer main commit but no release

Given the installed build is stable and main has newer commits but the stable formula still points at the installed version, when update status is checked, then it must not claim ordinary Homebrew has a stable update; it may report an optional HEAD-channel note only if the chosen policy includes HEAD suggestions.

HEAD install behind upstream

Given the installed build is HEAD-abc1234 and upstream main is def5678 ahead of that commit, when update status is checked, then the status is update_available and the next action includes brew update && brew upgrade --fetch-HEAD Nodaste-Lab/plan-reviewer/plan-reviewer.

HEAD install not present on upstream branch

Given the installed commit is not reachable from upstream main, when update status is checked, then the status is unsupported_channel or unknown, the next action tells the operator to reinstall from the chosen Homebrew channel rather than claiming an update, and no green update-available arrow is shown.

Development checkout or missing build metadata

Given the operator runs from a local development checkout or the installed build lacks Homebrew channel metadata, when update status is checked, then the status is unknown or unsupported_channel, the next action explains how to run a manual check or reinstall through a supported Homebrew channel, and no browser green up-arrow is shown.

Metadata endpoint failure

Given GitHub or Homebrew metadata cannot be reached, when the service starts or the browser loads the index, then normal plan-reviewer workflows continue and the update status records a retryable check_failed result with the exact manual retry command.

Browser update indicator appears without layout shift

Given the service reports update_available and the desktop review shell has the comments sidebar closed, when the review page renders, then a small fixed green up-arrow appears in the lower-right sparse comments rail, has accessible text/tooltip, opens a compact command detail, and the navbar, iframe, navigator, and comments rail keep the same layout measurements they had before the indicator rendered.

Operator disables automatic update checks

Given automatic update checks are enabled by default, when the operator opens the browser configuration/settings screen, disables Update checks, and saves, then the setting is persisted in ~/.config/plan-reviewer/config.json, the service/browser stops scheduling automatic metadata fetches, the runtime update API reports automaticChecksEnabled: false, and plan-review update check remains available for manual checks.

Update notice gives instructions but does not apply them

Given an update is available for a Homebrew-managed service install, when the operator opens CLI output or the browser up-arrow detail, then it shows the channel-correct Homebrew upgrade command, restart guidance such as brew services restart plan-reviewer, and a verification step, and then no process is spawned and no upgrade/restart command is executed by plan-reviewer.
