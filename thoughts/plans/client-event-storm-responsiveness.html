Plan Reviewer Client Event Storm Responsiveness

Status: execution-ready

Created June 8, 2026. Revised after Codex and Claude plan-review feedback; both re-reviews returned PLAN_EXECUTION_READY. P1-P3 implementation and verification completed on June 8, 2026.

Goal

Stop a single plan-review browser client from becoming unresponsive when a plan has many comment events or when many comment lifecycle events arrive in a burst, while preserving live comment updates, source-sync refreshes, and agent queue behavior.

Why This Plan Exists

Human reviewers need an open plan tab to stay responsive while comments and plan updates accumulate. The reported symptom is client-specific degradation: one browser stops responding over time, another browser can still work, and reopening the affected browser temporarily restores behavior.

Authority and Inputs

  • User request: reproduce the client-specific responsiveness failure and propose a fix; investigate and plan only.
  • Repo guide: AGENTS.md, especially the browser-review and quality-gate requirements.
  • Product intent: thoughts/specs/product_intent.md, especially “Do not lose comments” and preserving a trustworthy browser review surface.
  • Code evidence: src/server/app.ts and src/storage/database.ts.
  • Reproduction evidence from temporary Playwright runs against isolated SQLite databases under /tmp.

Current Implementation Reality

  • The browser client calls loadMeta() for every comment lifecycle SSE event and once on page load.
  • loadMeta() performs a full GET /api/plans/:planId, parses all comments, redraws markers, and rewrites the entire comment sidebar.
  • The browser opens /api/plans/:planId/events?mode=all. The server replays up to 200 stored events on connection before streaming new events.
  • The plan detail endpoint calls store.listPlans({ includeArchived: true }) twice to derive counts and progress for one plan. That method scans all plans and reads plan HTML blobs to extract progress.
  • listComments() returns all comments for the plan and remaps anchor state against the latest rendered HTML on every full metadata load.

Reproduction Evidence

Stored Event Replay

Seeded one plan with 350 comments before opening the review page. On fresh page load, the tab issued 200 full metadata requests, with 199 concurrent /api/plans/:planId fetches. The rendered UI eventually showed 350 comment rows and anchors, but the request storm consumed the client connection budget while settling.

Burst While Open

Opened a healthy plan page, then created 120 comments through the API. The tab issued 122 full metadata requests, with 117 concurrent fetches. Request duration p50 was about 150 ms and p95 about 210 ms in the small synthetic dataset; larger real stores will amplify this because each request asks the server for global plan-derived metadata and all comments.

Root Cause Hypothesis

The client is not dead; it is self-saturating. Historical SSE replay and bursty live events trigger many uncoalesced full-state reloads. Because each reload performs an O(all comments) sidebar rewrite and anchor remap, the affected tab can saturate its own rendering work and network request queue. Another browser process can appear healthy because it has a separate page/runtime budget, and reopening the affected browser clears the tab-local backlog until event volume builds again.

Product Intent Alignment

This plan advances thoughts/specs/product_intent.md by keeping browser comments visible and reliable without requiring reviewers to reopen tabs as a manual recovery step. The queue-backed agent path remains the correctness-critical comment delivery mechanism; the browser SSE stream is treated as a UI freshness signal that must be bounded and recoverable.

Locked Decisions

  • Do not change queue-backed agent delivery semantics.
  • Do not remove live browser updates; coalesce and bound them.
  • Keep the browser’s initial state source as GET /api/plans/:planId, then subscribe only to events newer than that snapshot.
  • Optimize the plan detail endpoint for the requested plan instead of deriving single-plan counts and progress through the global plan index path.

Acceptance Criteria

  1. A fresh review page with 350 historical comment events renders the current comments from the initial snapshot with no more than three total GET /api/plans/:planId calls and no more than one in flight at any time.
  2. A burst of 120 comment events while a page is open coalesces into no more than four additional full metadata refreshes, with no more than one full metadata request in flight per tab.
  3. Comment creation, claim, ack, resolve, release, plan version registration, source sync, and sync failure still refresh the browser to the latest truthful state, including exact expected comment counts and status transitions after coalescing.
  4. The plan detail endpoint computes counts and progress for the target plan without scanning and parsing every registered plan, and those target-plan values stay identical to the index/global list values for the same plan.
  5. Existing API, CLI, queue listener, and e2e behavior remain aligned.

BDD Scenarios

Historical Events on Page Open

Given a plan has 350 stored comment events, when a reviewer opens /p/:planId, then the page renders all 350 comments from the initial metadata snapshot, opens the browser SSE stream from a post-snapshot event sequence, and stays within the AC1 request and concurrency ceilings.

Live Comment Burst

Given a reviewer has a plan page open, when 120 comment events arrive rapidly, then the client schedules at most one active metadata load and one queued follow-up refresh, stays within the AC2 ceilings, and the final sidebar contains all 120 new comments.

Trailing Refresh After In-Flight Event

Given a metadata refresh is already in flight, when the newest comment or lifecycle status event arrives before that refresh completes, then the client records a trailing refresh and the final UI reflects the last event rather than dropping it.

Source Sync Refresh

Given a plan source sync event arrives while no comment draft is open, when the event is processed, then the iframe updates to the latest render without losing marker state. If a draft is open, the refresh remains deferred until the draft is submitted or cancelled.

Agent Queue Unchanged

Given an agent uses plan-review agent next, when browser comments are created and claimed, then queue delivery remains at-least-once and independent from browser UI event coalescing.

Default Event Replay Unchanged

Given a CLI or watch consumer connects to the existing event endpoints without a browser-only post-snapshot cursor, when stored queue events exist, then default replay and poll behavior remain compatible with current agent and watch flows.

Index and Detail Parity

Given a plan has mixed pending, claimed, acknowledged, and resolved comments plus phase progress markers, when the index and detail APIs are read, then both surfaces report matching counts and progress for the same plan.

Add a trailing-refresh regression where the last event arrives during an in-flight load and must still appear in the final UI.

P2: Browser Event Coalescing and Replay Boundaries

End State

The review page uses initial metadata as the current snapshot, subscribes only to newer browser events, and coalesces event-triggered metadata refreshes.

Tests first

Use the P1 failing e2e tests as the RED signal.

Expected files

src/server/app.ts and any contract tests needed for event endpoint query behavior.

Work

  • Add a latest event sequence to the plan metadata response or a lightweight event cursor endpoint.
  • Have the browser pass that initial sequence as an SSE query parameter, because EventSource cannot set Last-Event-ID on first connect.
  • On reconnect, treat a present Last-Event-ID header as newer authority than the initial query cursor so the browser does not replay events already seen since the first snapshot.
  • Allow the browser SSE endpoint to start after the supplied sequence, while preserving existing default replay behavior for CLI/watch/poll compatibility when the parameter is absent.
  • Replace direct event-handler calls to loadMeta() with a scheduler that keeps at most one request active and one merged follow-up pending.
  • Merge refresh options conservatively so source-sync refreshes still force iframe updates and draft-safe deferral still works.

Verify

bun run test
bun run test:e2e

Verification Strategy

Use tests as evidence for the failure mode and the fix. The most important new evidence is a browser-network assertion: historical or burst comment events must stay within the AC1/AC2 request ceilings and max one in-flight metadata request. Final verification should include the full repo gate plus e2e and queue fixture smoke because this touches browser, API, and agent queue-adjacent surfaces. Record render-settle timing in the new e2e evidence so large-comment DOM cost can be revisited only if bounded fetches still leave visible jank.

Delivery Order

  1. P1 proves the failure with tests.
  2. P2 makes the browser resilient to replay and bursts.
  3. P3 reduces server-side amplification and protects larger plan stores.

Non-Goals

  • No authentication or trusted-network behavior changes.
  • No rewrite of the comment sidebar into a virtualized UI unless bounded fetches still leave unacceptable rendering cost.
  • No change to agent queue claim, ack, release, or resolve semantics.
  • No compatibility break for current CLI watch and poll flows.
