Implementation plan

Configuration panel and review defaults

Add a local browser configuration panel for plan-reviewer, move board-column configuration into it, and make review-shell side panels, action skill names, and Kanban availability configurable with safe defaults.

Repo: plan-reviewer Surface: browser shell, index, local service config Linear issue: none supplied; direct user request Status: execution-ready Execution ready: true

Status

Execution-ready. Browser feedback is resolved, product-intent alignment has been checked, and independent GPT/GLM readiness reviewers cleared the plan after revisions. Product code changes can begin through the scoped execution workflow.

Goal

Operators should have one obvious configuration surface for local plan-reviewer behavior:

  • Choose whether the left plan navigator and right comments panel open by default when entering a plan. The new default is hidden/collapsed for both.
  • Configure the skill names used by Request execution-ready review and Build Plan, while keeping generated comments injection-safe.
  • Enable or disable the Kanban organizer without deleting board-column definitions or plan assignments.
  • Manage the existing Kanban column labels/visibility in the same configuration panel instead of a separate /columns page.

Decision Status

  • Resolved through browser feedback: configuration is an icon-only gear with tooltip/accessible text, visible on all topbar screens; in plan view it remains right-anchored after Archive/Restore and before Comments.
  • Resolved panel direction: Configuration is a full-page settings surface with sections for review-shell defaults, action skill routing, Kanban enablement, and board columns.
  • Implementation gate: product code changes should proceed only through the scoped execution workflow for this execution-ready plan.
  • Resolved from request: the side-panel defaults are hidden/collapsed for new plan entries. Kanban remains enabled by default to preserve existing installs, with an explicit opt-out toggle.

Solution narrative

Create a service-owned UI configuration model stored in the plan-reviewer SQLite database, exposed through GET/PUT /api/configuration, and edited at a new /configuration page. The stored values include review-shell defaults, action skill-routing names, and Kanban enablement. This keeps runtime UI preferences live without writing ~/.config/plan-reviewer/config.json or requiring service restarts.

The configuration page becomes the single local settings panel. The existing Kanban column editor moves into a Kanban section on that page. The old /columns route remains as a compatibility redirect or thin alias to /configuration#kanban-columns.

Review-shell rendering reads the saved defaults before emitting the page. If showPlanNavigatorByDefault is false, the body starts with the left navigator collapsed. If showCommentsByDefault is false, the comments column starts at zero width; the toolbar comments button still shows the pending count. The reviewer can open either panel at any time, and the two toggles remain independent.

Action buttons continue creating queue-backed comments, but their body template uses validated skill-name tokens from the SQLite-backed configuration record and a single-line inert registered plan path. Operators maintain skill names through the Configuration panel/API, not by editing prompt templates, environment variables, or the user config file:

Use the <configured-skill-name> skill for this plan.

Product intent alignment

This plan cites and advances thoughts/specs/product_intent.md.

  • Golden path: one visible icon-only Configuration gear replaces hidden knowledge of /columns and makes local defaults discoverable without widening toolbars.
  • Safe defaults: side panels are hidden by default per request but remain obvious through toolbar controls; Kanban stays enabled by default to avoid surprising existing users.
  • Truthful status: Kanban disabled state is shown in navigation, API errors, and docs rather than silently hiding data.
  • Agent safety: configurable skill names are validated tokens and action-comment plan paths are single-line/inert before insertion into a fixed body template, so browser configuration or malformed registration metadata cannot inject arbitrary agent instructions.
  • Recovery: disabling Kanban is reversible and preserves stored columns and assignments; failed saves show actionable UI/API errors.

Locked decisions

  1. SQLite-backed browser configuration. Store live UI settings in the service database, not restart-only user JSON.
  2. Side-panel defaults hidden. New defaults are showPlanNavigatorByDefault: false and showCommentsByDefault: false for desktop review pages.
  3. Mobile unchanged. Mobile/coarse-pointer layouts keep the current hidden left nav and bottom comments sheet behavior; desktop defaults are the first slice.
  4. Skill names are tokens. Values must match a strict skill-name regex and are rendered only inside Use the ... skill for this plan.
  5. Action-comment plan paths are single-line and inert. Registered plan paths used by Request execution-ready review and Build Plan must reject newline/control characters at registration or fail closed before action-comment creation; legacy unsafe rows must not produce queue comments with extra agent-visible lines.
  6. Skill routing is database-maintained. executionReadySkillName and buildPlanSkillName are stored with the rest of browser UI configuration in SQLite and maintained through the Configuration panel/API.
  7. Unknown configuration keys fail closed. PUT /api/configuration rejects unknown keys with an actionable validation error and preserves the previously saved configuration.
  8. Default skills preserve current behavior. Defaults are plan-reviewer-execution-ready and plan-reviewer-build.
  9. Kanban remains enabled by default. Existing installs continue opening the board unless the operator disables it.
  10. Disable is reversible. Disabling Kanban hides board UI and movement controls, rejects plan movement via PUT /api/plans/:planId/column and the CLI column set command, but preserves columns and plan assignments. Board-column configuration endpoints and CLI commands remain available so operators can prepare or repair columns before re-enabling Kanban.
  11. Columns move into Configuration. /columns remains as an alias/redirect to avoid breaking existing links during the transition.
  12. Configuration entry is icon-only. Every topbar surface uses a compact gear button with title/aria-label “Configuration”; no text label is shown in the toolbar. In the plan-view toolbar specifically, preserve the current right-anchored #plan-navbar-actions layout and place the gear to the right of Archive/Restore and to the left of the comments collapse/open button.

Acceptance criteria

  1. The service exposes GET /api/configuration with defaults for side-panel visibility, action skill names, and Kanban enablement, plus PUT /api/configuration for validated updates.
  2. A /configuration page is reachable from every topbar surface via an icon-only gear with title/aria-label text of “Configuration”, and contains Review shell defaults, Action skill routing, Kanban, and Board columns sections.
  3. Existing board-column editing behavior is available from the Configuration panel; /columns remains compatible by redirecting or rendering the same panel section.
  4. With default configuration, desktop plan pages start with left plan navigator hidden and comments panel hidden, while toolbar buttons can open each panel independently.
  5. When configuration sets either side panel to show by default, newly loaded plan pages start with that specific panel open without forcing the other panel open.
  6. Action-button request comments use configured skill names and exact single-line-safe plan paths in the fixed template.
  7. Invalid skill names and unsafe action-comment plan paths are rejected with actionable validation errors and cannot inject extra lines or arbitrary agent instructions.
  8. When Kanban is enabled, the index, board columns, drag/drop, Status filters, and column APIs preserve existing behavior.
  9. When Kanban is disabled, the index defaults to All documents, Kanban navigation/drag-drop/status filters are hidden, browser/API/CLI column assignment attempts fail with feature_disabled, board-column configuration remains available, and existing column data remains intact.
  10. README, API/CLI docs where applicable, contract tests, and e2e tests describe and verify the same configuration behavior.

BDD scenarios

Configuration gear is available everywhere

Given a reviewer is on Kanban, All documents, Archived, Deferred, Configuration, or a plan review page, when they inspect the top action row, then an icon-only gear with accessible text and tooltip “Configuration” is present alongside the other screen-specific action buttons; on plan-view pages the action buttons remain anchored to the right edge of the window and the gear sits to the right of Archive/Restore and to the left of the comments collapse/open button.

Default plan entry hides side panels

Given a fresh service database with default configuration, when a reviewer opens /p/:planId on desktop, then the rendered plan occupies the side-panel space, the left navigator and comments panel are not shown, and the toolbar has controls to open each panel.

Configured side panel opens by default

Given showPlanNavigatorByDefault is true and showCommentsByDefault is false, when the reviewer opens a plan, then the left navigator starts open and the comments panel remains hidden.

Configured skills route action comments

Given the execution-ready skill is configured as custom-readiness-skill and the registered plan path is single-line-safe, when the reviewer clicks Request execution-ready review, then the pending queue comment body is Use the custom-readiness-skill skill for this plan. followed by the exact registered plan path.

Invalid action routing inputs fail closed

Given a user tries to save a skill name containing a newline or spaces, when they submit the configuration, then the save is rejected, current settings remain unchanged, and the UI/API explains the accepted skill-name format.

Given a registered plan row has a plan path containing a newline or other control character, when a reviewer requests execution-ready review or Build Plan, then the action fails with an actionable validation error and no queue comment is created from the unsafe path.

Kanban disable is reversible

Given plans have assigned board columns, when Kanban is disabled, then the board and drag/drop are unavailable, All documents is the default index view, and re-enabling Kanban restores the prior columns and assignments.

Column configuration lives in Configuration

Given a user wants to rename or hide a board column, when they open Configuration and save the Board columns section, then the same migration, visibility, and plan-count warnings from the existing column editor apply.

Delivery order

  1. P1 locks the data contract and validation first so UI and behavior phases depend on a tested source of truth.
  2. P2 adds the visible configuration panel and moves the columns editor while preserving existing behavior.
  3. P3 applies configuration to the review shell, action comments, and Kanban behavior.
  4. P4 aligns docs and runs full verification/review.

Non-goals

  • Authentication or role-based access for the configuration panel. The MVP service remains trusted-network local-only.
  • Per-user, per-browser, per-repo, or per-plan configuration scopes.
  • A mobile-specific plan navigator drawer.
  • Editing arbitrary prompt bodies for action buttons; only safe skill-name tokens are configurable.
  • Deleting Kanban columns or clearing plan assignments when Kanban is disabled.
  • Replacing the existing queue/comment lifecycle or delivery worker behavior.
