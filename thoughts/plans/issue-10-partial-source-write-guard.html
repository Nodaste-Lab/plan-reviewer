Issue 10 Partial Source Write Guard Plan

Status: implementation complete; scoped Codex and Claude reviews passed

Goal

Prevent live-linked plan review pages from silently publishing and displaying intermediate, partially written source HTML as the latest plan version.

Why this plan exists

GitHub issue #10 documents a reliable reproduction where the source watcher renders the prefix of a plan while an agent is mid-write. The browser shell looks healthy, comments still show, and no sync warning appears, but later plan sections are absent.

Authority and inputs

  • Issue source of truth: GitHub issue #10.
  • Triage evidence from live browser reproduction: fresh registration/comment/claim paths loaded fully; non-atomic partial source write reproduced missing middle/bottom plan content.
  • Current source-sync implementation: src/server/sourceSync.ts.
  • Current render and store contracts: src/render/render.ts, src/storage/database.ts, src/server/app.ts.
  • Regression test home: src/__tests__/contracts.test.ts plus browser fixture coverage in src/test-fixtures/e2e-run.ts only if contract coverage is insufficient.

Current implementation reality

Watcher behavior

SourceSyncService.register() creates chokidar watchers with awaitWriteFinish: false. Changes schedule syncNow() after a fixed 500ms debounce.

Rendering behavior

performSync() reads the source once, renders those bytes, and commits a new filesystem-watch version when render succeeds. It does not prove the write is complete.

Invalid source behavior

renderPlan() rejects parse errors, and source read failures keep the last good render. Missing end tags can still parse/render enough to become a successful partial version.

UI behavior

The browser refreshes the iframe on plan.version.synced. If a partial source is committed as a valid version, the UI truthfully shows that bad version and has no reason to warn.

Product intent alignment

  • Default workflow: users and agents keep editing ordinary live-linked HTML plan files; the service absorbs transient write states.
  • Safe default: never replace the latest reviewable version with source bytes that look like an incomplete write.
  • Self-healing: when the source becomes stable and complete, automatically sync and clear any warning without manual re-registration.
  • Fail-closed boundary: if the source remains incomplete or unreadable beyond a bounded retry window, keep serving the last good version and expose an actionable sync warning.
  • Operator/agent guidance: error metadata should explain that the service observed an incomplete source write, kept the last good render, and will retry on the next stable change.

Locked decisions

  1. Last good remains authoritative during unsafe sync. Do not publish a new version until the source passes stability/completeness checks.
  2. Guard filesystem sync, not manual snapshot semantics. Issue #10 is about live-linked source watchers and startup rehydration for filesystem plans.
  3. Avoid rejecting intentional large deletions by size alone. Size deltas may inform diagnostics, but should not be the sole validity rule.
  4. Live-linked plan source is expected to be a complete HTML document. The primary mandatory guard must inspect the raw source bytes, not parse5's re-serialized output, because parse5 can auto-close truncated documents. Treat the source as incomplete unless its final significant raw tokens close the document structure, e.g. </body> followed only by optional whitespace/comments and </html> followed only by optional whitespace. Do not use broad substring checks; embedded examples containing literal or escaped close-tag text must not satisfy completeness.
  5. Image-only changes must still sync. The guard must not break existing relative image watch tests.
  6. Dynamic browser refresh remains a product contract. The fix must not degrade live-linked plans into manual refresh or snapshot-only behavior; complete source changes should still propagate to already-open review pages automatically.
  7. Structural completeness is the primary guard. Stat stability and chokidar write-finish behavior are supplementary timing protections only; they cannot catch a quiescent truncated file after a service restart. The same raw-source completeness guard must run through the existing rehydrateFromStore() → syncNow('startup') → performSync() path without adding a divergent startup branch.

Acceptance criteria

  • AC1: A filesystem-watch sync triggered while the source file contains only a valid-looking prefix does not create a new latest version and does not replace the rendered iframe content.
  • AC2: The plan metadata reports a truthful non-synced state with actionable detail when an incomplete source write is deferred or rejected.
  • AC3: Once the complete source file is restored or rewritten atomically, source sync creates the expected latest version and clears the warning automatically.
  • AC4: Source deletion/unreadable-source recovery and missing/changed relative image sync behavior continue to pass existing tests.
  • AC5: Service restart while a source file is incomplete does not promote the incomplete source during startup rehydration.
  • AC6: Fresh registration, browser comment creation, and claimed-comment state remain unaffected by the guard.
  • AC7: Adversarial negative cases are covered: valid-looking prefixes, prefixes containing embedded close-tag text before the truncation point, parse-invalid fragments, rapid partial-to-full write flaps, service restart with partial source, intentional complete large-to-small rewrites, and asset-only changes all produce the correct last-good, warning, or sync behavior without silent partial publication.
  • AC8: Already-open browser review pages dynamically refresh after complete source changes and asset-only changes, while incomplete writes never trigger a visible partial iframe refresh.

BDD scenarios

BDD1: watcher sees partial write

Given a live-linked plan has a last good render containing top, middle, and bottom sentinels, when the watched source temporarily contains only the top prefix, then the latest render still contains the last good middle/bottom sentinels and the plan status says the new source update was deferred or failed as incomplete.

BDD2: complete source recovers automatically

Given an incomplete source update was rejected, when the complete HTML source is written, then the service syncs the new content, emits a plan version sync event, and removes the warning from API/UI metadata.

BDD3: restart with incomplete source

Given a filesystem plan exists in the database with a last good render, when the service starts and the source file is currently incomplete, then startup rehydration does not promote the incomplete bytes and the plan remains reviewable from the cached last good render.

BDD4: intentional complete small plan remains valid

Given a user intentionally replaces a large plan with a much smaller but complete HTML document, when source sync runs, then the smaller complete document is accepted despite the size decrease.

BDD5: relative asset changes still sync

Given the HTML source is unchanged and a watched relative image changes, when source sync runs, then the rendered asset hash updates as it does today.

BDD6: parse-invalid fragment keeps last good render

Given a live-linked plan has a last good render, when the source temporarily contains parse-invalid or unsafe HTML, then the service does not publish a new version, records actionable sync failure metadata, and keeps serving the last good render.

BDD7: embedded close-tag text does not bypass completeness

Given a live-linked plan contains an earlier code example or prose with literal or escaped </body>/</html> text, when a partial source prefix is cut after that example but before the real document ending, then the raw-source completeness guard rejects it and keeps the last good render.

BDD8: quiescent partial source is rejected on startup

Given a source file is no longer being written but remains truncated, when service startup rehydrates filesystem plans, then timing/stability checks alone are not considered sufficient and the structural completeness guard prevents publishing the partial source.

BDD9: rapid partial-to-full write flap does not flash partial content

Given an agent writes a partial prefix and shortly after writes the complete document, when browser pages receive sync events, then no partial version is emitted and the final complete version is the only new render shown.

BDD10: repeated incomplete writes remain bounded and recoverable

Given repeated incomplete writes occur over several watcher cycles, when source sync retries or defers them, then the service keeps the last good render, keeps status truthful, avoids unbounded listener/timer churn, and recovers when a complete document appears.

BDD11: open browser refreshes dynamically for complete changes only

Given a review page is already open, when a complete plan edit or watched asset edit is synced, then the client receives the sync event and reloads the iframe to the new complete version; when an incomplete source write is rejected, then the client shows truthful sync status without replacing the iframe with partial content.
