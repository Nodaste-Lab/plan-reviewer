Fix bump scroll behavior

Plan for the regression where changing plan scroll direction first feels like a pull/bump and only a later gesture scrolls normally.

Status: execution-ready Execution ready: true Linear issue: none; direct user report Surface: review shell mobile/coarse-pointer scrolling Created: 2026-06-24

Status

This plan has cleared product-intent, GPT, and GLM execution-readiness gates and is ready for implementation. It should be registered with --execution-ready true before phase execution starts.

Goal

Make the rendered plan area scroll immediately on the first input after a direction change, while preserving the recent navbar isolation model: the navbar stays isolated, #review remains the native mobile/coarse-pointer scroll container, the iframe does not own scroll, and the transparent touch layer still supports taps for comments and in-plan links.

Decision Attention / Low-confidence Areas

No product decision is required. The intended behavior is unambiguous: the plan should scroll on the first gesture in either direction.

Evidence limitation: headless Chromium wheel and synthetic scroll gestures move the correct scroll owner, but the raw trusted CDP touch sequence against the live service did not scroll the touch layer at all. That makes the automated regression a root-cause guard for scroll-blocking touch listeners plus a direction-change gesture check, not a perfect simulation of every trackpad/iOS rubber-band physics path.

Solution narrative

Keep the native-scroll architecture from the navbar isolation change, but remove the browser's reasons to treat the plan touch surface as scroll-blocking. The implementation should make touch observation listeners on the plan scroll path passive, add vertical overscroll containment to the mobile #review scroller, and add regression coverage that proves a first reverse-direction gesture changes #review.scrollTop without moving the iframe or opening the composer.

The fix must not reintroduce JavaScript scroll emulation. Prior tests already protect against manual scrollBy behavior because it broke momentum scrolling.

Why this plan exists

Recent scroll ownership work isolated the sticky navbar and moved mobile/coarse-pointer plan scrolling to #review, with a transparent #plan-touch-layer on top of the iframe for taps. The user now observes that changing scroll direction can feel like a pull/bump before scrolling works. This is a high-friction review-shell regression: reviewers spend most of their time reading and scrolling plans, and the scroll surface must feel native and predictable.

  • Git history: commit 115fc8d (“Fix plan review scroll ownership”) introduced the current native #review mobile scroll ownership and related tests.

Current implementation reality

  • src/server/app.ts renders #plan-navbar sticky above #app. On mobile/coarse pointers, body is overflow-hidden, #review has overflow-y:auto and -webkit-overflow-scrolling:touch, the iframe is full content height with pointer-events:none, and #plan-touch-layer is the top touch target with touch-action:pan-y.
  • The touch-layer, frame, and iframe-document touch listeners are registered as capture listeners without explicit passive:true. They do not intentionally call preventDefault() for scrolling, but their non-passive registration can still put the browser on the scroll-blocking path.
  • The mobile #review scroller does not currently set vertical overscroll-behavior, so boundary gestures can escape to the page/viewport instead of staying contained to the plan scroll surface.
  • Existing tests assert the broad architecture: #review is scrollable, the iframe internal scroll stays at 0, the touch layer is on top, wheel events are not canceled, and old manual scroll emulation stays absent. They do not assert listener passivity or the first reverse-direction scroll behavior.

Reproduction evidence gathered before writing this plan

  • A live-service diagnostic plan with long content showed the page is scrollable and that Chromium wheel input over the plan moves the correct owner (#review on mobile/coarse layout, window on desktop) while keeping iframe scrollY at 0.
  • Input.synthesizeScrollGesture over the touch layer moved #review in both directions, confirming layout and sizing are not the blocker.
  • A raw trusted CDP touch drag over the live #plan-touch-layer left #review.scrollTop at 0 after the first drag and after repeated reverse drags, which points at input handoff/scroll-blocking listener behavior rather than missing content height.

Product intent alignment

This plan cites thoughts/specs/product_intent.md and advances these desired outcomes and principles:

  • Simplest reviewer workflow: reviewers can open a plan, read it, scroll it, and comment without fighting the shell.
  • Browser comment interactions covered by e2e: the fix adds targeted coverage around the same rendered-plan/touch layer used for commenting.
  • Safe rendered output and source of truth: no plan-authored scripts or iframe behavior changes are introduced; the browser shell remains the owner of review interactivity.
  • Minimal hidden state: scroll behavior remains native browser state, not a custom JS emulation layer that agents/operators must understand.

UI impact: yes — this changes interaction behavior of the review shell's rendered plan area. Existing evidence is the current mobile/coarse-pointer e2e scroll block and live diagnostic reproduction. Target evidence is first-gesture direction-change scrolling with preserved comment/link tap behavior.

Locked decisions

  • Keep native scrolling. Do not restore manual touch or wheel scrollBy emulation.
  • Keep current scroll owners. Desktop scroll remains document/window based; mobile/coarse-pointer scroll remains #review; iframe internal scroll must stay at 0.
  • Keep the overlay tap surface. #plan-touch-layer remains the top mobile/coarse touch target so iOS Safari can tap/comment reliably.
  • Touch observers on the scroll path are passive. Touch handlers that only observe movement/taps must not block browser scroll negotiation.
  • Scope is review-shell scrolling only. No navigator redesign, comment queue changes, storage changes, or source-sync changes are included.

Acceptance criteria

  1. First reverse scroll works: on mobile/coarse-pointer review shell, after the plan has scrolled in one direction, the first gesture in the opposite direction changes #review.scrollTop immediately; a second gesture is not required.
  2. Correct scroll owner: direction-change gestures over rendered plan content move #review on mobile/coarse pointers and do not move iframe.contentWindow.scrollY or the outer page.
  3. No scroll-blocking touch observers: touchstart and touchmove listeners on the plan touch path are explicitly passive where they do not need to cancel browser defaults.
  4. Boundary pull is contained: vertical overscroll from the plan reading surface is contained to the plan scroller instead of escaping into a misleading page/viewport pull where supported by the browser.
  5. Comment and link taps still work: mobile/coarse taps on plain plan content still open the composer, in-plan fragment links still navigate without opening the composer, and adjacent non-link taps remain commentable.
  6. Desktop and iPad-style wheel behavior preserved: wheel/trackpad input remains native, uncanceled, and routed to the existing correct scroll owner.

BDD scenarios

BDD-1 — First upward reversal scrolls

Given a mobile/coarse-pointer review shell with a long rendered plan and #review.scrollTop greater than zero, when the reviewer performs the first upward/reverse gesture over the plan touch layer, then #review.scrollTop decreases during that gesture, iframe.contentWindow.scrollY remains 0, the outer page does not scroll, and the comment composer stays hidden.

BDD-2 — First downward reversal scrolls

Given a mobile/coarse-pointer review shell after an upward scroll, when the reviewer performs the first downward/reverse gesture over the plan touch layer, then #review.scrollTop increases immediately without needing a second gesture and without moving iframe internal scroll.

BDD-3 — Touch listeners are non-blocking

Given the review shell loads on a mobile/coarse-pointer context, when the client registers touch listeners on the touch layer/frame/document scroll path, then touchstart and touchmove listeners that only observe scroll/tap state are registered with passive:true.

BDD-4 — Taps remain reviewer actions

Given the rendered plan contains a fragment link and adjacent plain text, when the reviewer taps the link, then the fragment navigation scrolls #review to the target and the composer stays hidden; when the reviewer taps adjacent non-link text, then the composer opens on that element.

BDD-5 — Wheel remains native

Given a wide coarse-pointer/tablet context, when wheel input occurs over the rendered plan, then the wheel event is not canceled, #review scrolls, and the iframe internal scroll remains 0.

Phase P2 — Fix touch scroll handoff and containment

End State

The plan touch layer remains commentable and link-aware, but it no longer makes the browser treat the plan reading surface as scroll-blocking. First reverse-direction gestures scroll immediately, and boundary pull behavior is contained where the browser supports it.

Tests first

Use the failing P1 tests as the RED contract. Do not alter them except to correct test bugs discovered from product evidence.

Expected files

  • src/server/app.ts

Work

  • Add a small shared listener options constant inside the review-shell client script, such as const passiveTouchCapture = { capture: true, passive: true };, and use it for touchstart/touchmove observers on the scroll path that never need preventDefault().
  • Update planTouchLayer, frame, and iframe-document touchstart/touchmove listener registrations as appropriate. Also passivate any scroll-path touchstart observers that only dismiss transient UI, such as archive-toast dismiss handlers, when the P1 instrumentation flags them. Keep click and pointer handlers unchanged unless evidence shows they are part of the scroll-blocking path.
  • Do not rely on preventDefault() in passive handlers. Link taps from the overlay already use manual navigation because the overlay, not the anchor, is the native event target; composer click suppression should continue to use suppressSyntheticClickUntil.
  • Add overscroll-behavior-y: contain to the mobile/coarse-pointer #review rule so plan-boundary gestures do not escape into a page-level pull where supported.
  • Preserve the existing CSS contract: #review remains overflow-y:auto, iframe remains pointer-events:none in mobile/coarse layout, and #plan-touch-layer remains touch-action:pan-y.
