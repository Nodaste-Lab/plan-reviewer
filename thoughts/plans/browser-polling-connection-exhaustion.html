Browser Polling for Plan Reviewer Connection Exhaustion

Status: implementation-complete

Created June 8, 2026. Browser feedback, product-intent review, Codex plan review, Claude plan review, scoped implementation, and local verification are complete.

Goal

Stop Brave/Chromium review tabs from hanging when many plan pages are open by removing persistent browser-side SSE connections from the review shell and replacing them with bounded, finite polling that still keeps visible plans fresh.

Why This Plan Exists

The prior event-storm fix bounded metadata refreshes after events, but it did not change the fact that every open review tab owns a long-lived EventSource connection. Chromium-family browsers have a per-origin HTTP/1 connection pool. Once enough review tabs are open, new navigations and ordinary fetch() requests to the same plan-reviewer origin can queue or fail even while the server itself is responsive to other clients.

Authority and Inputs

  • User report: Brave times out while interacting with plan-review pages from the shared plan-reviewer origin.
  • Live diagnostic evidence: the plan-reviewer service had multiple established inbound browser connections from the same client, and each open Brave/Chromium review tab held a persistent :4317 connection.
  • Reproduction evidence: a Chromium context against the shared plan-reviewer origin opened the first six review pages quickly, then pages seven through ten timed out, and a same-origin probe fetch('/api/plans') failed.
  • Code evidence: browser review shell currently starts new EventSource('/api/plans/'+planId+'/events?mode=all&afterSequence=...') in src/server/app.ts.
  • Existing API support: GET /api/plans/:planId/events/poll?mode=all&afterSequence=... already returns finite event batches plus latestSequence.
  • Repo guide: AGENTS.md and thoughts/plans/AGENTS.md.
  • Product intent: thoughts/specs/product_intent.md, especially preserving browser review reliability and not losing comments.

Current Implementation Reality

  • The browser shell loads initial metadata with GET /api/plans/:planId, stores latestEventSequence, then opens one persistent browser EventSource per plan tab.
  • The browser EventSource listens for plan version, sync failure, and comment lifecycle events and schedules full metadata refreshes.
  • The prior implementation already coalesces metadata refreshes and avoids historical SSE replay with afterSequence, but each tab still consumes a long-lived connection.
  • The CLI plan-review watch and plan-review agent next --wait flows also use SSE, but those are intentional process-level listeners and must not be changed as part of this browser-only fix.
  • The finite poll endpoint already supports both mode=queue and mode=all, and existing tests cover poll compatibility for agent/CLI behavior.

Product Intent Alignment

This plan advances thoughts/specs/product_intent.md by keeping the browser review surface trustworthy under realistic multi-plan usage. It preserves queue-backed agent delivery as the correctness-critical path, keeps comments recoverable through full-state metadata snapshots, and avoids requiring users to restart Brave as a manual recovery step.

Locked Decisions

  • Remove persistent browser-side EventSource from the review page.
  • Keep server SSE routes and CLI/agent SSE behavior intact for intentional listener workflows.
  • Use finite browser polling against the existing /events/poll endpoint rather than adding a new transport.
  • Visible review tabs should poll on a concrete short cadence, initially one request about every 1000ms with at most one in-flight poll. Hidden tabs should pause polling, or fall back to a much slower cadence of at least 30000ms only if pause behavior proves unreliable, and should catch up from a full metadata snapshot when revisited.
  • Preserve metadata refresh coalescing so bursts do not reintroduce request storms.

Acceptance Criteria

  1. Opening ten review pages from one Chromium/Brave browser context against the same plan-reviewer origin does not cause page seven or later to time out waiting for the review shell, and a same-origin fetch('/api/plans?limit=1') succeeds within two seconds after all pages are open.
  2. A browser review page does not construct EventSource and does not request /api/plans/:planId/events; browser freshness uses finite /events/poll requests only.
  3. A visible review page receives comment creation, claim, acknowledgement, resolution, release, plan version registration, source sync, and sync failure updates through polling and renders the latest truthful state within a bounded interval.
  4. Hidden or background review pages do not keep a tight polling loop or a long-lived connection; when a tab becomes visible again, it catches up from the latest metadata snapshot and resumes finite polling.
  5. The previous event-storm guarantees remain true: historical stored events and live bursts do not create overlapping full metadata loads or excessive refreshes.
  6. CLI and agent listener behavior remains compatible: plan-review watch, plan-review agent next --wait, queue polling, seeded-comment-stream fixtures, and harness smoke still pass.

BDD Scenarios

Many Review Tabs

Given ten registered plans and one Chromium browser context, when each plan review page is opened from that same context with context.newPage(), then every page reaches the review shell and a final same-origin fetch succeeds promptly because no page holds a persistent browser SSE connection.

Visible Poll Update

Given a reviewer has one visible plan page open, when a browser comment is created through the API, then a finite poll observes the event, schedules one coalesced metadata refresh, and the sidebar shows the new comment.

Plan Sync Update

Given a plan source changes while no comment draft is open, when polling sees a plan version or source-sync event, then the iframe refreshes to the latest render. If a draft is open, the refresh remains deferred until the draft is submitted or cancelled.

Hidden Tab Catch-Up

Given a review page is hidden or backgrounded, when events accumulate, then the tab does not hold a persistent connection or tight poll loop. When it becomes visible again, it loads current metadata and resumes from the latest sequence without replaying old work.

Agent Listener Unchanged

Given an agent uses plan-review agent next --wait, when a browser comment is created, then the agent queue listener still wakes, claims one comment, and preserves at-least-once queue semantics independent from browser polling.

P2: Browser Poller

End State

The review shell no longer creates a browser EventSource. It starts a finite poll loop after the initial metadata snapshot and uses existing event handling logic to schedule coalesced metadata refreshes.

Tests first

Use the P1 failing e2e scenario as the RED signal.

Expected files

src/server/app.ts.

Work

  • Replace startEventStream() with startEventPolling() in the browser client script.
  • Fetch /api/plans/:planId/events/poll?mode=all&afterSequence=<latestEventSequence>&limit=200 as a finite request.
  • Normalize each poll event before reusing existing handlers: poll rows expose eventType and parsed payload, while the current SSE handler expects type and stringified data.
  • For each normalized event, update latestEventSequence, route plan version events through handlePlanVersionEvent, and route comment/sync events through scheduleMetaLoad().
  • If a poll batch reaches the limit, immediately poll again until caught up; otherwise wait for the normal interval.
  • Use approximately 1000ms visible polling with a single in-flight poll, plus bounded retry backoff capped around 10000ms after transient failures.
  • Pause hidden polling by default, or use a fallback cadence of at least 30000ms if full pause behavior proves flaky. On visibilitychange to visible, call scheduleMetaLoad() once and resume polling from the latest sequence.
  • Abort any in-flight browser poll on pagehide or when the document becomes hidden if the chosen strategy pauses hidden tabs.
  • Keep metadata refresh coalescing unchanged.

Verification Strategy

The most important proof is browser-level: a single Chromium context must be able to keep many review pages open and still perform a same-origin metadata fetch. The second proof is transport-specific: browser pages must not create EventSource or call the SSE route. The final proof is behavioral: visible browser pages still converge to truthful comment and plan-sync state, and CLI/agent listeners retain their existing SSE-backed behavior.

Delivery Order

  1. P1 proves the browser connection-pool failure with a failing e2e regression.
  2. P2 removes persistent browser SSE and introduces finite polling.
  3. P3 proves comments, source sync, and event-storm behavior still converge.
  4. P4 proves CLI/agent compatibility and updates guidance only if necessary.

Non-Goals

  • No authentication or trusted-network behavior changes.
  • No changes to queue-backed comment delivery semantics.
  • No removal of the server SSE route or CLI/debug watch support.
  • No broad rewrite of the comment sidebar, rendering pipeline, or source-sync service.
  • No HTTP/2 migration as the primary fix; the browser shell should be robust on the existing HTTP/1 service.
