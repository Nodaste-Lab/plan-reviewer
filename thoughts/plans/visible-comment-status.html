Goal

The numbered circle and the surrounding dotted outline that identify a comment on the rendered plan must change color as the comment moves through its lifecycle, so a reviewer scanning the plan sees status without opening the comments panel:

1Purple — Pending 2Yellow — Claimed 3Green — Acknowledged 4Blue — Resolved

Both the circle (label) and the dotted outline (anchor border) must share the status color for each comment. Recommended fourth color for acknowledged is green #22c55e — see Decision Attention and Locked decisions.

Why this plan exists

Today the plan-review shell renders every persisted comment anchor with the same purple dotted outline and a purple numbered circle, then collapses acknowledged/resolved into a single faded "addressed" style that hides the circle. A reviewer looking at the plan cannot tell which comments are merely pending, which an agent has claimed and is working, and which are resolved. Status is only visible inside the comments panel text. Coloring the marker by lifecycle state makes review progress legible directly on the plan surface, advancing the product-intent principle that the golden path should make status obvious without extra navigation.

Current implementation reality

Lifecycle schema

src/schemas.ts commentStatusSchema = z.enum(['pending','claimed','acknowledged','resolved']). Four states, persisted on each comment and returned by GET /api/plans/:planId/comments as status.

Status → class mapping

isCommentAddressed(comment) in src/server/app.ts (~line 2062) returns true for acknowledged or resolved. addCommentAnchor() (~line 2064) sets the anchor class to comment-anchor addressed (addressed) or comment-anchor pending (everything else, including claimed). So claimed currently looks identical to pending.

Anchor CSS — iframe-injected

ensureFrameAnchorStyles() (~line 1706) injects #plan-review-comment-anchor-styles into the iframe document. This is the copy actually applied to anchors because anchors live inside the iframe body. Rules: .comment-anchor.pending{border:2px dotted rgba(192,132,252,.95);box-shadow:0 0 0 3px rgba(168,85,247,.08)}, .comment-anchor.addressed{border:2px dotted rgba(216,180,254,.9);box-shadow:none}, and the label .comment-anchor-label{background:#7e22ce;color:white;border:2px solid #f3e8ff} with .comment-anchor.addressed .comment-anchor-label{display:none}.

Anchor CSS — parent shell

The parent-shell stylesheet (app.ts ~line 625) contains a parallel .comment-anchor{position:fixed;...} block with .comment-anchor.pending / .comment-anchor.addressed and the same label rule. This block positions/sizes anchors but the iframe-injected block is the visually authoritative one for color. Both must stay aligned to avoid drift.

Drafting marker (transient)

addMarker(rect) (~line 2048) creates a standalone blue .marker circle in the parent shell only during submitPendingComment() (~line 2692) for the screenshot capture. It is removed after submit and is not a persisted lifecycle marker. Out of scope for this plan.

Existing e2e assertions

src/test-fixtures/e2e-run.ts asserts .comment-anchor.pending (background transparent, dotted, 2px) and .comment-anchor.addressed[data-comment-id=...] with borderStyle:'dotted' after claim/resolve (~lines 1207-1216, 1593-1631). The claim/resolve scenario currently relies on acknowledged/resolved collapsing to addressed. These tests must move to the new per-status class scheme.

Comments sidebar row

renderComments() (~line 1368) renders each row as <strong>#seq <status></strong> with the status as plain text. The sidebar is not in scope for color changes; the request is specifically about the on-plan marker. (See Non-goals.)

Locked decisions

  1. Marker = the on-plan anchor only. The numbered circle (.comment-anchor-label) and the dotted outline (.comment-anchor border) are the two surfaces that get lifecycle color. The transient draft .marker and the sidebar comment row are not recolored.
  2. Per-status class names. Anchors get one of: comment-anchor pending, comment-anchor claimed, comment-anchor acknowledged, comment-anchor resolved. The legacy addressed class is retired in favor of the explicit status class. isCommentAddressed() is replaced by an explicit anchorStatusClass(comment) helper.
  3. Color families (pending final contrast check): purple ~#a855f7/rgba(192,132,252,.95) (pending), yellow ~#eab308 with dark circle text #1c1206 (claimed), green ~#22c55e (acknowledged), blue ~#3b82f6 (resolved). The circle label background, circle label border, and anchor dotted border all share the same status hue; the anchor halo box-shadow uses the same hue at low alpha (pending/claimed/acknowledged) and is removed for resolved.
  4. Acknowledged mapping (CONFIRMED 2026-06-24): acknowledged renders with its own fourth color — green #22c55e — giving the intermediate "agent accepted this comment" state a distinct, legible signal. Green is chosen because it is already in the dark theme vocabulary (#22c55e = success/done) and reads as "accepted, not yet closed", while amber is already overloaded for warnings/attention and blue is overloaded for UI chrome + resolved. Reviewer confirmed via browser comment cmt_6qa1UgHykeSu.
  5. Circle label stays visible for resolved. The current rule hides the label when addressed. Under the new scheme the numbered circle remains visible for every status (including resolved) so reviewers can still map a resolved marker to its comment number. If the user prefers hiding resolved labels, that is a one-line override — call out as a follow-up, not a blocker.

Acceptance criteria

  1. A comment in pending renders its on-plan dotted outline and numbered circle in purple.
  2. A comment in claimed renders its outline and circle in yellow (distinct from pending), with legible contrast inside the circle.
  3. A comment in resolved renders its outline and circle in blue, and the numbered circle remains visible.
  4. A comment in acknowledged renders its outline and circle in green (per the recommended fourth color), visually distinct from pending/claimed/resolved.
  5. The iframe-injected anchor styles (#plan-review-comment-anchor-styles) and the parent-shell .comment-anchor rules use the same per-status colors — no drift between the two copies.
  6. Reflow, scroll, and source-sync refresh keep each anchor's status color after re-render (no regression to the existing reflow/scroll coverage).
  7. e2e asserts all four per-status classes (.comment-anchor.pending, .comment-anchor.claimed, .comment-anchor.acknowledged, .comment-anchor.resolved) and the expected borderStyle:dotted for each, replacing the old .addressed assertions.
  8. bun run build, bun run test, and bun run test:e2e all pass.
  9. A status banner at the top of the plan review page shows Red when there are pending comments and none claimed/acknowledged.
  10. The banner shows Yellow when at least one comment is claimed or acknowledged and not all comments are resolved.
  11. The banner shows Green when all comments are resolved (or there are no comments).
  12. The banner updates live as comments transition states, with no page reload, on both desktop and mobile.

BDD scenarios

Pending marker is purple

Claimed marker is yellow

Given a comment transitioned to claimed (claim exists),
When markers render,
Then the iframe contains .comment-anchor.claimed with a dotted yellow border and a numbered label with a yellow background and dark text, visually distinct from pending.

Resolved marker is blue and labeled

Given a comment transitioned to resolved,
When markers render,
Then the iframe contains .comment-anchor.resolved with a dotted blue border and a numbered label with a blue background, and the label is not display:none.

Acknowledged marker is green (fourth color)

Given a comment in acknowledged,
When markers render,
Then the iframe contains .comment-anchor.acknowledged with a dotted green border and a numbered label with a green background, visually distinct from pending (purple), claimed (yellow), and resolved (blue).

Status color survives reflow and sync

Given markers in pending, claimed, acknowledged, and resolved states,
When the plan source syncs and the frame re-renders, then scroll/reflow fires,
Then each anchor re-applies its status class and color, and no anchor reverts to a stale class.

Counterexample — claimed must not render as pending

Given a claimed comment,
When markers render,
Then the anchor does not match .comment-anchor.pending and the label background is not the pending purple.

Banner is Red when only pending comments exist

Given a plan whose comments are all pending (none claimed/acknowledged/resolved),
When the review page loads/refreshes,
Then the top-of-plan banner is Red and labeled to indicate pending comments awaiting agent pickup.

Banner is Yellow when an agent is working comments

Given at least one comment is claimed or acknowledged and not all comments are resolved,
When the review page refreshes,
Then the banner is Yellow and labeled to indicate an agent is working.

Banner is Green when all comments are resolved

Given every comment is resolved (or there are no comments),
When the review page refreshes,
Then the banner is Green and labeled “all resolved” (or equivalent).

Banner updates live across transitions

Given a plan with one pending comment (banner Red),
When the comment is claimed then acknowledged then resolved via API,
Then the banner transitions Red → Yellow → Yellow → Green on successive loadMeta() refreshes with no page reload.
