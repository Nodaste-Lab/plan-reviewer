Mermaid Diagram Rendering in Plan Viewer

Linear issue: none provided. Do not invent a NOD key for this plan.

Plan paththoughts/plans/mermaid-diagram-rendering.html
Primary surfacesrc/render/render.ts, src/server/app.ts, browser review shell
Requested outcomeMermaid diagrams render in the viewer and remain commentable at diagram-element granularity.

Goal

Plan documents can include Mermaid diagrams using conventional Mermaid blocks, and the plan viewer renders them as safe, readable SVG diagrams without allowing plan-authored scripts. Reviewers can select a diagram node, edge, label, or the diagram as a whole and submit normal browser comments that agents receive through the existing queue.

Solution narrative

The viewer should treat Mermaid as a first-class, service-owned rendering feature rather than as arbitrary plan JavaScript. Registration keeps the source HTML safe and script-free, annotates Mermaid source blocks with stable source hashes, and the review shell renders those blocks after the iframe loads by importing the official bundled Mermaid browser ESM file from a local vendor route such as /vendor/mermaid.esm.min.mjs. The iframe remains no-script; only the parent review shell runs trusted viewer code and injects sanitized SVG into the same-origin iframe DOM.

The commenter then targets Mermaid SVG sub-elements the same way it targets other plan DOM, with added diagram metadata so anchors can survive source sync and re-rendering. If Mermaid cannot parse a diagram, the viewer shows an inline, commentable error panel next to the original source instead of blanking the plan or replacing the last good synchronized source.

The implementation must not expose a brittle package-entry route that leaves Mermaid’s relative module imports unresolved. If the installed package entry is not a single browser-ready bundle, implementation should serve the package’s documented browser bundle path or add a minimal static vendor mount for Mermaid’s required package assets. Browser import success is proven by the e2e viewer scenario that renders an SVG from the vendor route; the dependency smoke test remains a secondary HTTP-level check for route existence, MIME type, and bytes.

Why this plan exists

Mermaid blocks are currently inert because plan-authored scripts are removed by renderPlan and the rendered iframe is served with script-src 'none'. That is the correct safety baseline, but it means diagrams authored inside plans cannot render. The missing product behavior is a trusted viewer-side Mermaid pipeline that keeps the plan artifact safe while making diagrams useful review targets.

Authority and inputs

  • User request: add Mermaid diagram support inside the viewer, ideally with selectable diagram elements for commenter questions.
  • AGENTS.md: rendered-plan safety, comment lifecycle, source sync, and browser UI are product-critical.
  • thoughts/specs/product_intent.md: reviewers must select exact plan content, comments must stay durable, and sanitized render output must remain script-free.
  • Mermaid API evidence: mermaid.initialize({ startOnLoad: false }) plus mermaid.render()/mermaid.run(); securityLevel: 'strict' is the safe default and disables Mermaid click callbacks.
  • Dependency evidence: npm mermaid is MIT licensed, current version observed as 11.15.0, and is the canonical implementation rather than a custom diagram parser.

Current implementation reality

  • src/render/render.ts sanitizes registered HTML, removes <script>, rewrites images, and adds data-plan-node-id to rendered nodes.
  • /render/:planId in src/server/app.ts serves the plan iframe with script-src 'none' and default-src 'none'; this should remain true for plan-authored content.
  • The parent review shell already serves trusted vendor scripts for html2canvas, @medv/finder, and @washi-ui/core, then reaches into the same-origin iframe to attach selection/comment behavior.
  • Comment anchoring currently supports dom, text_range, and image. SVG diagram elements can use dom anchors if the client assigns stable selectors and metadata.
  • Server-side anchor remapping currently checks stored rendered HTML for data-plan-node-id, text quotes, image hashes, and selectors; dynamic Mermaid anchors need explicit source-container metadata to avoid false stale states.

Product intent alignment

This plan advances thoughts/specs/product_intent.md by making the simplest reviewer workflow work for diagrams: open a plan, select the exact visual element needing discussion, submit a comment, and trust the agent receives durable context. It preserves the safety bar that rendered output remains script-free from plan authors and that source sync fails safe.

  • Golden path: authors write ordinary Mermaid blocks; reviewers do not install browser extensions, run separate renderers, or screenshot diagrams manually.
  • Safe default: the iframe stays no-script and Mermaid runs only as trusted viewer code with strict Mermaid security, local assets, and post-render SVG hardening.
  • Recovery: malformed diagrams produce an inline commentable error with the exact source block and next fix, while the rest of the plan remains reviewable.
  • Truthful status: diagram render failures are visible in the viewer and test-covered; they do not masquerade as successful blank diagrams.

Locked decisions

  • Do not enable plan-authored scripts. Keep /render CSP script-src 'none' and do not add allow-scripts to the plan iframe.
  • Render Mermaid from trusted parent-shell code. Serve the official browser-ready Mermaid ESM bundle through a local /vendor/mermaid.esm.min.mjs-style route, or serve the required Mermaid static module graph if the bundle imports local chunks, and render after iframe load/source-refresh.
  • Use Mermaid strict security. Configure startOnLoad:false, securityLevel:'strict', htmlLabels:false, deterministic IDs, bounded text size, and dark theme variables.
  • Anchor to source and rendered element. Store Mermaid source-node ID and source hash in comment anchors, then add SVG element IDs for precise in-view reattachment. For Mermaid comments, anchor.diagram.sourcePlanNodeId is the static source block data-plan-node-id, while anchor.planNodeId may identify the rendered SVG sub-element; server remapping must use the source block/hash fields rather than requiring the dynamic SVG node to exist in stored rendered HTML.
  • Diagram failure is local, not whole-plan failure. A malformed Mermaid block renders a visible error placeholder and keeps comments/source sync operational.

Acceptance criteria

  1. A plan with <pre class="mermaid">, <div class="mermaid">, or <pre><code class="language-mermaid"> displays a rendered SVG diagram in the viewer.
  2. Rendering does not require or permit plan-authored scripts; existing script-blocking warnings and iframe CSP remain effective.
  3. Reviewers can click/select a Mermaid node, edge, label, or fallback diagram container and submit a normal comment.
  4. Agent-visible comment payloads include useful diagram context through the correctness-critical plan-review agent next --json path: source block node ID, diagram source hash, selected SVG element key/label when available, heading path, selector, preview text, and screenshot when capture succeeds.
  5. Existing markers redraw after Mermaid rendering and source refresh; comments on unchanged diagram elements do not become falsely stale merely because SVG is client-rendered.
  6. Malformed Mermaid source shows a visible, accessible, commentable error panel while the rest of the plan remains usable.
  7. The implementation is covered by contract/dependency tests and browser e2e tests, including comment creation on diagram elements.
  8. Rendered Mermaid diagrams use viewer-owned dark card styling that matches the plan-review shell palette instead of showing a mismatched white diagram background.

BDD scenarios

Rendered diagram happy path

Given a registered plan contains a Mermaid flowchart block, when the reviewer opens the plan URL, then the viewer replaces the source block with an SVG diagram, preserves an accessible fallback/source affordance, and keeps the plan iframe no-script.

Node-level commenting

Given a rendered Mermaid diagram has visible nodes and edges, when the reviewer selects a node and submits “why this transition?”, then the comment payload identifies that diagram source and selected node, and the marker reattaches to that node after reload.

Edge and label commenting

Given a Mermaid edge or edge label is clicked, when the composer opens, then the selected target is the nearest meaningful SVG edge/label element rather than the whole iframe body.

Source sync refresh

Given a plan source sync updates text outside an unchanged diagram, when the open viewer refreshes the iframe content, then Mermaid rendering reruns, markers redraw after render completion, and existing Mermaid comments remain mapped.

Malformed diagram recovery

Given one Mermaid block has invalid syntax, when the viewer renders diagrams, then that block shows an error panel with a clear fix path while other diagrams and comments continue working.

Safety boundary

Given a plan contains a Mermaid block plus a <script> tag or unsafe URL, when it is registered and opened, then the script remains removed, unsafe generated SVG attributes are stripped, and no plan-authored JavaScript executes.

P2 — Render safe Mermaid SVG in the viewer

End State

The review shell renders Mermaid diagrams after iframe load and after source-refresh replacement, using trusted parent code while keeping the iframe no-script.

Tests first

  • Add dependency smoke coverage for the Mermaid vendor route.
  • Add an e2e scenario with a plan containing a Mermaid block and assert the iframe contains a rendered SVG plus no executable plan scripts.

Expected files

  • package.json, lockfile
  • src/server/app.ts
  • src/__tests__/dependency-smoke.test.ts
  • src/test-fixtures/e2e-run.ts

Work

  • Add the official mermaid dependency and serve a browser-importable local bundle route, preferring mermaid/dist/mermaid.esm.min.mjs or the package’s documented bundled ESM artifact over the Node package entry if the entry has unresolved relative imports.
  • Import Mermaid in the parent client.js, initialize once with strict security, no auto-load, no HTML labels, deterministic IDs, bounded text size, and dark theme variables.
  • On iframe load/source refresh, find Mermaid source blocks, render them asynchronously, replace each block with a wrapper containing sanitized SVG, and leave a hidden/collapsible source copy for diagnostics.
  • Harden generated SVG before insertion with an explicit browser-side allowlist pass. Do not rely only on Mermaid’s internal sanitization.
  • Use this hardening contract: retain only Mermaid-required SVG structure and presentation such as svg, g, path, line, polyline, polygon, rect, circle, ellipse, text, tspan, defs, marker, style, title, desc, geometry/presentation attributes, viewBox, role, aria-*, id, class, and data-*. Retained style blocks are accepted only as Mermaid strict-mode theming output; if tests show author-controlled CSS can escape normal presentation styling, strip style blocks and rely on presentation attributes/theme variables instead. Strip all event-handler attributes, script, foreignObject, use, animate, set, image with external or inline hrefs, xlink:href, and href on non-anchor SVG elements. The required support target is flowchart and sequence diagrams first; if Mermaid 11.x output for another diagram type requires use, that type stays out of scope until a narrower safe allowlist is added.
  • Show an accessible inline error panel for render failures with the Mermaid error text and source preview; do not fail whole-plan registration or source sync.
