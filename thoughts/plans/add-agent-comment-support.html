Native Agent Comment Support

Status: execution-ready Plan path: thoughts/plans/add-agent-comment-support.html Linear: no Linear issue exists for this request

Solution narrative: add a native plan-review command/API path that lets an agent target a stable rendered-plan DOM node, submit a comment through the existing comment creation pipeline, and persist the first thread entry with an agent identity instead of pretending it came from a human reviewer.

Goal

Agents can add review comments to registered plans without using the browser UI, while preserving the existing comment lifecycle, queue visibility, document comment history, anchor remapping behavior, and rendered sidebar markers.

Why this plan exists

The current browser path already lets humans select plan content and submit anchored comments. Agents can process, ack, resolve, and reply to comments from the CLI, but there is no first-class command for an agent reviewer to create a new anchored comment with its own identity. This creates an unnecessary gap in agent plan-review workflows and encourages ad hoc notes instead of durable review comments.

Authority and inputs

  • User request: add native comment support to planner commands so agents can add comments like humans, using DOM-based anchor selection, preserving comment history, and recording agent identity.
  • Repo guidance: AGENTS.md requires reviewed HTML plans, queue/comment lifecycle care, source sync safety, and aligned API/CLI/README/tests.
  • Product intent: thoughts/specs/product_intent.md defines durable browser comments, queue-backed delivery, and API/CLI/browser lifecycle parity as product-critical.
  • Planning guidance: thoughts/plans/AGENTS.md, reviewed-html-plan, planning-workflow, html-plan-reviewer, and product-principles.

Current implementation reality

  • src/server/app.ts renders the browser review shell. The browser client computes anchors in anchorForElement and anchorForSelection, then posts to POST /api/plans/:planId/comments.
  • src/render/render.ts sanitizes registered HTML and adds stable data-plan-node-id values to rendered DOM nodes, which is the right canonical target for agent-created DOM comments.
  • src/storage/database.ts createComment already owns comment IDs, sequence numbers, duplicate guards, events, conversation payloads, queue delivery, and the first comment_thread_entries row.
  • Today createComment normalizes all creators to { type: "reviewer", displayName } and always creates the first thread entry with role human. That hides agent-authored comments.
  • src/cli.ts exposes agent next, ack, resolve, reply, and plan notes, but no command that creates a new anchored comment.
  • README.md, src/__tests__/contracts.test.ts, and src/test-fixtures/e2e-run.ts already document and test the human comment path, lifecycle, queue claims, duplicate guards, and browser marker behavior.

Product intent alignment

This plan advances the product intent outcomes that review comments are durable, queue-visible, recoverable, and consistent across browser, CLI, service, and agent workflows.

  • Golden path: an agent can run one copy-paste command with a plan id, stable DOM target, body, and identity.
  • Safe defaults: the command targets the latest rendered safe plan version; source sync remains the source of truth, and the service fails closed when the target is missing or ambiguous.
  • Recovery: duplicate retries reuse clientMutationId and the existing fingerprint protections; if the same mutation id is retried with a different agent identity but the same version/body/anchor fingerprint, first-create-wins and the API returns the original stored identity. Target errors explain how to find a stable data-plan-node-id.
  • Parity: agent-created comments use the same persisted comment rows, thread history, events, queue delivery, sidebar rendering, and ack/resolve lifecycle as browser comments.

Locked decisions

  1. Agent-created comments are normal comments. They remain pending, queue-visible, ackable, resolvable, and visible in the sidebar using the existing comment lifecycle.
  2. Agent identity is first-class comment metadata. Store createdBy.type = "agent", a non-empty display name, and optional stable agentId when provided. The first thread entry uses role agent.
  3. First slice targets DOM nodes, not text ranges or image regions. Native agent creation resolves a rendered plan DOM node by data-plan-node-id or an exact element id selector. Text selection and image rectangle authoring stay browser-only for now.
  4. The service resolves anchors. The CLI sends intent; the server resolves the latest rendered HTML into the same anchor shape used by browser DOM comments before calling createComment.
  5. The native endpoint is fixed before execution. Implement POST /api/plans/:planId/comments/dom for this slice; do not leave endpoint naming or request shape to implementation discretion.
  6. Plan read surfaces must expose anchor targets. Agents must be able to discover usable DOM anchors from API/CLI reads without opening the browser review page.
  7. No SQLite schema migration is required. Comment author data and anchors are already JSON-backed; the change is schema validation, normalization, API/CLI behavior, and tests.

Native agent comment contract

The public API for this slice is POST /api/plans/:planId/comments/dom. It targets the latest rendered version for the plan and returns the same envelope shape as the existing browser comment creation endpoint: { comment, event, created }.

{
  "body": "Clarify this acceptance criterion.",
  "target": { "planNodeId": "ac-2" },
  "createdBy": { "type": "agent", "displayName": "Codex", "agentId": "codex-review-1" },
  "clientMutationId": "optional-idempotency-key"
}

Plan read surfaces must expose enough anchor inventory for agents to choose a target without a browser view. GET /api/plans/:planId and the new plan-review show <planId> --json command return anchorTargets derived from the latest rendered HTML. Each target includes planNodeId, exact id selector when available, tagName, headingPath, textPreview, outerHtmlPreview, and anchorCommand showing the copy-paste comments add form for that target. The inventory omits active content and does not require browser execution. Because the renderer assigns data-plan-node-id to every node, inventory must prioritize useful semantic comment targets—explicit IDs, headings, sections/articles, figures/images, tables, lists, and code blocks—and avoid redundant low-value descendants unless needed for exact targeting.

  • target.planNodeId is the primary selector and resolves against [data-plan-node-id="..."] in the current rendered plan.
  • target.selector is optional and allowed only for exact element id selectors such as #ac-2; broad CSS selectors are rejected to avoid ambiguous agent targeting.
  • Resolved comments call the existing createComment path with anchorType: "dom" and an anchor containing planNodeId, cssSelector, domPath, xpath, textQuote, headingPath, textPreview, outerHtmlPreview, rect, and viewport.
  • Identity placement is part of the public contract: comment.createdBy is { type: "agent", displayName, agentId? }; the first comment.threadEntries[0] has role: "agent" and matching createdBy; top-level comment.conversationPayload.createdBy carries the same identity so agent next claims are self-describing without a second API lookup.
  • Human/browser comments continue to store comment.createdBy.type = "reviewer", first thread role human, and no agent identity requirement.

Acceptance criteria

AC-1: Native agent command creates anchored comments

plan-review comments add <planId> --plan-node-id <id> --body <text> --agent <name> --json creates a pending comment on the latest rendered version with anchorType: "dom" and a browser-compatible anchor.

AC-2: Agent identity is durable and visible

The comment record, first thread entry, API responses, queue payload, and sidebar history identify the creator as an agent with the supplied display name instead of a human reviewer.

AC-3: Existing human comment behavior is unchanged

Browser-created comments still default to reviewer/human identity, keep duplicate-submit protections, render anchors, and enter the queue as before.

AC-4: Target resolution fails closed

Missing, stale, unsupported, or ambiguous DOM targets return actionable validation errors and create no comment, event, delivery outbox row, or thread entry.

AC-5: Public contracts stay aligned

README, CLI help, API schemas, contract tests, and e2e/fixture coverage all describe the same agent comment creation lifecycle.

AC-6: Agents can discover anchors from read surfaces

GET /api/plans/:planId and plan-review show <planId> --json expose current anchorTargets with stable planNodeId, context previews, heading path, and copy-paste comment command guidance so agents do not need a browser view to choose an anchor.

BDD scenarios

BDD-1: Agent adds a DOM comment

Given a registered plan whose rendered HTML contains data-plan-node-id="ac-2", when an agent runs plan-review comments add plan_123 --plan-node-id ac-2 --body "Clarify this" --agent Codex --json, then the service creates one pending browser.comment.v1 comment with a DOM anchor, creator type agent, thread role agent, and queue-visible event.

BDD-2: Sidebar shows agent history

Given an agent-created comment exists, when the browser review page loads comments, then the comment row shows the agent display name and an agent thread role while using the same marker and status rendering as human comments.

BDD-3: Human path remains human

Given a reviewer selects plan text or a DOM node in the browser, when they submit a comment, then the stored creator remains a reviewer and the first thread entry remains role human.

BDD-4: Missing agent identity fails

Given no --agent value, when an agent tries to create a comment, then the CLI exits with an actionable error and the service stores nothing. Environment-variable identity fallback is intentionally out of scope for this slice.

BDD-5: Missing target fails closed

Given the target DOM node no longer exists in the latest rendered plan, when an agent submits a comment for that target, then the service returns validation_failed with guidance to refresh/read the current rendered plan and no lifecycle event is emitted.

BDD-6: Agent comment remaps after source sync

Given an agent-created comment is anchored by planNodeId, when source sync registers a new version, then existing DOM remap semantics are preserved: anchorState: "mapped" only when the node id and quote/preview text still match, "stale" when only the node id remains, and "unmapped" when neither target nor quote remains.

BDD-7: Agent discovers anchors without browser view

Given a registered plan contains id="solution-narrative", when an agent reads GET /api/plans/:planId or runs plan-review show plan_123 --json, then the response includes an anchorTargets entry for solution-narrative with heading/context preview and a copy-paste plan-review comments add ... --plan-node-id solution-narrative command.
