PR Merge Detection for Plan Index

Execution-ready implementation plan for persistently linking plans to pull requests, linking Linear issues, and surfacing merged/open/unlinked PR state in the plan index.

Status: execution-readyScope: PR + Linear metadata, index status, planning guidanceRisk: medium

Progress

Goal

Make the active and archived plan indexes truthfully show whether each plan has an associated PR, whether that PR is open, merged, closed-unmerged, unknown, or stale, and whether the plan is linked to its Linear issue. The associations must be reliable and programmatic: agents can explicitly link a PR when they create it, the CLI can infer or refresh PR state from GitHub using registered repo and branch metadata, and registration/source sync can detect NOD-NNN-style Linear references without treating plan prose as the only source of truth.

Why this plan exists

Plan progress currently tells reviewers whether phases are complete, but it does not answer the operational question that matters after execution: did the implementation PR merge? The index also only displays Linear issue text when registration metadata already has it, so plans with a NOD-NNN reference can miss the direct Linear link reviewers need. Relying on agents to manually edit plan text is fragile because the index cannot trust or query that text. The product needs first-class PR association, refreshable merge status, Linear issue linking, and planning guidance that makes both the solution narrative and Linear issue presence part of the normal plan contract.

Solution narrative

The proposed solution adds a small, explicit PR-tracking layer to plan-reviewer. Each plan can have one current GitHub pull request record stored beside the existing plan metadata. That record contains the PR URL, owner/repo, number, head and base refs, open/closed state, merged timestamp when present, last checked time, and any refresh error. The plan HTML can still mention a PR for human context, but the plan index and API trust only this structured record.

For agents, the normal workflow becomes deterministic: after creating a PR, run plan-review pr link <plan> --url <github-pr-url> --json, then run plan-review pr refresh <plan> --json before final handoff. If the agent forgets the explicit link, refresh can safely try to connect the dots from the registered GitHub remote and branch. It links only when GitHub returns exactly one plausible PR; no matches or multiple matches fail closed with the exact link command to run.

For users, the plan index gains a PR status pill and link on every card plus a clickable Linear issue link when a NOD-NNN-style issue is known or detected. A reviewer scanning active or archived plans sees No PR, PR open, PR merged, PR closed, PR unknown, or PR stale without opening each plan, and can jump directly to the Linear issue when available. Unknown or stale cards explain when status was last checked and how to refresh it. API and CLI index output expose the same state so scripts can answer the same question programmatically.

Product intent alignment

This advances the product intent outcome that the plan index truthfully reports plan status and repository metadata. It preserves the repo HTML plan as the plan source of truth while making PR status and normalized Linear links service-owned metadata facts that APIs and UI can query. The golden path is: create a plan with a solution narrative and Linear issue reference, register/build the plan, create a PR, link or auto-discover it, refresh status, and scan the index. Routine missing data is self-healed through safe branch-based GitHub discovery and NOD-NNN Linear reference detection; ambiguous matches fail closed with an exact command for explicit linking.

Locked decisions

  • Source of truth: PR association and merge state live in structured service metadata, not in plan HTML text. Plan HTML may mention the PR, but the index does not parse it for truth.
  • Provider scope: this plan supports GitHub only. Other providers are non-goals until there is a concrete repo need.
  • Agent update path: agents that create a PR must run plan-review pr link <planId-or-slug> --url <pr-url> or --number <n> from the repo, then refresh status before handoff.
  • Connect-the-dots fallback: plan-review register and plan-review pr refresh may infer one GitHub PR by matching the registered remote owner/repo and branch head. Zero or multiple matches do not guess.
  • GitHub data source: use GitHub REST from the CLI with GITHUB_TOKEN or a token from gh auth token when available; unauthenticated public repo lookup is allowed as a best effort. Do not add Octokit for this narrow slice.
  • External refresh location: GitHub network calls happen in CLI commands, not during normal index rendering, so page loads remain fast and deterministic. The index shows lastCheckedAt and stale/unknown guidance.
  • PR persistence API: CLI PR commands persist through PUT /api/plans/:planId/pull-request with a validated PR metadata payload and clear through DELETE /api/plans/:planId/pull-request. These routes are local-service metadata updates only; they do not call GitHub.
  • Status vocabulary: UI/API status is one of unlinked, open, merged, closed, unknown, or stale. merged requires GitHub merged_at or equivalent merged signal. closed means closed without a merged signal and is terminal. stale is derived, not persisted, only when a linked PR's last known state is open or unknown and it has no successful lastCheckedAt or the last successful check is older than 24 hours; stale never masks terminal closed or merged states.
  • Linear detection: detect canonical NOD-NNN-style issue keys case-insensitively from registration metadata and plan HTML text, normalize to uppercase, and render a Linear URL as https://linear.app/nodaste/issue/<ISSUE_KEY> unless a future config surface explicitly overrides it. Do not call Linear APIs in this slice.
  • Planning guidance: new HTML plans in this repo should include a top-level Solution narrative section and a Linear issue reference, or explicitly state why no Linear issue exists.

Acceptance criteria

  1. A plan can store at most one current GitHub PR association with URL, owner, repo, number, head branch, base branch, state, merged flag, merged timestamp, last checked timestamp, source, and last refresh error.
  2. GET /api/plans, GET /api/plans/:planId, and plan-review index --json include the PR metadata without breaking existing fields.
  3. PUT /api/plans/:planId/pull-request validates and persists PR metadata submitted by the CLI, and DELETE /api/plans/:planId/pull-request clears the current association without touching comments or plan versions.
  4. plan-review pr link <plan> --url <github-pr-url> --json validates the URL, fetches the current GitHub PR state when possible, persists it, and returns the stored association.
  5. plan-review pr refresh <plan> --json updates an existing link or safely infers exactly one PR from registered repo/branch metadata.
  6. Auto-discovery fails closed with an actionable error when no PR or multiple plausible PRs exist; it does not mark the plan merged or open by guess.
  7. The active and archived HTML indexes show a visible PR pill/link for each plan: No PR, PR open, PR merged, PR closed, PR unknown, or PR stale.
  8. The index search/filter haystack includes PR URL, number, state, and merged/open terms so users can find merged or unmerged plans.
  9. Agent-facing build/review handoff guidance tells agents the exact plan-review pr link and plan-review pr refresh commands to run after PR creation and before final handoff.
  10. Existing registration, source sync, archive, queue, comment, execution readiness, and Build Plan behavior remain intact.
  11. Failures from GitHub lookup explain what was attempted, why automation stopped, and the next safe command to link or refresh manually.
  12. Registration/source sync detects NOD-NNN-style Linear references from metadata or plan HTML, normalizes them, and the active/archive indexes render them as links.
  13. Repo planning guidance requires new plans to include a near-top Solution narrative section and a Linear issue reference or explicit no-issue rationale.

BDD scenarios

BDD-1 - Explicit link happy path

Given a registered plan and a GitHub PR URL, When an agent runs plan-review pr link <plan> --url <url> --json, Then the service stores the PR association and the index shows a linked PR pill with the fetched state.

BDD-2 - Merged PR refresh

Given a plan already linked to PR #12, When plan-review pr refresh <plan> receives GitHub state closed with merged_at, Then the plan index shows PR merged and includes the merged timestamp.

BDD-3 - Safe branch auto-discovery

Given a registered GitHub remote and branch feature/x, When refresh finds exactly one PR with matching head repo owner and branch, Then the plan is linked with source auto-discovered.

BDD-4 - Ambiguous auto-discovery fails closed

Given refresh finds two plausible PRs for a branch, When the CLI cannot prove which PR belongs to the plan, Then it stores no new association, keeps the index at PR unknown or No PR, and prints the exact plan-review pr link command format.

BDD-5 - Missing or insufficient GitHub auth

Given GitHub lookup returns authentication or not-found errors, When refresh runs, Then the CLI records a refresh error, marks the displayed state unknown/stale, and tells the agent to set GITHUB_TOKEN, run gh auth login, or explicitly link a URL if lookup is otherwise impossible.

BDD-6 - API/CLI/UI parity

Given plans with no PR, open PR, merged PR, and closed-unmerged PR states, When the API, CLI index, active index, and archive index render, Then all surfaces report the same state vocabulary and PR URL/number.

BDD-7 - Agent handoff includes PR update

Given an executing agent creates a PR, When it follows plan-review handoff guidance, Then it has a deterministic command to attach the PR to the plan and the index no longer depends on manual plan edits.

BDD-8 - Existing workflows remain intact

Given existing comment queue, archive, source sync, and Build Plan flows, When PR metadata is absent, Then those workflows still behave as before and display No PR without errors.

BDD-9 - Linear link detection

Given a registered plan contains nod-123 in its plan text or registration metadata, When the index renders, Then the card shows a normalized NOD-123 Linear link and includes the issue key in search/filter terms.

BDD-10 - Planning guidance contract

Given an agent creates a new repo HTML plan, When it follows thoughts/plans/AGENTS.md, Then the plan includes a top Solution narrative and either a Linear issue reference or an explicit no-issue rationale.

BDD-11 - Adversarial same branch in wrong repository

Given GitHub returns a PR with the same branch name from a fork or different repository owner than the registered plan remote, When auto-discovery runs, Then it does not link that PR unless the head repo and registered remote match the locked matching rules.

BDD-12 - Adversarial spoofed PR URL

Given an agent passes a URL that looks similar to GitHub but is not a canonical https://github.com/<owner>/<repo>/pull/<number> URL, When plan-review pr link validates it, Then it rejects the URL, stores nothing, and prints the accepted URL shape.

BDD-13 - Adversarial closed but unmerged PR

Given GitHub returns state: closed with no merged_at, When refresh maps state, Then the plan displays PR closed, not PR merged, even if the plan phases are complete.

BDD-14 - Adversarial Linear false positive

Given plan text contains a non-issue token such as NOD-ABC, NOD-, or a code sample that should not be treated as a canonical issue key, When Linear detection runs, Then only valid NOD-\d+ keys are normalized and linked.

BDD-15 - Adversarial cross-plan update

Given two plans in different repositories share a slug or branch name, When an agent links or refreshes one plan, Then only the resolved plan ID is updated and the command fails with the existing ambiguous-slug guidance if the identifier is not unique.

  3. Expose the metadata in API/CLI/index UI.

Non-goals

  • Creating pull requests from plan-reviewer.
  • Running background GitHub polling from normal index page loads.
  • Supporting GitLab, Bitbucket, Gerrit, or arbitrary forge providers in this slice.
  • Calling the Linear API, syncing Linear issue state, or creating Linear issues.
  • Using plan HTML parsing as the authoritative PR source.
  • Changing comment queue delivery, source sync safety, or execution-ready review semantics except for additive PR handoff guidance.
  • Adding authentication or multi-tenant security to the local unauthenticated service.
