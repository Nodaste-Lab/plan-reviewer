Goal

Add an existing, token-efficient plan authoring format that preserves the full review power of the current HTML plan artifacts. Agents should write compact structured source, the service should compile it into semantic HTML, and the existing sanitizer/render/source-sync/review-comment lifecycle should remain the final authority.

The recommendation is Markdoc source plus generated HTML output. Raw HTML remains supported for historical plans and as an explicit escape hatch, not as the default agent-authored plan format.

Decision Attention / Low-confidence Areas

  • No unresolved product decision remains. The first slice uses Markdoc as the default compact source, permits raw HTML only through explicit audited escape blocks for rich mocks and legacy fragments, keeps MDX out of the default path, and updates repo/product guidance so agents know when .markdoc is authoritative versus legacy .html.

Solution narrative

Introduce a plan-authoring pipeline where thoughts/plans/<slug>.markdoc compiles to thoughts/plans/<slug>.html. The generated HTML is the same semantic, dark-mode, stable-ID artifact that the browser reviewer already serves and annotates. Registration accepts either HTML or Markdoc: HTML follows the current path; Markdoc is compiled, validated, then sent through the existing HTML safety pipeline.

Markdoc gives the repository an existing language rather than a custom DSL. It starts with CommonMark, adds declarative tags such as {% section %} and {% phase %}, supports attributes and validation schemas, produces an AST/renderable tree, and can render HTML. Markdoc can also parse raw HTML when its tokenizer is configured with HTML support, so gaps in the custom tag set can be supplemented without inventing syntax. This plan intentionally routes that capability through an explicit {% html reason="..." %} escape hatch and the existing plan-review sanitizer, so raw HTML is available for rich mocks and legacy fragments but remains auditable rather than becoming the default authoring style. The repo-owned template supplies the repetitive page shell, shared CSS, table of contents, required section ordering, and stable wrapper structure.

The first implementation should be conservative: no plan-authored JavaScript, no MDX runtime, no React execution. If future work wants interactive trusted components, add a separate MDX/component mode with a different threat model and explicit trust boundary.

Why this plan exists

Raw HTML plans are reviewable but token-inefficient. Agents spend large context budgets on boilerplate tags, repeated CSS, closing tags, and layout scaffolding instead of product decisions, tests, and evidence. The current corpus shows that plans need more than Markdown: they contain structured phases, rich tables, screenshots, full UI mockups, ARIA-labeled pseudo-controls, stable IDs, code blocks, and generated review targets. The new authoring format must preserve those capabilities while reducing authoring noise.

MDX option and exclusion rationale

MDX is a real candidate for the long-term vision where plans can contain trusted components. It combines Markdown with JSX, JavaScript expressions, and ESM imports/exports. Conceptually, an MDX plan could render custom components such as <PlanPhase />, <EvidenceMatrix />, or <InteractiveMock />.

What MDX would look like

import { Plan, Phase, EvidenceMatrix } from './plan-components'

export const metadata = {
  title: 'Markdoc Plan Authoring DSL',
  executionReady: false
}

# Markdoc Plan Authoring DSL

<EvidenceMatrix rows={[
  ['Safety boundary', 'renderPlan sanitizes HTML', 'Compiler must reuse it'],
]} />

<Phase id="phase-p1-compiler" title="Add compiler" verify="bun run test">
  Add a Markdoc compiler and fixtures.
</Phase>

Why not MDX first

  • Execution model: MDX content compiles into JavaScript component code. That is not just markup; it can include expressions and module imports. The current product intent says browser shell interactivity is service-owned and plan-authored active content is not supported.
  • Security boundary: Today the repo can reason about plan safety by parsing and sanitizing HTML and serving the iframe with no plan scripts. MDX would require a separate trusted compilation/execution sandbox or a strict component allowlist before it is safe for untrusted or agent-authored plans.
  • Framework coupling: MDX is strongest when paired with React/Preact/Vue component rendering. This package currently serves first-party HTML from Fastify and vanilla client code, not a React app shell.
  • Review determinism: Browser comments rely on stable DOM targets. Arbitrary components can produce dynamic DOM depending on props, imports, runtime state, or component versions unless the system freezes a render contract.
  • Operational cost: Supporting MDX well means dependency policy, bundling, component registry, SSR/static rendering, sandboxing, source maps/error reporting, and generated-DOM stability tests. Markdoc gives most needed structure without that runtime.

Future MDX lane

Keep MDX as a possible future trusted component mode, not the default plan source. A later plan could add .mdx only for repo-owned component libraries, precompiled at registration time, with no network imports, no arbitrary user imports, deterministic static rendering, and the same final HTML sanitizer/source-sync behavior. That future mode should be gated by an explicit trust label such as --trusted-components and should never silently replace the default safe Markdoc path.

Product intent alignment

This plan advances thoughts/specs/product_intent.md by keeping browser-reviewable HTML as the delivered artifact while making authoring easier for agents. It preserves stable URLs, source sync, exact browser annotations, queue-backed comments, and safe rendered output.

  • Golden path: agents can register a compact Markdoc plan and receive the same reviewer URL and comment workflow.
  • Safe defaults: Markdoc compiles to sanitized HTML; plan-authored JavaScript remains unsupported.
  • Recovery: compiler validation errors should identify the source line, tag, missing ID, or unsupported escape hatch and keep the last good rendered HTML active.
  • Truthful status: generated HTML should identify its source and stale/generated state so agents do not hand-edit the wrong file.

Locked decisions

  • Use Markdoc for the first compact authoring format. It is existing technology, Node-compatible, declarative, schema-validatable, and renders HTML.
  • Keep HTML as the registered browser-review artifact. Markdoc source does not replace the viewer contract; it generates it.
  • Keep legacy HTML passthrough. Historical plans and special artifacts remain registerable as HTML.
  • Do not adopt MDX in the first slice. Reserve MDX for a later trusted-component mode with a separate security plan.
  • The existing sanitizer/render path remains final. Markdoc compiler output must still pass through HTML parsing, sanitization, image rewriting, and node-ID assignment.
  • Allow a controlled raw HTML escape hatch. The corpus requires it for rich UI mocks unless equivalent structured mock tags exist. The first slice permits approved reasons ui-mock, legacy-fragment, and unsupported-markdoc-shape; the compiler must require a reason, warn in generated metadata, and still pass output through the existing sanitizer.
  • Use source-by-extension authority. When <slug>.markdoc exists, agents edit that source and treat <slug>.html as generated review output. When only <slug>.html exists, the HTML remains the authoritative source. Repo guidance and product intent must be updated in this plan to prevent agents from hand-editing generated HTML.
  • Fail closed before overwriting legacy HTML. Compiling or registering <slug>.markdoc must not overwrite an existing <slug>.html unless that HTML is already marked as generated from the same Markdoc source or the operator uses an explicit migration/force path. The error must explain whether to choose a different slug, migrate intentionally, or keep the HTML-only plan authoritative.

Acceptance criteria

  1. A new .markdoc plan can be compiled into a dark-mode semantic HTML plan with generated ToC, stable IDs, progress checkboxes, phases, acceptance criteria, BDD scenarios, verification strategy, and decisions log.
  2. The compiler validates required plan structure and reports actionable errors for missing IDs, missing phase subblocks, unmatched progress/phase mappings, unsafe raw HTML escape hatches, and unsupported attributes.
  3. Registering a Markdoc source produces or refreshes the generated HTML artifact and then follows the same plan-review register ... --execution-ready false path as HTML.
  4. Existing raw HTML plans under thoughts/plans/*.html remain registerable without conversion.
  5. Representative corpus features are covered: progress lists, complex tables, code blocks, image figures, Mermaid source blocks, rich UI mockups, stable IDs/classes/data/ARIA attributes, and scoped styling.
  6. MDX is documented as a future trusted-component lane with explicit concerns and non-goals, not implemented as the default authoring format.
  7. Compiler and registration failures preserve the last good rendered plan and explain the next safe action to an agent.
  8. Compiling or registering <slug>.markdoc refuses to overwrite an existing non-generated <slug>.html unless an explicit migration or force path is used, preserving historical HTML plans and unrelated user edits.

BDD scenarios

BDD-1: Agent registers a compact Markdoc plan

Given an agent authored thoughts/plans/example.markdoc with required frontmatter and phase tags, when it runs plan-review register thoughts/plans/example.markdoc --repo auto --branch auto --commit auto --execution-ready false --json, then the CLI compiles thoughts/plans/example.html, registers that HTML, reports source sync truthfully, and returns normal agent instructions.

BDD-2: Missing phase contract fails before registration

Given a Markdoc plan phase omits testsFirst or verify, when the agent compiles or registers it, then the command fails before replacing the last good generated HTML and prints the exact phase ID, missing field, and fix pattern.

BDD-3: Historical HTML plan still registers

Given an existing completed plan such as thoughts/plans/queue-backed-agent-next.html, when an agent registers the HTML path, then the current HTML registration behavior remains unchanged and no Markdoc conversion is required.

BDD-4: Rich mockup survives with stable review targets

Given a Markdoc figure contains a structured mock or approved raw HTML block with nested controls and ARIA labels, when it compiles, then the generated HTML preserves commentable IDs/classes/ARIA/data attributes that are allowed by the sanitizer and still receives data-plan-node-id values.

BDD-5: MDX source is not silently executed

Given an agent tries to register thoughts/plans/example.mdx, when MDX mode has not been explicitly implemented and enabled, then the CLI rejects it with a message explaining that MDX is reserved for a future trusted-component mode and suggests Markdoc or HTML.

BDD-6: Markdoc compile cannot clobber legacy HTML

Given thoughts/plans/example.html exists and is not marked as generated from thoughts/plans/example.markdoc, when an agent compiles or registers thoughts/plans/example.markdoc, then the command fails closed before writing HTML and explains how to choose a different slug, run an explicit migration, or keep the existing HTML as authoritative.
