Review Shell Flash and Scroll Regression Plan

Plan after exploratory UI testing of the plan-reviewer shell: every major shell button, plan-to-plan navigation, comments, navigator refresh, desktop/WebKit wheel scrolling, and mobile/coarse scroll ownership.

Goal

Make plan-reviewer feel stable while reading and reviewing plans: no navigator content flash after switching plans, no first-scroll no-op/bump in the rendered plan area, and no untested scroll-blocking paths on adjacent UI surfaces. Lock these behaviors with e2e coverage so regressions fail before release.

Solution narrative

There are two root causes to address. First, the left navigator is rendered twice with different display logic: server first paint uses human readiness/progress labels, then the async client refresh rewrites the same items with raw Kanban column keys. That produces the visible flash. Second, WebKit can still lose the first tiny wheel/trackpad input when it follows a pending or freshly scheduled shell scroll. Existing tests wait for the programmatic scroll to settle, so they miss the user path where input arrives immediately.

The fix should create one source of truth for navigator display fields and add explicit e2e tests for visual stability across the async refresh. For scrolling, add a red WebKit reproduction that wheels immediately after the shell performs any programmatic scroll/restore, then replace the global window.scrollTo monkeypatch with narrowly scoped, deterministic scroll restoration that cannot leave a pending rAF scroll competing with real user input.

Current implementation reality

  • The server-rendered navigator uses planNavigatorStatus(), which prioritizes sync attention, completion, collaboration, and execution readiness. It does not display board column keys for active plans.
  • The client re-render uses planItemStatus(), which displays boardColumnKey before completion/execution readiness for active plans. That makes the async refresh visibly disagree with first paint.
  • The review shell currently has passive touch observers for the main plan/touch-layer path and mobile/coarse synthetic scroll behaves correctly in Chromium/WebKit diagnostics.
  • The desktop shell wraps window.scrollTo globally in requestAnimationFrame. That is a broad primitive override and is exactly the kind of hidden scroll state that can race real input.
  • Index/archive/deferred generated scripts still include older touchstart dismissal listeners outside the previous review-shell scroll fix scope.

Product intent alignment

This plan cites thoughts/specs/product_intent.md. It supports the product intent that a reviewer can open a plan, read it, annotate it, and hand work to agents without fighting the UI. Scroll and navigator stability are part of the golden path, not polish: a reviewer spends most of the session reading, switching plans, and leaving comments.

  • Simple browser review: plan navigation and scrolling should feel native and deterministic.
  • Safe defaults: no hidden global scroll monkeypatch should compete with user input.
  • Regression strategy: user-reported interaction regressions become Playwright e2e tests with artifacts and clear failure messages.
  • Operator experience: the fix should reduce visual churn and make failures obvious to developers before they reach the browser review workflow.

Progress

Locked decisions

  • Keep native scrolling. Do not reintroduce manual wheel/touch scrollBy emulation.
  • One navigator display source. First paint and async refresh must use the same display semantics.
  • Avoid global primitive overrides. Do not globally replace window.scrollTo; use named helpers at the call sites that need scroll preservation.
  • Test representative UI controls. Repeated list buttons can be sampled, but every distinct visible control type should be inventoried and covered.
  • Keep evidence attached. Repro JSON, traces, and recordings remain linked from the plan until the tests are merged.

Acceptance criteria

  1. Plan navigator text, active item, and item order remain stable from first paint through async navigator refresh when the backing data did not change.
  2. Human labels are shown consistently: no raw backlog, in_progress, or done keys appear in the review-shell navigator when column labels are configured.
  3. In WebKit, the first wheel/trackpad input after shell navigation or programmatic scroll restoration moves the native scroll owner by the input delta; a second input is not required.
  4. Desktop wheel input scrolls the window/document and keeps iframe internal scroll at 0; mobile/coarse input scrolls #review and keeps window/iframe internal scroll at 0.
  5. Touch observers that only dismiss UI or observe taps are explicitly passive on review, index, archive, deferred, and Kanban surfaces.
  6. Comment create, cancel, submit, plan note, execution review request, build request, archive/undo, defer/resume, pin/unpin, comments toggle, navigator toggle, current-status change, quick-open, and configuration saves continue to work without unexpected reloads or visual flash.

BDD scenarios

BDD-1 — Navigator refresh does not flash

Given a plan is loaded with the navigator open, when the async navigator refresh completes, then each visible item keeps the same human status label and the active item remains highlighted without a transient raw-column state.

BDD-2 — Plan-to-plan click stays visually stable

Given the reviewer clicks another plan in the left navigator, when the destination plan first paints and the client refreshes navigator data, then the navigator does not flash to different labels or ordering unless server data changed during the click.

BDD-3 — First WebKit wheel after scroll restoration moves

Given the desktop shell has just restored or set scroll position, when the reviewer immediately performs one small wheel input over the rendered plan, then the native scroll owner moves beyond the restored position and the iframe internal scroll remains zero.

BDD-4 — Mobile/coarse scroll remains native

Given a mobile/coarse review shell with the touch layer over a long plan, when the reviewer scrolls down and reverses up, then #review.scrollTop changes on the first gesture in each direction, the composer stays closed, and iframe/window scroll remain zero.

BDD-5 — Representative controls do not regress

Given the copied database contains active, deferred, archived, and configurable plans, when the e2e control inventory clicks each distinct visible control type, then expected controls mutate in place or navigate intentionally, and no unexpected reload/flash is recorded.
