Plan viewer controls for navigator filters and current-plan status

Move plan-list filter selectors into the left navigator, stacked vertically, and reserve the top plan bar for controls that mutate the current plan. Add a current-plan status selector there while keeping state and project changes out of top-level selectors.

Status: execution-ready Linear: none — user-requested local plan UI impact: yes Artifact: thoughts/plans/current-plan-status-controls.html

Status

This plan is execution-ready. Browser feedback has been integrated, independent GPT and GLM readiness reviews cleared the latest material edit, and the plan has been re-registered with truthful execution-ready metadata.

Goal

When viewing a registered plan at /p/:planId, the UI should clearly separate two jobs:

  • Left navigator filters choose which plans appear in the left navigation list.
  • Top current-plan controls change settings for the open plan.

The current-plan controls include a status selector for the plan board column. They do not include state or project selectors because state remains covered by Defer / Resume / Archive / Restore buttons and project assignment is intentionally not introduced in this slice.

Decision Attention / Low-confidence Areas

No product decision required before browser review.

Reviewer feedback resolved the implementation detail: split navigator filters and current-plan settings into explicit components/helpers instead of stretching the existing inline .filter-control markup. This keeps the DOM semantics and client wiring simpler while preserving the same product scope.

Solution narrative

The plan viewer currently places project, state, and status filter selectors in the sticky top bar alongside plan actions. This makes filter selectors look like current-plan settings. The target design makes the top bar action-oriented and moves filter criteria into the left navigator where their effect is visible.

The left navigator gets a compact filter stack above the plan list: Project, State, and Status. The current plan bar gets a status selector labeled as a current-plan setting, backed by the existing board-column API. Existing state buttons remain in place and continue to reflect archived/deferred/active lifecycle behavior.

Current implementation reality

  • reviewShell() builds organizationControls from pin, project filter, state filter, and status filter, then injects them into #plan-navbar-actions.
  • planNavigatorHtml() renders only the navigator header, retry/error area, and plan list items; it has no filter-control slot today.
  • Client code already reads projectFilterControl, stateFilterControl, and statusFilterControl, updates URL query parameters, reloads navigator items, and preserves filters while switching plans.
  • The API already supports plan status mutation through PUT /api/plans/:id/column and the store validates visible board columns.
  • E2E coverage already exercises filter persistence and archive/defer lifecycle behavior, so this work should adjust coverage rather than invent a parallel workflow.

Product intent alignment

This plan advances thoughts/specs/product_intent.md by making browser plan status and controls more truthful and obvious. It keeps the plan file authoritative, avoids introducing a document editor, and maintains parity across UI/API/tests for plan lifecycle and board-column status.

  • Obvious workflow: filter criteria live where filtered plans are shown; current-plan status lives with current-plan actions.
  • Truthful status: status selector changes the existing board-column status and updates visible metadata without implying execution readiness changes, including when the current saved column is hidden from normal board choices.
  • Safe failure: failed status updates restore the previous selector value and show actionable inline/toast guidance rather than leaving stale UI.
  • Boundary: no authentication, queue, source-sync, or rendered-plan safety behavior changes.

Locked decisions

  • Navigator filter controls move into #plan-list-nav above #plan-list-items and stack vertically.
  • Navigator filters and current-plan settings use separate rendering helpers/components rather than one overloaded inline control helper.
  • The filter controls retain their current IDs unless tests prove a compatibility-safe replacement is needed: project-filter-control, state-filter-control, and status-filter-control.
  • The top bar current-plan status selector uses a distinct label/ID from the navigator status filter, such as current-plan-status-control, and maps to PUT /api/plans/:id/column.
  • If the current plan is assigned to a hidden board column, the selector must truthfully show that current saved status as a disabled or otherwise non-selectable current option, while update choices remain limited to visible board columns accepted by PUT /api/plans/:id/column.
  • No top-bar selector is added for lifecycle state or project. State remains button-driven; project assignment remains out of scope for this slice.
  • Collaboration documents do not receive planning status controls; planning-only status remains board-column based.
  • Mobile/coarse-pointer behavior stays conservative: do not expose left-nav-only filters in an unreachable hidden navigator.

Acceptance criteria

  1. On desktop plan pages, Project / State / Status navigator filters appear at the top of the left plan navigator, stacked vertically, and no longer appear in #plan-navbar-actions.
  2. Changing any navigator filter preserves existing URL query semantics, reloads navigator items, and keeps filtered plan navigation links carrying the filter query.
  3. On planning-mode plan pages, the top bar includes a current-plan status selector populated from visible board columns, plus the open plan's saved current board column when that current value is hidden.
  4. Changing the current-plan status selector calls the existing board-column update API, updates the visible selector and navigator item metadata on success, and restores the previous value with actionable error text on failure.
  5. When a plan's saved board column is hidden, the selector truthfully displays that hidden current status but does not offer it as an update target; visible update choices still use the API-accepted visible columns.
  6. No current-plan state or project selector is added to the top bar; existing Defer / Resume / Archive / Restore buttons continue to own lifecycle state changes.
  7. Collaboration-mode documents omit planning-only current-plan status controls while keeping document navigation and comments usable.
  8. Keyboard labels, ARIA names, and focus order distinguish navigator filters from current-plan settings.
  9. Existing archive/defer, quick-open, comments, source-sync, and plan frame behaviors do not regress.

BDD scenarios

Navigator filters are visually and semantically scoped to the left nav

Given a user opens a planning plan on desktop, when the shell renders, then Project, State, and Status filter selectors are stacked above the left navigator list and the top bar contains no filter-labeled controls.

Filters still drive navigator list membership

Given a project filter excludes a plan, when the user changes Project to All projects, then the navigator reloads with matching plans and links preserve the filter query while switching plans.

Current-plan status update succeeds

Given the current plan is in Backlog, when the user selects In progress from the top status selector, then the app sends PUT /api/plans/:id/column, keeps the selector on In progress, and updates navigator metadata for the current plan.

Current-plan status update fails safely

Given the status update API returns an error, when the user selects a new status, then the selector returns to its previous value and displays guidance that the status was not changed and the user can retry.

Hidden current status remains truthful

Given the current plan is assigned to a hidden board column, when the plan page renders, then the top status selector displays the hidden saved status as the current value while offering only visible board columns as selectable update targets.

Lifecycle and project controls do not expand scope

Given a user views an active plan, when they inspect the top bar, then they can use Defer and Archive buttons for state but cannot change lifecycle state or project through selectors.

Collaboration documents avoid planning status controls

Given a collaboration document is open, when the shell renders, then no current-plan status selector is present and existing document actions remain usable.

Mobile does not depend on hidden navigator filters

Given a coarse-pointer/mobile viewport hides the left navigator, when the plan page loads, then the rendered plan and comments remain usable and no required current-plan action is hidden only inside the navigator.
