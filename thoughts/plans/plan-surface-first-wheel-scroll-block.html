Goal

Make the first scroll input work identically whether the cursor is over the rendered plan or over the left plan navigator. The fix must preserve native browser scrolling, keep iframe internal scroll at zero on desktop, and keep the mobile/coarse pointer touch-layer behavior that already scrolls #review natively.

Decision Attention / Low-confidence Areas

No product decision required. The intended behavior is clear: a reading surface must never require a sacrificial first scroll. Native capture proved the cursor-location difference comes from wheel events targeting the rendered-plan iframe, which had a fractional internal scroll range; the left navigator is parent-page DOM and does not enter that iframe scroll-latching path. Playwright synthetic wheel coverage remains a guard, but the decisive regression contract is that iframe sizing must round up fractional rendered document height rather than relying only on integer scrollHeight.

Why this plan exists

This is the fifth scroll regression pass. Prior tests proved pieces of the behavior, but they did not isolate the cursor-location and direction-change matrix the user just described: first wheel over the plan fails once, continued same-direction wheels work, changing direction requires another sacrificial first wheel, and first wheel over the left navigator does not show the reset. This plan makes that matrix the primary regression contract and records installed-service smoke as a release/deploy follow-up, not a pre-PR source gate.

Current implementation reality

  • Desktop review shell scroll owner is the outer window/document. The iframe content is same-origin and kept from accumulating internal vertical scroll; tests assert iframe contentWindow.scrollY === 0.
  • The left navigator is normal parent-page DOM in #plan-list-nav. It is sticky and independently scrollable, and it is never covered by the plan touch layer.
  • The rendered plan area is an iframe plus an absolutely positioned sibling #plan-touch-layer. On desktop the layer is normally hidden, but armPostProgrammaticScrollWheelHandoff() temporarily sets display:block and pointer-events:auto for 120ms after restoreShellScroll().
  • The temporary layer has a wheel handler that only proxies horizontal deltas over wide iframe-local regions. For vertical wheel deltas it returns without preventing default or manually scrolling.
  • A window capture listener clears the handoff layer on the first wheel/pointer/mouse event, but that happens after the browser has already hit-tested the event against the layer.

Why behavior differs by cursor position

Confirmed root cause: the rendered plan crosses an iframe boundary that the left navigator does not. Native capture showed wheel events delivered inside the iframe while the desktop touch layer was inactive. Because the iframe was sized from integer scrollHeight while rendered content extended by a fractional amount, the iframe had a tiny internal scroll range; WebKit/Brave latched the first physical wheel events to that iframe before chaining to parent window scroll.

Cursor over left navigator
Wheel target is navigator/window parent-page DOM. No iframe scroll latch. First input scrolls.
Cursor over rendered plan
Wheel target enters the iframe. A fractional internal iframe scroll range can swallow first-direction input before parent scrolling chains.

This explains why the bug feels directional and one-shot: it is not a persistent broken scroll state. It is the first event of a newly latched wheel sequence over the rendered-plan boundary being consumed before native parent scrolling receives the delta. Continued same-direction scrolling stays latched and works; reversing direction starts a new latch and repeats the loss.

Captured repro update: physical trackpad input on Security-Critical Remediation Inventory and Execution Plan produced wheel events inside the iframe, not the parent page. The touch layer was display:none and pointer-events:none throughout. The iframe reported a fractional internal scroll position (0.5) and parent window.scrollY stayed unchanged for the first 20–24 wheel events of each new direction before chaining to the parent. Evidence summary: thoughts/validation/scroll-block/repro-iframe-fractional-wheel-summary.json.

Target state

On desktop, vertical wheel/trackpad input over the plan must remain native from the browser's perspective. The iframe must have no vertical internal scroll range, including subpixel/fractional range, so wheel latching chains directly to the parent window on the first event in either direction. The desktop touch layer must remain inactive for normal vertical scrolling; the captured bug was not caused by that layer, so this implementation leaves the existing overlay handoff alone and instead removes the fractional iframe scroll range.

Product intent alignment

This plan advances the product intent that browser review is the golden path. Reviewers spend most of the session reading plans; a first-scroll bump undermines trust more than a missing advanced feature. The plan keeps the system's safe default as native browser scroll, avoids custom scroll physics, and adds regression tests centered on the exact human workflow rather than internal helper behavior.

Locked decisions

  • Native scroll only. Do not reintroduce JavaScript vertical wheel/touch scroll emulation.
  • Cursor-location parity is required. Tests must compare first scroll over the plan and over the left navigator in the same scenario.
  • No desktop vertical wheel swallowing. The plan touch layer may remain for mobile/coarse tap handling and for the existing short post-programmatic handoff window, but it must not prevent/default-swallow vertical wheel input; the first vertical wheel must move parent scroll and leave iframe internal scroll at zero.
  • WebKit is required. Chromium alone is not acceptable because prior evidence showed Chromium masks this class of bug.
  • Installed service smoke is release/deploy validation. The pre-PR source gate is contract/e2e plus native repro evidence. Homebrew-served smoke remains tracked by scripts/record-current-viewer-wheel.sh and this validation record for the next deploy/release check.

Acceptance criteria

  1. After a fragment link click, comment jump, render refresh, or same-session direction reversal, the first small WebKit wheel over the rendered plan changes the desktop native scroll owner in the requested direction; a second wheel is not required.
  2. The same first-wheel scenario passes with the cursor over #plan-list-nav and over the rendered plan surface; neither path records a swallowed first input.
  3. On desktop, normal vertical wheel input over the rendered plan is not swallowed: the existing short post-programmatic handoff layer may appear, but it must not prevent the first vertical wheel from moving parent scroll or leave iframe internal scroll nonzero.
  4. Desktop vertical wheel scrolls window and leaves iframe internal scroll at 0; mobile/coarse touch scrolls #review and leaves window/iframe internal scroll at 0.
  5. Horizontal wheel/gesture behavior for iframe-local wide regions such as tables, code blocks, figures, and Mermaid diagrams still works where currently supported.
  6. Click/tap to open the composer, text selection adoption, fragment-link navigation, comment jumps, live render refresh, and marker reflow continue to work.
  7. Release/deploy follow-up: the installed Homebrew service at 127.0.0.1:4317 should be smoke-checked with scripts/record-current-viewer-wheel.sh before promoting the fixed client.

Given the same post-navigation state, when the pointer is over the left navigator and the user sends one small wheel delta, then the navigator/window scroll behavior is not blocked and no plan touch-layer target is observed.

BDD-3 — Rendered iframe has no fractional vertical scroll range

Given a desktop rendered plan whose content has fractional layout height, when the shell sizes #plan-frame, then the frame height is rounded up to cover the rendered document rect and iframe internal scroll remains zero during vertical wheel input.

Given a mobile/coarse review shell with the touch layer over a long plan, when the reviewer finger-scrolls down and reverses up, then #review.scrollTop changes on the first gesture in each direction and the composer stays closed.

BDD-5 — Wide content remains locally scrollable

Given a wide table or code block inside the rendered plan, when the user performs a horizontal wheel/gesture over that region, then the wide region scrolls horizontally without blocking vertical document scroll elsewhere.

Verification strategy

The regression strategy is deliberately stricter than prior passes:

  1. Native repro first: capture the cursor-location plus direction-change first-wheel matrix with physical macOS trackpad input. The captured run is saved in thoughts/validation/scroll-block/repro-iframe-fractional-wheel-summary.json.
  2. Target the cause: assert iframe height covers fractional rendered document height and iframe internal scroll remains zero for vertical wheel input.
  3. Prove the first event: assert the first wheel moves; do not accept tests that pass only because a second wheel moves.
  4. Keep old protections: run existing mobile/coarse, horizontal wide-region, fragment-link, composer, marker, and source-refresh coverage.
  5. Release/deploy follow-up: repeat the passive native-input recorder against the installed service before promoting a Homebrew-served build.

Delivery order

  1. Capture native-input cursor-location evidence, then keep the Playwright WebKit cursor-location matrix as a guard.
  2. Round iframe sizing up to the fractional rendered document height.
  3. Run and preserve mobile/horizontal/comment-flow coverage.
  4. Track installed-service first-wheel smoke as release/deploy validation using the passive recorder.
  5. Run scoped review and only then mark the source gate complete.

Non-goals

  • No redesign of the review shell, navigator, comments tray, or plan rendering model.
  • No custom vertical scroll physics.
  • No queue/comment lifecycle changes.
  • No migration away from iframe-rendered plan content.
  • No broad rewrite of the e2e fixture beyond the focused cursor-location and installed-service probes.
