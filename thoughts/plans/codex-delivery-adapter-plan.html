Solution Narrative

Add a first-party delivery-adapter path inside plan-reviewer, with Codex as the first concrete adapter rather than the only possible destination. Browser comments stay durable in the existing queue, and that queue remains the canonical arbitration point across manual agent next listeners and automatic delivery workers. When a plan has an explicit Codex target and delivery is enabled, comment creation also records one generic delivery outbox row. A background worker must win the same authoritative comment claim as every other consumer before it sends a deterministic prompt to the configured Codex thread; if another listener claims or resolves the comment first, the outbox row records that external outcome instead of duplicating delivery. If delivery fails, the worker releases any active claim when safe, records visible failure state, and leaves the existing agent next manual path intact.

Goal

When a reviewer leaves a browser comment on a registered HTML plan, plan-reviewer should be able to deliver that comment to configured agent channels without asking agents to poll on a timer and without creating a plugin surface. The first implementation targets Codex, but the service remains the durable queue owner and should arbitrate all consumers through the existing claim lifecycle. Codex receives one explicit prompt only after it wins the claim for a real pending comment.

Token behavior No heartbeat turns that say “nothing new.” A background worker sleeps outside Codex and starts a turn only after a comment is pending and claimable.
Queue authority Keep the existing at-least-once queue, claim, lease, ack, release, and resolve semantics in PlanReviewStore.
User control Delivery is opt-in per plan. The target Codex thread is explicit registration metadata, not guessed from the currently open UI.
Channel parity Automatic delivery workers and manual listeners compete through the same queue claim path; whichever claims first owns that comment, and every delivery channel reflects the resulting state.

Product Intent Alignment

This plan advances the product intent by making browser comments durable, queue-visible, recoverable, and deliverable to agents without heartbeat polling. It preserves the existing desired outcome that agent next remains the correctness-critical manual delivery path while adding an opt-in automatic adapter path for comments that should wake a configured agent thread. Codex is the first adapter because it is the current request target, not because the queue lifecycle is Codex-specific.

  • Queue state remains canonical server state; every delivery worker uses claimComments, ackComment, releaseComment, and optional resolveComment instead of bypassing lifecycle semantics.
  • Manual listeners and automatic delivery channels are parallel consumers of the same queue, not separate sources of truth. A comment claimed by one consumer must be visible to the other channels as already claimed, delivered, resolved, or externally handled.
  • Delivery is disabled by default and requires an explicit target thread id, matching the product boundary that the MVP is unauthenticated and trusted-network only.
  • Recoverable Codex transport failures are visible through API/CLI status and retry controls; manual agent next remains available when automatic delivery is unavailable.
  • API, CLI, README, fixture tests, and contract tests must describe the same lifecycle semantics before the plan can be complete.

Locked Decisions

  • Adapter framework, Codex first. The storage and worker lifecycle should be adapter-neutral enough to support parallel channels later, while this plan implements only the Codex adapter.
  • No plugin for v1. A plugin would package behavior after the fact, but it does not add the event-driven wakeup primitive.
  • Explicit target thread id. Registration or a follow-up command must specify the Codex thread using the public field name threadId. The target-management CLI uses --thread; the existing register command uses a Codex-scoped convenience flag --codex-thread so registration flags remain unambiguous next to other metadata. The service must not infer “active session” from UI state.
  • Outbox pattern. Browser comment creation stores the comment and delivery intent, then returns immediately. Delivery happens in a background worker.
  • One comment per Codex turn. Preserve small reviewable work units and avoid long-lived claim batches.
  • Delivery artifact is a normal Codex turn prompt, proven by Phase 0. The v1 artifact is not a Codex plugin, generated polling script, or long-lived Codex connection. The plan-reviewer service waits for comments outside Codex; only after it claims one comment does it resume the target thread and submit one ordinary text-input turn containing the comment payload, plan context, and ack guidance. Phase 0 proved this works through both SDK and app-server transports.
  • Use text prompt input for v1. Pass the browser.comment.v1 payload as formatted JSON inside a normal Codex turn. Do not depend on experimental raw item injection for v1.
  • Verify SDK thread identity. Phase 0 showed resumeThread("not-a-real-thread-id") can start a new SDK thread instead of failing. The adapter must compare the observed thread id with the configured threadId and fail closed before acking if they differ.
  • Use controlled Codex config. Phase 0 showed unrelated user plugin/MCP configuration can break or contaminate transport runs. Delivery mode must provide a controlled config surface and disable unrelated connectors/plugins unless explicitly allowed.
  • Serialize per target thread. Phase 0 showed app-server can accept a second turn/start while another turn is active. The worker must enforce one in-flight delivery per target thread instead of relying on Codex to reject concurrency.
  • Disabled by default. A stored target does not imply automatic delivery unless the plan target is enabled and the service worker is enabled by config.
  • Enablement backfills pending comments. When delivery is enabled for an adapter, the service enqueues delivery rows for currently pending, unclaimed comments by default so operators do not need to rediscover old browser feedback. It must not enqueue already acknowledged, resolved, deleted, or actively claimed comments.
  • Visible failure over silent retry loops. Failed delivery is stored and exposed in CLI/API so operators can retry, release, or switch to manual delivery.

Architecture

Delivery flow
Browser comment POST
  -> PlanReviewStore.createComment(...)
  -> comment.created event
  -> AgentDeliveryOutbox row queued for adapter="codex"
  -> DeliveryWorker wakes inside plan-reviewer; Codex is not connected yet
  -> worker attempts the same queue claim as manual listeners
  -> PlanReviewStore.claimComments(planId, { mode: "selected", commentIds: [commentId], leaseSeconds })
  -> if claim is unavailable, mark row externally_claimed / externally_acknowledged / externally_resolved / externally_deleted as appropriate
  -> CodexClient.resumeThread(threadId) only after the claim succeeds
  -> CodexClient.run(one-shot prompt containing browser.comment.v1)
  -> store adapter_turn_id/result_json before acking
  -> PlanReviewStore.ackComment(commentId, { claimId, action: response metadata })
  -> if ack fails after Codex completion, retry ack without starting another Codex turn
  -> optional resolve based on configured policy or explicit Codex result

Outbox State Machine

Status Meaning Next statuses
pending Delivery target exists and a comment is waiting to be processed. claiming, paused, failed
claiming Worker selected the row and is attempting an authoritative queue claim. delivering, pending through stale-claiming recovery, externally_claimed, externally_acknowledged, externally_resolved, externally_deleted, retry_wait, failed
delivering Active claim exists and Codex turn is being started or is running. ack_pending, retry_wait, pending through stale-delivering recovery when no Codex result exists and the claim is expired/lost, externally_claimed, externally_acknowledged, externally_resolved, externally_deleted, failed
ack_pending Codex completed and result metadata is stored, but the queue ack has not succeeded yet. delivered, ack_failed, externally_acknowledged, externally_resolved, externally_deleted
delivered The configured adapter accepted and completed the turn; ack succeeded. resolved when auto-resolve is enabled and resolution succeeds.
resolved Auto-resolve was enabled, the adapter result explicitly indicated the feedback was fully addressed, and resolveComment succeeded. Terminal.
retry_wait Transient failure; the row is scheduled for a later attempt and any active claim has been released if possible. pending, failed
ack_failed Codex completed, but ack failed or the claim expired/lost before ack. The row keeps adapter_turn_id and result_json and must not start a duplicate Codex turn automatically. delivered through ack retry while claim is valid, failed when manual intervention is required.
failed Permanent failure or retry limit exceeded; requires operator action. pending through explicit retry, or manual queue processing.
externally_claimed Another queue consumer claimed the comment before this adapter won the claim. Terminal for this adapter unless an operator explicitly retries after the comment returns to pending.
externally_acknowledged Another queue consumer acknowledged the comment before this adapter delivered it. Terminal.
externally_resolved Another queue consumer resolved the comment before this adapter delivered it. Terminal.
externally_deleted The comment was deleted before this adapter delivered it. Terminal.
paused Delivery disabled after row creation. pending after re-enable.

Codex Prompt Contract

The Codex-facing delivery artifact is a deterministic text prompt submitted as a normal Codex turn through the SDK or app-server transport. Phase 0 proved this path with throwaway SDK and app-server threads. It is not a Codex plugin, not a generated polling script, not a long-lived Codex wait loop, and not raw experimental item injection. The prompt must be self-contained and explicit about ack behavior, and it should not rely on hidden session state beyond the target Codex thread history.

How the prompt is used

Codex never sits open waiting for comments. The always-on component is the plan-reviewer delivery worker, which sleeps in the service process using database/SSE/interval wakeups. When a browser comment is created, the service persists it, queues a delivery row, and the worker tries to claim that exact comment. Only after the claim succeeds does the worker create a short-lived Codex interaction by resuming the configured thread and submitting this prompt once. The Codex turn handles that one comment and exits; the service then acks, resolves, retries, or records failure based on the turn result.

Ack policy

The first backend version should ack only after the Codex turn completes and the worker can derive a non-empty final response. The service should not auto-resolve unless a per-plan setting enables it and the response explicitly indicates the issue is fully addressed.

Security and Operational Risks

Unauthenticated local service

The current README states the MVP has no authentication. Codex delivery turns comments into agent actions. Keep delivery disabled by default and bind service usage to loopback or a trusted network until authentication exists.

  • Prompt injection: Treat browser-authored comment bodies and plan HTML as untrusted input. The delivery prompt should constrain Codex to the registered plan and comment.
  • Thread targeting: A wrong thread id can send feedback to unrelated work. Show thread id clearly in target config and require explicit operator action to enable it.
  • Lease expiry: Codex turns can exceed the default 5-minute lease. Use a longer delivery lease and release on failure. Consider a future lease-renew endpoint if long turns are common.
  • SDK/app-server maturity: App-server is documented as experimental. Keep the adapter isolated and make failures recoverable through the existing manual queue path.
  • Duplicate delivery: At-least-once semantics mean retries can happen. The prompt should include comment id and claim id, and the outbox table must enforce UNIQUE(comment_id, adapter) to prevent duplicate delivery rows per adapter while still allowing future parallel adapters.

Non-Goals

  • Do not build a Codex plugin for the first version.
  • Do not depend on private in-app annotation UI internals or active-window state.
  • Do not support cloud-hosted plan-reviewer delivery until local delivery is proven.
  • Do not batch multiple reviewer comments into one Codex turn in v1.
  • Do not let the service commit, push, or merge changes. Codex remains responsible for editing within its thread.
