Status

Execution-ready planning state

The source issue is concrete, repo surfaces are identified, and the plan locks the command shape, payload contract, queue semantics, registration-instruction change, tests, and verification gates. Implementation should start only after explicit user approval to code.

Goal

Add a first-class CLI command that waits for or checks the authoritative comment queue, atomically claims exactly one pending browser comment, prints one agent-actionable JSON payload, and exits. Registration instructions should prefer that one-shot command instead of requiring every harness to keep a long-running plan-review watch process wired into conversation notifications.

Why this plan exists

Issue #7 documents a real missed-reviewer-comment incident: plan-review watch emitted the event, but the harness-side stdout/log-watch notification path did not produce an agent turn. The queue and stream worked; the brittle contract was requiring each agent harness to translate a long-lived stream into actionable conversation state.

Product intent alignment

Golden path

After registering a plan, an agent starts a simple listener loop around one normal command: plan-review agent next <planId> --wait --json --url <service-url>. Each invocation waits internally, claims the next pending comment, returns the exact conversation payload plus claim ID, and exits. The harness acts on that payload, acks it with the returned claim ID, optionally resolves after ack, then immediately starts the same command again. This loop replaces stdout-watch plumbing while preserving continuous comment delivery.

Agent listener loop

Registration instructions must render this loop as the primary agent contract: on start or resume, run agent next --no-wait --json until it returns empty to drain pending work, then run agent next --wait --json; after every claimed result is acted on, acked with the returned claim ID, and optionally resolved after ack, rerun agent next --wait --json. If the plan-review service restarts, the active invocation retries until the service returns or the optional timeout expires; if the process exits, the harness restarts the same command and the queue/lease state determines whether work remains.

Self-healing expectation

Every loop iteration must consult queue/claim state before relying on stream sequence. In --wait mode, temporary SSE, polling, and network failures are recoverable until the command timeout expires: the command reconnects, retries the intended queue claim, and relies on current queue state rather than any missed event. If a previous process exited or missed notification, rerunning the command should be safe because expired claim leases return comments to pending and the command claims from the authoritative queue.

Fail-closed boundary

The command must not auto-ack or auto-resolve. In --no-wait mode, service unavailability fails immediately with an actionable error. In --wait mode, transient service unavailability is retried until --timeout; only an expired timeout, unknown plan, validation failure, or unsafe claim conflict stops the command.

Locked decisions

  • Command shape: implement plan-review agent next <planId> --wait|--no-wait --json --url <service-url> [--lease-seconds <seconds>]. --json is required for agent next in this issue; non-JSON human output is a non-goal. --wait blocks; without --wait or with --no-wait, the command performs one immediate queue claim attempt and exits. Passing both --wait and --no-wait, a non-positive/non-integer --timeout, or a non-positive/non-integer --lease-seconds is validation_failed and exits 2. --lease-seconds passes through to the existing claim API and defaults to 300 seconds, matching claimCommentsSchema.
  • Wait default: --wait without --timeout waits indefinitely. --timeout <ms> is optional and bounds the whole wait, including claim attempts, reconnects, SSE reads, poll fallback, and sleeps.
  • Retry cadence: waiting mode attempts an immediate claim, then subscribes to per-plan queue-mode SSE at /api/plans/:planId/events?mode=queue when available. SSE events only wake the command to retry the authoritative claim. If SSE is unavailable or disconnects, use REST polling at /api/plans/:planId/events/poll?mode=queue every 1s initially with exponential backoff capped at 10s. Recoverable errors during --wait: network_error / HTTP 503 from temporary service unavailability. Terminal errors: not_found / HTTP 404, validation_failed, and other 4xx contract errors.
  • Claimed JSON: claimed output uses type: "plan-review.agent.next.v1", status: "claimed", planId, commentId, claimId, conversationPayload, ackCommand, resolveCommand, and resolveAfterAck: true. resolveCommand is follow-up guidance only and is valid after a successful ack, never as an alternative to ack for a claimed comment.
  • Empty JSON: non-waiting empty output exits 0 with { "type": "plan-review.agent.next.v1", "status": "empty", "planId": "..." }. If a previous claim is still active, rerunning agent next must not double-claim it; the command reports empty unless another pending comment is available. After release or lease expiry, the same comment can be claimed again through normal queue state.
  • Error output: successful --json results are JSON on stdout. Errors stay on the existing CLI PlanReviewError stderr path so this change does not create a second CLI-wide error protocol. Existing exit mapping applies: watch_timeout uses status code 1 and exits 1; API/terminal errors such as not_found 404, validation_failed, and exhausted network_error 503 exit 2. Tests must assert stderr content and these exit codes.
  • Server API: use existing claim and event/poll APIs first. Do not add a new API route unless implementation evidence shows the CLI cannot satisfy the issue’s queue-backed contract with existing endpoints.
  • Watch preservation: leave plan-review watch available and documented as optional low-latency/debug stream, not correctness-critical agent delivery.

Contract notes

The command should enrich relative conversationPayload.evidence.reviewUrl using the resolved service URL, matching current watch behavior. ackCommand and resolveCommand should include the resolved --url so the next operation targets the same service. resolveCommand must be labeled as valid only after successful ack because the current server rejects resolving a claimed comment before it is acknowledged. Error output intentionally uses the existing CLI stderr protocol; do not add a new JSON error envelope in this issue.

Acceptance criteria

  1. plan-review agent next <planId> --no-wait --json returns status: "empty" and exits 0 when no pending comment exists.
  2. plan-review agent next <planId> --no-wait --json claims one pending comment and returns commentId, claimId, and conversationPayload.type === "browser.comment.v1".
  3. plan-review agent next <planId> --wait --json --timeout <ms> blocks until a comment exists, then returns exactly one claimed comment and exits 0.
  4. The returned claimId can be passed directly to plan-review ack <commentId> --claim <claimId> ... --json.
  5. If the process exits or the agent misses its notification, rerunning the command is safe because queue and claim leases remain authoritative: active claims are not double-claimed, and released or expired claims become pending and claimable again.
  6. Registration output and agentInstructions prefer plan-review agent next <planId> --wait --json and document watch as optional.
  7. Existing plan-review watch, queue claim, ack, resolve, and registration JSON compatibility fields remain available.
  8. Harness smoke tests prove Pi, Codex, and Claude Code can each subscribe to plan comments through the registered listener loop, claim and ack incoming comments within the mode-specific budgets in #harness-evidence, survive a same-URL plan-review service restart, restart or reconnect their listener, and catch a subsequent comment without manual nudges.

BDD scenarios

BDD-1: Empty non-waiting queue

Given a registered plan with no pending comments, When an agent runs plan-review agent next <planId> --no-wait --json, Then stdout is valid JSON with status: "empty" and no claim is created.

BDD-2: Immediate pending comment

Given a registered plan with one pending browser comment, When the agent runs agent next --no-wait --json, Then the command claims that comment, returns claimId, returns the original browser.comment.v1 payload, and leaves the comment in claimed state until ack, release, or lease expiry.

BDD-3: Waiting command

Given no pending comment at command start, When agent next --wait --json --timeout 5000 is running and a reviewer creates a comment, Then the command detects queue availability, claims one comment, prints one claimed payload, and exits.

BDD-4: Missed process notification recovery

Given an earlier agent process exited or missed a harness notification, When the agent reruns agent next --no-wait --json while a prior claim is still active, Then it does not double-claim that comment. When the prior claim lease expires and claimComments() automatically releases it back to pending, Then the command uses queue state to claim the actionable comment instead of depending on prior stream sequence.

BDD-5: Wait timeout

Given no pending comment arrives before the timeout, When agent next --wait --timeout 50 --json runs, Then it exits non-zero with an actionable timeout error and does not claim or ack anything.

BDD-6: Registration guidance

Given an agent registers a plan, When the CLI human output or API agentInstructions is inspected, Then the primary command is plan-review agent next <planId> --wait --json, the resume check is --no-wait, and plan-review watch is labeled optional/debug-only.

BDD-7: Pi, Codex, and Claude Code listener recovery

Given identical registered test plans for Pi, Codex, and Claude Code, When src/test-fixtures/harness-smoke.ts runs simulated mode and real mode with the command templates in #harness-smoke-contract, Then each harness claims and acks both comments within the mode-specific budgets, acks each comment before any optional resolve, records the same-URL service restart/reconnect event, and reports zero manual interventions.
