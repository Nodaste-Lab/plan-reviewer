Toggle Plan Annotations

Add a plan-level UI control that turns browser annotation affordances on and off without hiding the comment sidebar or losing existing comments.

Goal

Give reviewers a clear annotation-target control in the plan toolbar. Annotations are enabled by default. When the reviewer turns them off, the rendered plan behaves like a normal web page: ordinary clicks do not open the composer, hover/touch selection outlines disappear, comment number badges and highlight boxes disappear, and text can be selected for copying. The sidebar can still be opened and still shows all comments.

Decision Attention / Low-confidence Areas

  • Browser feedback requested: confirm the toolbar placement and icon treatment in the mocks below before execution-ready review.
  • No product decision required: the default behavior, sidebar behavior, and document-marker behavior are specified by the user request.
  • Implementation risk to prove: mobile/coarse-pointer pass-through is coupled to #plan-touch-layer; on rebased main the layer is pointer-inert on desktop and pointer-active only in the mobile media query, so execution must include a shipped-surface e2e check that disabling annotations prevents comment creation while preserving practical scroll/link/text-selection behavior.
  • Source-authority update from main: new compact plans now prefer Markdoc, but this already-registered raw HTML plan has no sibling .markdoc and remains source-authoritative under the current legacy HTML rule.

Solution narrative

Add an Annotations toolbar toggle beside the comments control. The current shell has no dedicated annotation icon beyond the comments glyph, so use a target/crosshair glyph ⌖ in the existing icon-only toolbar style with aria-pressed="true" when annotation mode is active. Store the browser-local plan-specific state in localStorage so each plan starts on unless the reviewer turned it off for that plan.

Annotation mode becomes a single client-side source of truth. Every path that draws anchors, shows hover or active selection boxes, opens the composer from frame clicks/touches, captures text selection as a comment, proxies mobile taps, or adds marker screenshots must first check that source of truth. Turning annotations off clears visible annotation overlays immediately; turning them back on redraws current comment anchors from the already-loaded metadata.

The comment sidebar is independent. Its toggle, counts, filters, plan notes, comment rows, delete/resolve controls, and metadata polling continue to work whether annotations are on or off.

Product intent alignment

This plan advances thoughts/specs/product_intent.md by making browser review actions more intentional: reviewers can choose between precise plan commenting and ordinary document reading/copying without losing comments or agent-visible queue state. The rebased product intent also distinguishes Markdoc-authored plans from legacy HTML-only plans; this plan preserves that boundary by keeping the existing raw HTML source authoritative while requiring implementation to preserve both Markdoc and legacy HTML source-sync behavior.

  • Desired outcome: reviewers can select exact plan content when they want annotations, while plan authors and reviewers can read/copy text normally when they do not.
  • Experience principle: the golden path remains unavoidable because annotations stay on by default; turning them off is explicit, reversible, and visible in the toolbar.
  • Quality bar: browser comment interactions and rendered-plan markers change, so e2e coverage is required. Queue-backed delivery, Markdoc compilation/source sync, and legacy HTML registration remain untouched.

Locked decisions

  • Default: annotations are on when no browser-local preference exists.
  • Persistence: the preference is browser-local and plan-scoped, keyed by plan id, so turning annotations off in one plan does not silently alter every plan.
  • Control: use an icon-only target/crosshair control (⌖) in the toolbar, immediately before the comments toggle because both controls affect review/comment surfaces. Repo evidence shows no dedicated annotation icon in the current design system; the shell uses simple icon glyphs, and the target glyph better communicates click/selection targeting than the rejected fountain-pen glyph.
  • Sidebar: comment metadata and sidebar rendering are independent of annotation visibility.
  • Off state: do not render document comment anchors, labels, hover boxes, active boxes, marker screenshot badges, or new-comment composer activation from plan-body clicks/selections.
  • Server contract: no new API, CLI, schema, queue, or persisted database field is needed for this UI-only preference.
  • Plan source authority: keep this active plan as source-authoritative HTML because it predates the Markdoc-preferred mainline change, contains raw product mocks, and has no sibling Markdoc file. Future compact plans should use Markdoc; this plan should not be migrated unless explicitly approved.

Acceptance criteria

  1. The review toolbar includes an accessible Annotations icon control with the target/crosshair glyph (⌖), visible active/off state, aria-pressed, and labels that tell the user whether activating it will turn annotations on or off.
  2. A newly opened plan defaults to annotations enabled unless that browser has a stored off preference for that same plan.
  3. With annotations enabled, existing hover/click/text/image/mobile comment creation and visible comment anchors continue to work.
  4. With annotations disabled, ordinary clicks and text drags in the plan body do not open the composer, do not clear native text selection for copy, and do not show hover/active selection boxes.
  5. With annotations disabled, existing comment anchors, highlight outlines, number labels, and newly submitted marker badges are absent from the rendered document.
  6. Opening the comment sidebar while annotations are disabled still shows all comments, counts, statuses, plan notes, and existing comment actions.
  7. Toggling annotations back on redraws comment anchors from current metadata without reloading the page or duplicating comments.
  8. Links, fragment navigation, plan-shell links, wide-content scrolling, and mobile/coarse-pointer scrolling remain usable in both modes.
  9. The change is limited to the review shell UI/client behavior and does not change comment queue, ack/release/resolve, source sync, registration, or rendered-plan sanitization contracts.

BDD scenarios

Default annotation mode

Given a reviewer opens a plan for the first time, When the review shell loads, Then the target/crosshair control is pressed/on, comment anchors render, and clicking commentable plan content opens the composer.

Copy text without creating a comment

Given annotations are off, When the reviewer drags across text in the rendered plan and releases the mouse, Then the browser selection remains available for copy and the composer stays hidden.

Existing comments hidden from document only

Given a plan has pending and resolved comments with anchors, When annotations are turned off, Then the document no longer shows highlight boxes or number badges, but the sidebar still lists those comments and counts.

Re-enable annotations

Given annotations are off and the sidebar has loaded comments, When the reviewer turns annotations on, Then anchors redraw once from current metadata and clicking a normal plan target opens the composer again.

Sidebar remains useful while document annotations are hidden

Given annotations are off and comments are visible in the sidebar, When the reviewer opens or filters the sidebar, Then all comment rows and actions remain available without forcing annotations back on or drawing document badges.

Mobile/coarse pointer off mode

Given a narrow or coarse-pointer review shell, When annotations are off, Then tapping text does not create comments, comments remain visible through the tray, links still activate, scrolling still works, and text selection/copy behavior is preserved. If implementation evidence shows those cannot all hold together on a target mobile browser, stop for explicit product approval before carving out mobile text selection/copy behavior.
