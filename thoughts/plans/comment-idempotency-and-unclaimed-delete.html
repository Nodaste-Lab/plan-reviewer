Comment Idempotency and Unclaimed Delete Plan

Plan for preventing duplicate browser comments from repeated submits, detecting duplicate comment identifiers, and allowing safe deletion of unclaimed comments.

Status

Plan status: execution-ready and implemented on branch fix-duplicate-comments. Keep this artifact as the source of truth for scoped verification and review status.

Implementation status: all phases implemented; PR monitoring is active. Latest Codex PR feedback is classified as REGRESSION_FROM_THIS_DIFF and is being addressed without expanding scope.

Goal

Each browser select → comment composer cycle must create at most one comment, even when the reviewer submits repeatedly while the dialog is still open or while the service is slow. The system must detect duplicate comment identifiers, distinguish true retries from conflicting reuse, and let reviewers delete comments that are still pending and unclaimed.

Why this plan exists

When the plan service is slow or unhealthy, reviewers may press Submit multiple times before the composer dismisses. The existing backend has partial idempotency through clientMutationId, but the browser composer does not send one and the submit control is not guarded during the in-flight request. This can create duplicate agent-visible comments and duplicate queue work.

Authority and inputs

  • User request: prevent duplicate comments, assign a unique comment identifier per select → comment cycle, detect duplicate adds, and allow deletion of unclaimed comments.
  • Repo guidance: AGENTS.md requires HTML plan artifacts, product intent alignment, TDD/BDD phases, and plan-review registration.
  • Product intent: thoughts/specs/product_intent.md prioritizes durable, deduplicated comments and canonical queue state.
  • Observed files: src/server/app.ts, src/schemas.ts, src/storage/database.ts, src/cli.ts, src/__tests__/contracts.test.ts, src/test-fixtures/e2e-run.ts, and README.md.

Current implementation reality

Browser submit path

submitPendingComment() in src/server/app.ts posts versionId, body, anchor, markerScreenshot, and createdBy. It does not include clientMutationId, and the Submit button remains usable while the async request is active.

Existing idempotency hook

createCommentSchema already accepts optional clientMutationId. The database already has UNIQUE(plan_id, client_mutation_id).

Backend retry behavior

PlanReviewStore.createComment() already returns the original comment with created:false when the same clientMutationId is reused, but it does not yet reject conflicting payload reuse.

Deletion gap

There is no comment delete route, no deleted comment state, and no browser affordance to remove pending comments that have not been claimed.

Product intent alignment

  • Advances the desired outcome that review comments are durable, deduplicated, queue-visible, and recoverable across browser, CLI, service, and agent restarts.
  • Supports the simplest reviewer workflow by making repeated Submit attempts safe instead of requiring the reviewer to know whether the service accepted the first request.
  • Supports canonical server queue state by enforcing idempotency and delete eligibility in storage/API logic, not only in the browser.
  • Preserves fail-closed behavior for claimed, acknowledged, and resolved comments because deleting agent-visible work can create authority and data-loss ambiguity.

Locked decisions

  1. Each select → comment composer cycle gets one browser-generated clientMutationId.
  2. Every retry from that still-open composer reuses the same identifier.
  3. The server remains the source of truth; browser guards improve UX but do not replace server idempotency.
  4. Duplicate identifiers with materially different fingerprint payloads are rejected as conflicts. The fingerprint fields are exactly versionId, body, anchorType, and canonicalized anchor.
  5. Anchor canonicalization means comparing the JSON-safe normalized anchor value with object keys sorted recursively, array order preserved, primitive values preserved exactly, null preserved, and no anchor fields dropped. The comparison uses the stable JSON string for that normalized value.
  6. Duplicate retries ignore markerScreenshot and createdBy differences. The first successful create preserves the original screenshot asset and creator; later retries with the same fingerprint do not update stored comment fields.
  7. A duplicate POST whose clientMutationId belongs to a soft-deleted comment returns 409 duplicate_comment_deleted, emits no new event, and never recreates or undeletes the comment. Browser retry handling treats this as terminal: refresh comments/markers, dismiss any stale in-flight draft for that deleted identifier, and show a short notice if the composer is still visible.
  8. Point lookups must still be able to observe soft-deleted comments. getComment() must not filter deleted rows the way normal list/count/queue queries do; the returned shape must expose deletion state through deletedAt or equivalent so duplicate detection and selected-mode claims can fail closed instead of falling through to not-found or crashing.
  9. Only effectively pending comments with no active claim may be deleted.
  10. Deletion should be soft-delete unless implementation evidence proves hard-delete is safe for event/audit consistency.
  11. No fuzzy body/anchor dedupe; only the explicit per-cycle identifier defines idempotency.
  12. CLI comment deletion is out of scope for this plan. Recovery deletion is API/browser/README only unless a later plan identifies a concrete operator workflow gap.

Acceptance criteria

  1. Repeated button clicks from one open composer create exactly one stored comment and one queue-visible comment.created event.
  2. Keyboard submit plus button submit from one open composer create exactly one stored comment.
  3. Network/service retries using the same clientMutationId and the same fingerprint fields (versionId, body, anchorType, canonicalized anchor) return the existing non-deleted comment with created:false.
  4. The same clientMutationId with different body, anchor type, canonicalized anchor, or version is rejected with 409 duplicate_comment_conflict and an actionable nextAction; differing markerScreenshot or createdBy alone is accepted as retry noise and does not mutate the original comment.
  5. The same clientMutationId after the original comment was deleted returns 409 duplicate_comment_deleted, emits no event, and does not recreate or undelete the comment.
  6. A pending unclaimed comment can be deleted through the API and browser UI.
  7. Claimed, acknowledged, and resolved comments cannot be deleted through this feature.
  8. Deleted comments are absent from normal comment lists, listPlans() count aggregates, markers, automatic queue claims, and explicit selected-mode claims; explicit claim attempts for deleted comment IDs fail closed with 409 invalid_state while existing active-claim claim_conflict behavior remains unchanged.
  9. Deleting a comment emits a queue/all event that open pages use to refresh.
  10. Existing claim, ack, release, resolve, event replay, and source sync behavior remains unchanged for non-deleted comments. The intentionally changed existing contracts are duplicate-identifier conflict rejection for mismatched fingerprints, covered by AC-4, and deleted comments acting as terminal state for lifecycle endpoints so hidden/deleted work cannot be acknowledged, released, or resolved.

BDD scenarios

BDD-1: Repeated Submit clicks

Given a reviewer opens a comment composer for one selected DOM section
When they click Submit multiple times before the first request completes
Then exactly one comment is stored, exactly one marker appears, and later duplicate responses identify the existing comment.

BDD-2: Keyboard and button submit race

Given the composer has a valid draft
When the reviewer triggers keyboard submit and button submit for the same draft
Then both requests, if sent, use the same identifier and only one comment exists.

BDD-3: Lost response retry

Given the service stores a comment but the browser misses the response
When the browser retries the same request with the same identifier
Then the API returns created:false, the original comment ID, and no new queue event.

BDD-4: Conflicting identifier reuse

Given identifier X is already consumed by one comment fingerprint
When another request uses X with different body, canonicalized anchor, anchor type, or version
Then the API returns 409 duplicate_comment_conflict with an actionable nextAction explaining the draft ID was already consumed.
And if only screenshot or creator metadata differs, the API returns the original non-deleted comment with created:false and does not mutate the original stored metadata.

BDD-5: Duplicate retry after delete

Given a pending unclaimed comment is created with identifier X and then soft-deleted
When a duplicate POST arrives with identifier X
Then the API returns 409 duplicate_comment_deleted, emits no new event, and does not recreate or undelete the comment.
And the browser refreshes comments/markers and dismisses or notices any stale in-flight draft for that identifier.

BDD-6: Delete pending unclaimed comment

Given a pending comment has no active claim
When the reviewer deletes it
Then it disappears from comment lists, markers, counts, and queue claims, and clients refresh from a comment.deleted event.

BDD-7: Reject deleting active claimed work

Given an agent has an active claim on a comment
When a reviewer tries to delete it
Then the API returns 409 invalid_state with guidance to release, ack/resolve, or wait for lease expiry.

BDD-8: Expired claim releases before delete decision

Given a comment has a claim whose lease expired
When delete is requested
Then the store first releases the expired claim and then allows deletion because the effective state is pending and unclaimed.

BDD-9: Explicit claim of deleted comment fails closed

Given a comment was soft-deleted
When an agent or operator calls selected-mode claim with that deleted comment ID
Then the API returns 409 invalid_state, does not create a claim, and does not emit a queue event.
And this is a new deleted-ID fail-closed branch: existing selected-mode behavior for active claimed comments still returns claim_conflict, and existing non-deleted non-pending skip behavior is not broadened.

P2 Server duplicate conflict detection

End State

The API treats exact duplicate identifiers as idempotent retries and rejects conflicting identifier reuse with an actionable error.

Tests first

Add contract tests for exact fingerprint retry success, body mismatch 409 duplicate_comment_conflict, canonicalized anchor mismatch 409 duplicate_comment_conflict, version mismatch 409 duplicate_comment_conflict, actionable nextAction on each conflict, screenshot-only retry acceptance without mutation, createdBy-only retry acceptance without mutation, and no new queue event after accepted retry. Update the existing duplicate-retry assertion in src/__tests__/contracts.test.ts that currently reuses clientMutationId: 'comment-1' with a different body: the idempotent 200 created:false assertion must reuse the same fingerprint, and the different-body request must become a separate 409 duplicate_comment_conflict assertion. This is an intentional locked-contract change, not a regression.

Work

  • Ignore duplicate retry differences in markerScreenshot and createdBy; preserve the first successful comment's screenshot asset and creator without mutation.

  • Before implementing P2, grep tests and fixtures for other clientMutationId reuse so any intentionally changed duplicate-fingerprint expectations are updated in the same phase.

P3 Pending unclaimed delete API

End State

Pending unclaimed comments can be safely soft-deleted through the API. Deleted comments no longer appear in normal lists, counts, markers, or claim results.

Tests first

Add contract tests for successful pending delete, list/count/automatic-claim exclusion, selected-mode claim rejection for deleted comment IDs, active claimed deletion rejection, acknowledged/resolved deletion rejection, expired-claim release before delete, and duplicate retry after soft-delete returning 409 duplicate_comment_deleted with no new event.

Work

  • Add deleted_at to comments via migration helper.
  • Exclude deleted comments from listComments(), the inline SUM(CASE ...) count aggregates in listPlans(), queue snapshots, and automatic claim selection. Any query that treats status = 'pending' as visible or claimable must also require deleted_at IS NULL.
  • Do not filter deleted rows from getComment(). Point lookups must return soft-deleted comments with deletion state exposed as deletedAt or equivalent so duplicate detection and selected-mode claim can make deliberate 409 decisions.
  • Make selected-mode claim fail closed with 409 invalid_state when any requested comment ID is soft-deleted; do not create a claim or emit an event. This is a new deleted-ID branch only: preserve current claim_conflict for active claimed selected comments and preserve existing non-deleted non-pending skip semantics.
  • In duplicate detection, after deleted_at exists, throw PlanReviewError('duplicate_comment_deleted', ...) with status 409 and no event when the identifier belongs to a soft-deleted comment; do not recreate, undelete, or mutate the deleted original.
  • Add event type comment.deleted to schemas and event filters. Its payload must mirror existing comment lifecycle events: { eventType:'comment.deleted', planId, commentId, comment }, where comment exposes deletion state. Ensure both queue/all SSE streams and poll/replay paths accept and replay the new comment.* event without disrupting existing event replay semantics.
  • Add deleteComment(commentId) that releases expired claims before deciding eligibility.
  • Add DELETE /api/comments/:commentId in src/server/app.ts.
  • Return 409 invalid_state for active claimed, acknowledged, resolved, or already deleted comments with clear next-action guidance.

Delivery order

  1. Browser sends a stable per-composer clientMutationId and guards in-flight submits.
  2. Backend rejects conflicting duplicate identifiers.
  3. Backend supports soft-delete for pending unclaimed comments.
  4. Browser exposes delete and refreshes from delete events.
  5. Docs align with the locked API/browser lifecycle; CLI deletion remains out of scope.

Non-goals

  • No fuzzy deduplication by comment body, text selection, coordinates, or anchor similarity.
  • No deletion of active claimed, acknowledged, or resolved comments.
  • No auth or role model changes.
  • No CLI delete command in this plan.
  • No rewrite of the browser shell or agent listener architecture.
  • No change to source sync completeness rules.
