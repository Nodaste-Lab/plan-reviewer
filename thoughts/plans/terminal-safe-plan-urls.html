Terminal-safe plan review URLs

Goal: Change human-facing plan URL formatting so plan review links remain clickable when a generated plan ID ends in an underscore.

Decision Attention / Low-confidence Areas

None blocking. Repo evidence points to a display-formatting fix. The plan intentionally does not change generated ID semantics or route identity.

Why this plan exists

Plan IDs are generated with nanoid(12) and prefixed with strings such as plan_. Nanoid's default alphabet can produce an underscore as the final random character, creating URLs such as http://127.0.0.1:4317/p/plan_abc_. Current human CLI output prints those URLs naked, so some terminal linkifiers stop before the trailing underscore and open .../plan_abc, which is a different plan ID and breaks the link.

Solution narrative

Add a small terminal-display formatter for human output that renders user-facing plan URLs as angle-bracketed links, for example <http://127.0.0.1:4317/p/plan_abc_>. The visible token no longer ends with an underscore, and common terminal linkifiers include the full URL inside the brackets. Keep machine-readable JSON, stored review URLs, API payloads, route paths, and existing plan IDs unchanged.

The implementation should apply this formatter anywhere the CLI prints a plan review URL for humans, especially registration output and index/list output. Commands that carry only a service base URL in --url do not need plan-link wrapping unless they add a full plan URL later.

Product intent alignment

This plan advances thoughts/specs/product_intent.md outcomes for stable URLs, minimal hidden state, and copy-paste-ready command output. It keeps the simplest reviewer workflow intact: register a plan, open the printed review URL, and comment. The safe default is to fix terminal-visible formatting where the failure appears rather than changing record identity or routing semantics.

Locked decisions

  • Display-layer fix: Human-facing plan URLs printed in terminal contexts are wrapped in angle brackets.
  • Machine contracts unchanged: JSON/API values such as reviewUrl, agentInstructions.reviewUrl, and conversation payload evidence remain plain URLs/paths without brackets.
  • No ID alphabet migration: Do not change nanoid alphabet or stored ID formats. That would not repair existing affected links and would affect every ID prefix, not just plan URLs.
  • No trailing-slash route change: Do not make /p/:planId/ the canonical URL solely to avoid the trailing underscore. It is broader than needed and would require URL/query parity work across browser navigation.

Acceptance criteria

  1. Human plan-review register output prints Review URL: <http://.../p/plan_with_trailing_> when the API returns a review URL ending in underscore.
  2. Human plan-review index output wraps every plan review URL in angle brackets, including rows whose plan ID ends in underscore.
  3. Machine-readable --json registration output remains byte-for-byte plain JSON from the service and does not include display-only angle brackets.
  4. Plan API, route paths, comment evidence, agent-next enrichment, and stored plan IDs continue to use plain unbracketed URL or path values; relative paths such as /p/:planId and enriched absolute URLs such as http://.../p/:planId never receive terminal-display angle brackets in machine-readable payloads.
  5. README or command guidance states that printed review URLs may be angle-bracketed for terminal-safe clicking, while commands remain copy-paste ready.

BDD scenarios

Register output with trailing underscore

Given the service registers a plan with reviewUrl: "/p/plan_cli_", when the CLI prints normal human output, then the Review URL line is angle-bracketed and the clickable token includes the trailing underscore.

Index output with trailing underscore

Given the index API returns a row with reviewUrl: "/p/plan_cli_", when plan-review index prints the table, then the review URL cell is <http://.../p/plan_cli_>.

JSON remains plain

Given the same registration response, when the user passes --json, then stdout preserves the service payload exactly and contains "reviewUrl":"/p/plan_cli_", not brackets.

Normal IDs are still readable

Given a plan ID that does not end in underscore, when the CLI prints a human review URL, then the URL is still consistently bracketed so operators learn one format.
