Implementation plan

Left-hand plan navigator and collapsible comments panel

Create a plan-review page layout that keeps the user in one browser window: plans are selectable from a compact left navigator, the plan stays commentable in the center, and the comments panel is collapsed on the right by default with a top-right toggle.

Status

Execution-ready. Browser feedback and plan-review findings have been integrated. Service metadata has been registered with --execution-ready true, and the plan is ready for scoped implementation handoff.

Goal

When viewing any plan at /p/:planId, users should see a persistent left-hand list of active plans, switch plans by clicking that list, and continue using the existing plan review actions and comment/highlight workflow. The comments panel should no longer occupy the right side by default; it should be collapsed to a narrow right rail and expandable/collapsible from an icon button in the top-right toolbar.

Why this plan exists

The current review shell optimizes for one plan at a time: the plan iframe fills the left side, and a full comments panel is always visible on desktop. That makes it harder to monitor many active plans, compare execution-ready/completion status, and move between plans without returning to the index or opening many tabs. The new layout makes plan navigation the default context and makes comments available on demand.

Authority and inputs

  • User request: add a compressed left plan navigator; collapse comments right by default; provide a top-right comments expand/collapse icon; keep plan-specific review/status/build buttons at the top; keep highlighting and commenting working while switching plans.

  • src/server/app.ts: reviewShell() currently renders top actions, an iframe plan area, and an always-visible desktop comments sidebar.
  • src/server/app.ts: indexHtml(), planCardHtml(), and /api/plans already expose plan metadata, progress, comment counts, execution readiness, archive state, and source-sync status.
  • src/storage/database.ts: listPlans() derives progress from the latest HTML blob but does not currently return a human-readable plan title.
  • src/test-fixtures/e2e-run.ts: browser e2e coverage already exercises plan comments, deletion, source-sync refresh, mobile comments drawer behavior, and multi-plan API access.

Product intent alignment

  • Desired outcome advanced: the plan index truthfully reports plan status, source sync state, comment counts, repository metadata, and execution-readiness state; this change brings the same status into the plan review workspace.
  • Reviewer golden path: a reviewer opens one browser window, chooses a plan from the left, reviews the center plan content, and opens comments only when needed.
  • Safe default: comments are collapsed by default on desktop to maximize reviewable plan area, while the toggle remains visible and accessible.
  • Self-healing/recovery: plan switching uses canonical /p/:planId navigation for the first slice so all plan-scoped comment and source-sync state reinitializes safely instead of carrying stale state across plans.
  • Fail-closed boundary: if the plan list fails to load or a plan title cannot be derived, the current plan remains reviewable and the nav falls back to repo/slug labels or a small retry/error state rather than blocking commenting.
  • Actionable status: source missing, execution not ready, pending comments, and complete/incomplete progress are visible in the left nav so reviewers do not need to return to the index for routine monitoring.

Locked decisions

  • Comments default: desktop comments start collapsed to a 48px right rail; the only visible expand control is the top-right toolbar icon button. Existing mobile bottom-drawer behavior remains supported and can reuse the same expanded/collapsed state semantics.
  • Left nav default: active, non-archived plans show in the left navigator by default. Archived plans remain accessible from the existing archive surface unless the user explicitly expands scope.
  • Left nav sort: sort active plans in the left navigator by monitoring usefulness, separate from the existing listPlans() index/API ordering: complete plans first, then execution-ready incomplete plans, then in-progress/not-ready plans by progress, then source-attention items. Preserve a visible active selection even when the selected plan is not at the top.
  • Plan title source: use the rendered HTML document title when available; fall back to repoName / slug. Do not add a persisted database title column for this first slice.
  • Switching behavior: clicking a plan in the left nav navigates the current window to that plan's /p/:planId URL. This avoids stale iframe/comment/composer state and preserves browser history.
  • Plan-specific actions: execution-ready review, build/run plan, archive/restore, and status badges remain in the top toolbar for the currently selected plan. The top row contains navigation and action buttons; the current plan title/status appears in a second row below those buttons. The toolbar must use current shell styling and avoid overlapping controls through wrapping, truncation, or compact visual labels with full accessible labels.
  • Comments toggle: use a single top-right icon button with aria-controls="sidebar" and aria-expanded. The collapsed right rail is only a narrow edge/gutter and must not duplicate the icon or create a second comments control.
  • Execution boundary: the plan-review service coordinates review artifacts and request events only; implementation agents execute this plan through the repo's normal execution workflow, not inside the service runtime.

  • AC4: On desktop, the comments panel is collapsed by default and the center plan area uses the released space.
  • AC5: A single top-right icon button expands and collapses the right comments panel, updates accessible state and a visible comment-count/attention badge, and preserves existing comments list, sync warning, delete, and empty-state behavior; the collapsed right rail does not show a duplicate comments button.
  • AC6: Highlighting, selecting text/images, opening the composer, submitting comments, and rendering markers still work with the left nav present and with comments either collapsed or expanded.
  • AC7: The left navigator refreshes status through the existing /api/plans surface on initial load, after current-plan metadata changes, and on a bounded periodic interval without causing request storms.
  • AC8: On small screens, existing mobile comments behavior remains usable and the left navigator does not make the plan iframe unreachable; if necessary, the left nav becomes a drawer or horizontally accessible list in the implementation phase.

BDD scenarios

BDD1: reviewer opens a plan with the navigator visible

Given multiple active plans are registered, when the reviewer opens one plan's review URL, then the page shows the selected plan in the center, a left nav with all active plans, and a collapsed comments rail on the right.

BDD2: reviewer switches plans in one browser window

Given the reviewer is viewing Plan A, when they click Plan B in the left nav, then the current window navigates to Plan B's /p/:planId, Plan B becomes selected in the nav, and Plan B's toolbar actions target Plan B.

BDD3: reviewer creates a comment while comments are collapsed

Given the comments panel is collapsed, when the reviewer selects content in the plan and submits a comment, then the comment is created for the current plan, the comments panel remains collapsed by default, and the top-right comments button updates its passive count/attention badge without losing selection context or adding any right-rail control.

BDD4: reviewer expands and collapses comments

Given comments exist on the current plan, when the reviewer uses the top-right comments icon, then the right panel expands to show the existing comments list; when they use it again, then the panel collapses back to a narrow right rail with no duplicate icon.

BDD5: navigator is sorted by plan usefulness

Given active plans include complete, execution-ready incomplete, in-progress not-ready, and source-attention plans, when the reviewer opens the left navigator, then complete plans appear first, execution-ready incomplete plans appear before not-ready plans, and source-attention items stay visible after normal progress states.

BDD6: navigator status stays current enough for monitoring

Given plan progress or comment counts change while the page is open, when the next navigator refresh runs, then the left nav updates the affected plan's status and sorted position without reloading the center iframe or disrupting an open comment composer.

BDD7: plan list failure does not block review

Given /api/plans temporarily fails, when the review shell loads, then the current plan remains reviewable and commentable, and the left nav shows a retryable failure state instead of breaking the page.

BDD8: mobile comments remain reachable

Given a reviewer opens a plan on a narrow viewport, when they need comments, then the existing mobile comments drawer/toggle remains usable and the left plan navigation does not cover the composer or prevent plan selection.

Non-goals

  • No changes to implementation execution semantics beyond the existing request-review/build event buttons.
  • No database schema migration for persisted plan titles.
  • No cross-plan real-time SSE subscription or queue aggregation in the first implementation slice.
  • No changes to comment creation, claim, ack, resolve, release, or delete semantics.
  • No implementation execution from the plan-review service; the Build Plan request behavior remains the existing event request path.
  • No archived-plan management redesign beyond preserving existing archive access.
